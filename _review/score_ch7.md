## 二、逐题点评

### 7-1 进程、线程、协程的区别是什么 —— 81 分（良好）

- **得分**：A36 / B19 / C15 / D9 / E2

- **必答点核对**：
  - 三维框架（资源拥有 / 调度者 / 切换开销）✅ 开篇即给，且是全篇骨架
  - 进程 = 资源分配基本单位、独立地址空间、IPC ✅
  - 进程切换要换页表 ✅（"切换时要换页表"）
  - 线程 = CPU 调度基本单位、陷内核、调度器选线程、保存恢复寄存器 ✅
  - 线程栈 1MB → 万级线程内存顶不住 ✅（不错的量化锚点）
  - 线程共享 / 私有边界 ⚠️ 只讲了"共享进程资源 + 栈 1MB"，**没有**列举私有项（栈、寄存器、PC、TLS）与共享项（堆、代码段、全局数据、fd、信号处理表）
  - 用户态 vs 内核态切换 ✅
  - 1:1 模型（Java 线程 ↔ 内核线程）✅
  - M:N 模型 ⚠️ 只在 Go 上提了一句" M 个 goroutine 映射 N 个内核线程"，没展开 GMP，也没把 Java 虚拟线程明确归到 M:N
  - JDK21 虚拟线程 ✅（Project Loom、载体线程、几十万任务/几十个载体）
  - 虚拟线程 pin ❌ 完全没提（synchronized 块 / JNI 本地方法卡住载体线程）
  - Continuation（挂起/恢复的实现机理）❌ 没提
  - 协程缺点与选型边界 ❌ 没提"用户态调度不被内核感知、一个协程阻塞卡死整个线程、要事件循环才能吃满多核"
  - Go GMP ❌ 没提 G/M/P 三元结构

- **硬伤**：严格意义上**无**（无版本错误、无机制说反）。但有 2 处"似是而非"，按评分纪律第 4 条单独标注、计入 A/C：
  1. 原文"协程……也叫纤程或虚拟线程" → 正确说法：协程是**语言/运行时层面的概念族**，纤程（fiber）、Go goroutine、Kotlin 协程、JDK 虚拟线程是它的不同实现，不能划等号；尤其**虚拟线程的挂起点是隐式的**（遇到阻塞调用自动 unmount），而 Kotlin/Python 协程是**显式** `yield/await`。原文紧接着又写"程序自己决定切换点(yield/await)"，与它自己后文把虚拟线程归入协程自相矛盾，面试官一追就露。
  2. 原文"切换开销接近零，一个线程内可以挂几十万上百万个协程" → 正确说法："接近零"是**相对线程而言**的量级差（协程切换约几十~几百 ns，线程切换约 1~10 µs 且含内核态往返，进程切换再叠加换页表/TLB flush，数十 µs 级），不是字面上的零；且"几十万"的可行性来自**每个协程栈小（Go 初始 2KB 可增长）**而非仅靠切换快，原稿没给这个因果。
  3. 附带：原文"有独立的地址空间(页表、文件描述符等)" → 文件描述符表（`files_struct`）属于进程资源但**不属于地址空间**，措辞上把两者并进了括号。属表述不严谨（记入 C，不单独按硬伤扣 A）。

- **扣分点**：
  - A(-4)：上述"协程=虚拟线程"概念混同 -2；"接近零"绝对化、未标注相对性 -2。
  - B(-6)：线程私有/共享清单缺失 -2；虚拟线程 pin 场景缺失 -2；Continuation 与"载体线程 = ForkJoinPool worker、并行度 = CPU 核数"缺失 -1；协程缺点/边界缺失 -1。
  - C(-5)：**最关键的机理没点透**——线程切换之所以比进程便宜，是因为**不换地址空间、不刷 TLB、不污染 cache**，原稿只说"它比进程轻"，把因果留白了 -3；没触及内核侧结构（Linux 统一 `task_struct`、PCB/TCB） -2。
  - D(-1)："对比 Go 是 M:N 模型"这句像插进来的追问答案，打断主线；末段"多线程是不是越多越好"已偏出本题。
  - E(-3)：全篇零项目锚点，纯八股（虽然"1MB×几万线程"算半个工程体感）。

- **可加分但没说的**：
  - 现代 Linux 内核口径：进程和线程都由 `task_struct` 表示、都是调度实体，`clone()` 的 flag 决定共享哪些资源（`CLONE_VM/CLONE_FILES/CLONE_THREAD`）——说了这句，"线程是调度基本单位"就从背书升级成"知道教材口径与内核实现的差别"。
  - 现代 Linux 线程切换也**不换 CR3**；进程切换才写 CR3 并 flush TLB（有 PCID 可减少 flush）。
  - 虚拟线程的调度器是 `ForkJoinPool`（默认并行度 = `availableProcessors`），虚拟线程阻塞时通过 Continuation **unmount**，载体线程去跑别的虚拟线程。
  - JDK 24 的 JEP 491 已让 `synchronized` 不再 pin 载体线程（说这句会显得跟得上版本）。
  - 协程的代价：无法被内核抢占（一个死循环协程会饿死同线程其它协程）、栈不能跨线程随意迁移（有栈协程 vs 无栈协程）。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **"线程切换比进程切换便宜，具体便宜在哪几个动作上？"**
     → 进程切换 = 换页表（写 CR3）+ TLB flush + cache/分支预测器污染 + 内核栈与寄存器保存恢复 + 调度器决策；线程切换只做后两项，地址空间不变、TLB 不失效，所以通常快 2-3 倍，量级分别在数十 µs 与数 µs。
  2. **"JDK21 虚拟线程什么情况下会 pin 住载体线程？你们怎么发现？"**
     → 在 `synchronized` 块内发生阻塞、进入 JNI/本地方法、类初始化等场景，虚拟线程无法 unmount，会占着载体线程把 ForkJoinPool 打满；JDK21 用 `-Djdk.tracePinnedThreads=full` 打栈定位，JDK24（JEP 491）已解除 `synchronized` 的 pin，所以升级 JDK 是根本解。
  3. **"Go 的 GMP 里为什么需要 P 这一层？"**
     → G 是 goroutine（初始 2KB 可增长栈）、M 是内核线程、P 是逻辑处理器（持有本地 runqueue，数量 = GOMAXPROCS）；P 让 M 拿 G 时不必抢全局队列锁，还支撑 work-stealing 和 GC 的 STW 协作，M 被系统调用阻塞时 P 可以转交给别的 M。

- **改法（可直接替换进稿子的一段话）**：
  > 三者是不同粒度的并发执行单位，看三个维度：资源、调度者、切换成本。进程是资源分配单位，有独立地址空间（页表）、独立的 fd 表和信号处理表，隔离靠 IPC；创建要分配地址空间，切换要换 CR3/页表并刷 TLB、污染 cache，最重。线程是 CPU 调度单位（这是经典教材口径；现代 Linux 内核统一用 `task_struct` 管理，进程线程都是调度实体，差别只在 `clone` 时共享哪些资源），共享堆/代码段/全局数据/fd，私有栈（默认 1MB 左右）、寄存器、PC、TLS；切换仍要陷内核、换内核栈、存恢复寄存器、跑调度器，但不换页表，所以比进程便宜一个量级。协程是用户态调度的执行流，切换不陷内核、只存少量寄存器和栈指针，成本是线程的几十分之一（所谓"接近零"是相对线程的 ns 级，不是真为零），能开几十万是因为每个协程栈只有几 KB；代价是内核不感知、一个协程阻塞会卡住整个线程，得靠事件循环或多载体线程才能吃满多核。Java 线程是 1:1 内核线程；JDK21 虚拟线程是 M:N，JVM 把大量虚拟线程挂到 ForkJoinPool 的少量载体线程上，遇到阻塞调用就通过 Continuation unmount 让出载体线程；坑是 `synchronized` 块内阻塞和 JNI 调用会 pin 住载体线程（JDK24 JEP 491 才解决前者），排查用 `-Djdk.tracePinnedThreads`。演进就是痛点驱动：进程太重 → 线程共享资源；线程切换进内核、栈贵 → 用户态协程。

### 7-2 进程的状态、如何切换 —— 85 分（良好）

- **得分**：A39 / B20 / C15 / D9 / E2

- **必答点核对**：
  - 五态：新建 / 就绪 / 运行 / 阻塞 / 终止 ✅ 齐全且每个都给了判别性定义
  - 六种合法转换 ✅ 全对，且**主动标注了"谁触发"**（这是加分表达）
  - 三种非法转换 ✅ 阻塞→运行、新建→运行、就绪→阻塞，三条全中，且给了原因
  - 抢占 vs 主动阻塞的区分 ✅（运行→就绪 = 时间片耗尽/更高优先级抢占；运行→阻塞 = 自己请求 IO/sleep）
  - 时间片到 vs sleep 的区别 ✅ 用"被动/主动 × 可运行/不可运行"两轴切分，干净准确
  - 七态（就绪挂起 / 阻塞挂起）⚠️ 概念和换出原因（内存不足、调试观察）都对，但**转换不全**：只说了"就绪→就绪挂起、阻塞→阻塞挂起"两条换出 + 对应换入，漏了**阻塞挂起 → 就绪挂起**（挂起期间等待的事件先到了，进程回到就绪挂起队列），也没说"挂起态进程不在内存、不参与调度"
  - 抢占式 / 非抢占式调度 ❌ 完全没讲（原文只在转换里出现 preempt 一词，没有调度方式这一层）
  - Java 状态映射 ✅ NEW/TERMINATED/RUNNABLE(=就绪+运行)/BLOCKED/WAITING/TIMED_WAITING 的拆分讲对了
  - Java RUNNABLE 含 IO 阻塞 ❌ 没讲（这是本题最有区分度的加分点）
  - BLOCKED 的精确语义 ⚠️ 说成"等待锁"，但没点明**只指等 `synchronized` 监视器进入权**；且 `sleep` 落到 TIMED_WAITING 而非 BLOCKED，原稿把三者笼统归"阻塞"
  - Linux 实际状态（R/S/D/T/Z、僵尸进程）❌ 没提

- **硬伤**：无。五态、六转换、三非法、时间片 vs sleep 全部经得起核对，是本章最扎实的一段。

- **扣分点**：
  - A(-1)：仅"就绪→运行 是唯一**主动**获得 CPU 的入口"用词不当——就绪→运行是**被动**被 dispatch，主动的是"运行→阻塞"；同句"唯一入口"没问题，"主动"二字容易被抓。另"阻塞(Blocked/Waiting)"两种叫法混用，建议只说 Blocked 或 Waiting 其一。
  - B(-5)：抢断式/非抢占式调度缺失 -3（rubric 必答点）；七态转换缺"阻塞挂起→就绪挂起"且缺"挂起不占内存不参与调度" -1；Java 侧缺 RUNNABLE 含 native IO 阻塞 -1。
  - C(-5)：停在"状态机背图"层，没有下沉到内核：没提就绪队列（runqueue/CFS 红黑树）、没提 Linux `task_struct->state` 的具体标志、没提 D 状态（不可中断睡眠）与僵尸进程。七态只给"两条换出"，说明图是记的而不是推的。
  - D(-1)：六条转换用 1-6 平铺，没说"这是经典六转换全集"，缺一句收口；"阻塞(Blocked/Waiting)"命名混用。
  - E(-3)：零项目锚点；没有"线上看到大量 S/D 状态线程"这类真实体感。

- **可加分但没说的**：
  - Linux 具体状态：`TASK_RUNNING`（R，**就绪与运行在内核里是同一个状态**，这正是"JVM 区分不了就绪/运行"的呼应点）、`TASK_INTERRUPTIBLE`（S，可被信号唤醒）、`TASK_UNINTERRUPTIBLE`（D，不可中断，常见于磁盘 IO，kill -9 也杀不掉）、`__TASK_STOPPED`（T）、`EXIT_ZOMBIE`（Z）。
  - 僵尸进程（子进程退出、父进程未 `wait`，PCB 不释放占 PID）与孤儿进程（父先死，被 init/systemd 收养）——进程状态题最经典的两个延伸。
  - 上下文切换成本构成：用户态→内核态、保存现场、调度器选下一个、切换地址空间、返回用户态；`vmstat` 的 `cs`、`pidstat -w` 可观测。
  - "就绪→运行"由调度器 dispatch，"阻塞→就绪"由**中断/软中断**里唤醒（IO 完成中断），这条因果原稿给了"IO 中断处理完"，其实已经踩到点上，可以再抬一句"所以唤醒发生在中断上下文"。
  - Java `Thread.sleep` 在 jstack 里是 `TIMED_WAITING (sleeping)`，而 `synchronized` 竞争才是 `BLOCKED (on object monitor)`——用 jstack 现象反证状态语义，很有说服力。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **"Linux 里进程状态到底有哪几个？D 状态是什么、能不能 kill 掉？"**
     → `task_struct->state` 主要有 R（TASK_RUNNING，含就绪+运行）、S（可中断睡眠）、D（不可中断睡眠，等磁盘/NFS IO，不响应信号，kill -9 也杀不掉）、T（STOPPED）、Z（僵尸）；D 状态大量堆积通常意味着 IO 子系统或存储打挂了。
  2. **"僵尸进程怎么产生、怎么处理？孤儿进程呢？"**
     → 子进程退出后内核保留其退出码和 PCB 等父进程 `wait/waitpid` 回收，这期间就是僵尸（Z），会占 PID；父进程先死则子进程成孤儿被 init/systemd 收养并由它回收；处理僵尸要么父进程正确 `wait` 或处理 `SIGCHLD`，要么杀掉父进程让 init 接管。
  3. **"jstack 里一片 RUNNABLE，是不是说明 CPU 打满了？"**
     → 不一定。JVM 的 RUNNABLE 包含"在 native 里阻塞"的情况（`socket read`、文件 IO 等），这些线程在 OS 侧是睡眠的；要结合 `nid` 去 `top -H`/`pidstat` 看 OS 线程状态和 CPU 占用，R 才算真跑。

- **改法（可直接替换/补进稿子的两段话）**：
  > 补七态与调度方式：七态在五态上加了**就绪挂起**和**阻塞挂起**——挂起就是把进程换出到外存，它不占内存、不参与调度，动机是内存不足或调试观察。转换在六条之外多了：就绪→就绪挂起、阻塞→阻塞挂起（换出），就绪挂起→就绪、阻塞挂起→阻塞（换入），以及**阻塞挂起→就绪挂起**（挂起期间等的事件先到了，进程还不能跑，先挪到就绪挂起队列）。调度方式上分**非抢占式**（进程不主动放弃就一直跑，早期批处理、Windows 3.1）和**抢占式**（时间片到期或更高优先级到来就剥夺 CPU，现代通用 OS 都是），今天说的"运行→就绪"只在抢占式下才存在。
  >
  > 补 Java 侧：映射时要注意两点——一是 `RUNNABLE` = 就绪 + 运行，而且**在 native 里阻塞（socket read、文件 IO）也报 RUNNABLE**，所以 jstack 全是 RUNNABLE 不等于 CPU 打满；二是 `BLOCKED` 只指等 `synchronized` 监视器进入权，`WAITING/TIMED_WAITING` 才是 `wait/join/park/sleep` 这类主动等待（`sleep` 落在 `TIMED_WAITING (sleeping)`，这正好和"阻塞 vs 时间片"的语义区分对应上）。

## 三、本章小结

- **平均分 83**，最高 **85（7-2）**，最低 **81（7-1）**，两题均为"良好"档，无硬伤、无一票否决项。
- 结论：这两题的信息密度在"短答"里算高的，**框架都是面试官喜欢的**（结论先行 + 三/六条编号 + 主动排雷）；丢分不在错，而在"**深度没到底、必答点缺 2-3 个**"。按当前稿件直接上场，能拿到"合格偏上"，但遇到追问底层（pin、TLB、Linux 状态、D 状态、RUNNABLE 语义）会断在第二问。

**最容易被面试官击穿的点（按严重度排序）**：

1. **"协程切换开销接近零"没标注相对性**（7-1）——面试官必问"具体多少 ns？为什么不是零？"，需立刻补"是相对线程的 ns 级 vs µs 级差距"，并说明"能开几十万"靠的是几个 KB 的小栈。
2. **虚拟线程 pin 完全没提**（7-1）——JDK21 虚拟线程的坑只有一个标准答案（`synchronized` 块内阻塞 / JNI 本地方法 pin 住载体线程），说了是加分项，不说等于只会官方文档第一段。
3. **七态转换只讲了两出两进**（7-2）——"阻塞挂起时等待的事件提前到了，进程去哪？"答不出"就绪挂起"，就暴露图是背的不是推的。
4. **Java RUNNABLE 含 IO 阻塞没讲**（7-2）——这是 Java 岗问 OS 状态唯一的"落地接口"，缺了会显得 OS 与 Java 两张皮。
5. **"线程是 CPU 调度基本单位"未加口径说明**（7-1）——现代 Linux 两者都由 `task_struct` 表示，一句"这是经典教材口径，内核里统一按 task 管"就能把背书变成懂行。

**最值得保留的亮点**：

1. **7-1 的三维骨架 + 痛点驱动演进**（资源/调度者/开销 → 进程重所以有线程，线程贵所以有协程），一段话把三个概念串成因果链，非常好背也经得起"为什么会有协程"的追问。
