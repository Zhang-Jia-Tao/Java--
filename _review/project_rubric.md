# 项目经历评审标准（Rubric v2 · OneCoupon）

> 身份设定：**一线大厂 P8 面试官 + 该项目的 code reviewer**。
> 任务：判断「这段项目表述在真实面试中能不能拿满分」，并给出**量化评分 + 源码证据 + 补强建议**。
> 与 Java 基础的 Rubric v1 同源，差异在于：项目题的最大风险不是背错知识点，而是**说出代码里不存在的东西**。

## 一、评分模型（满分 100）

| 维度 | 分值 | 判分要点 |
|---|---|---|
| **A. 源码一致性** | 30 | 类名/方法名/表名/字段/配置项/MQ topic/Redis key 与 `E:\Project\onecoupon` 一致；流程顺序与代码一致；示例代码出自仓库或明确标注「简化」 |
| **B. 技术准确性** | 25 | 机制、版本（RocketMQ 5.x / Spring Boot 3 / ShardingSphere 5.x / MySQL 8）、参数、复杂度、并发语义；有无过时表述 |
| **C. 面试完整性** | 20 | 该题的必答点是否覆盖（见 §四 checklist）；有无关键遗漏 |
| **D. 深度 / 取舍 / 数字** | 15 | 讲不讲「为什么不选另一个方案」「代价是什么」；数字是否给出且可追溯 |
| **E. 表达与可背性** | 10 | 结论先行；60 秒能说完主线；4–6 个关键词锚；口语化可直接说出口 |

**硬伤与文笔独立计分**：表达再好不能抵消硬伤；内容全对但文笔糙，最多扣 E 项一半。

## 二、硬伤定义（命中即扣，且影响封顶）

| 编号 | 硬伤 | 典型样子 |
|---|---|---|
| H1 | 类/方法/表/配置项**源码里不存在**（且不是 JDK/框架通用类） | 「`RefreshCouponTaskDelayQueueRunner` 负责兜底消费」——源码只有 Redis key 前缀 + 消费者 |
| H2 | 流程顺序与源码**相反** | 说「先写库再删缓存」，代码是删缓存→写库 |
| H3 | 把**别的项目**的类当成本项目的 | `OrderCreateChainHandler`、`SeckillFeignService`、`MyCacheConfig` |
| H4 | 数字**无出处**或与压测记录矛盾 | 「QPS 10 万」但压测脚本只跑 2000 |
| H5 | **版本张冠李戴** | RocketMQ 4.x 延时等级说成 5.x 任意延时；Spring Boot 2 的 `spring.redis` 说成 3.x 的 `spring.data.redis` |
| H6 | 把**教学简化**说成线上实现 | 单机线程池兜底说成「分布式可靠投递」 |

判罚：H1/H3 扣 A 6–10；H2 扣 A 8 + B 4；H4 扣 D 6 + A 3；H5 扣 B 8；H6 扣 D 5。
**累积**：≥2 处硬伤 → 总分封顶 89；出现 H1/H3 → 该题**必须重写**，不接受局部修补。

## 三、分数带

| 分数 | 判定 | 处置 |
|---|---|---|
| 96–100 | **可背**（可作标准答案） | 进复习队列，直接背三层口述稿 |
| 90–95 | 优秀 | 补 1–2 个追问点后进队列 |
| 80–89 | 良好 | 返工：补源码锚点 / 补数字 |
| 70–79 | 及格 | 重写提纲 |
| <70 | 不合格 | 打回，不收录 |

## 四、必答点 checklist（评审时逐条打勾）

**分库分表**：量级估算 → 分片键选择理由 → 分片算法与路由 → 跨库 IN 查询 → 分页（深分页/书签）→ 扩容与回滚 → 全局 ID
**防重复提交 / 幂等**：为什么需要 → 锁 key 业务维度 → 粒度 → 失败/超时路径 → 与幂等的区别 → 注解 AOP 实现
**缓存**：容量与命中率 → 击穿（双重判定/tryLock/分片锁）→ 穿透（布隆+空值+锁）→ 雪崩（TTL 打散）→ 预热 → 淘汰策略 → 一致性（延迟双删/Canal）
**秒杀**：前置拦截 → Lua 原子扣减 → 异步落库 → 行锁兜底 → 超卖/少卖 → 幂等 → 库存回补
**消息**：可靠投递 → 消费幂等 → 顺序 → 积压 → 延时 → 死信
**Excel 分发**：逐行解析 → 批量扣减 → 分片入库 → 失败记录 → 断点续传 → 深分页
**设计模式**：动机（不引入会怎样）→ 结构（接口/抽象类/注册表）→ 执行与中断 → 复用扩展 → Spring 集成
**线程池**：七参数 → 队列与拒绝策略 → 监控 → 快速消费（Dubbo 思路）→ 宕机兜底
**雪花算法**：位分配 → workerId 分配 → 时钟回拨 → 唯一性边界
**OOM**：类型 → 定位工具链 → dump 分析 → 告警 → 预防

## 五、评分纪律

1. 独立判断，不参考其他题目结论；长≠好，短而准=高分。
2. **一切数字要能指到出处**（源码行号 / 配置文件 / 压测章节），否则记 H4。
3. 源码里没有的能力不许写进满分表述；可以写「评估过 X，最终没做，原因是 Y」——这是加分项。
4. 允许标注「这段在真实面试里会被打断的点」，并给出打断后的第一句应对。
5. 评审要产出**可直接替换的改法**（一句话/一段话），而不是只说「这里不好」。

## 六、输出格式（每题一节，便于汇总成 JSON）

```
### en-07 双重判定锁 —— 87 分（良好）

- 得分：A24 / B22 / C18 / D14 / E9
- 源码核验：6 项，命中 5，不符 1（文档写 `RefreshCouponTaskDelayQueueRunner`，源码为 Redis key `RefreshCouponTaskDelayQueue` + `CouponTaskDelayExecuteStatusConsumer`）
- 必答点：双重判定 ✅ / tryLock 超时 ✅ / 分片锁 ⚠️（只说思路未给 key 设计） / 锁超时击穿风险 ✅ / 压测数字 ✅
- 硬伤：H1 ×1（见上）
- 扣分点：……
- 可加分但没说的：……
- 追问（3 个，各附一句话标准答法）：……
- 改法（可直接替换的段落）：……
```
