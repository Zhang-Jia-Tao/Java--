## 二、逐题点评

### 6a-1 TCP 三次握手的过程以及为什么是三次 —— 86 分（良好）

- **得分**：A40 / B19 / C15 / D9 / E3
- **必答点核对**：
  - SYN / SYN+ACK / ACK 三步 ✅（顺序、携带 ISN、合并 SYN+ACK 的理由都对）
  - ISN 随机化的两条理由 ✅✅（防旧报文串号 + 防序列号预测攻击）——这是本题做得最好的部分，超出多数候选人
  - 为什么不是两次 ✅（防止已失效连接请求报文导致服务端空建连接）
  - 为什么不是四次 ✅（SYN+ACK 可合并）——但只说"没必要"，未说"四次在信息量上等价于三次，是冗余"
  - 服务端状态迁移 ✅（LISTEN→SYN_RCVD→ESTABLISHED）
  - 客户端状态迁移 ⚠️（CLOSED→SYN_SENT→ESTABLISHED 给了，但漏掉发送 ACK 后客户端即 ESTABLISHED、以及 SYN 重传导致的 CLOSED 回退）
  - SYN 洪泛 / 半连接队列（SYN queue）与 accept 队列 ❌ **完全缺失**
  - SYN 重传（指数退避、tcp_syn_retries）❌ 缺失
  - 第三次握手为什么可以携带数据（及安全性前提）❌ 缺失
  - syncookies（syncache）作为半连接队列打满的兜底 ⚠️ 未提
- **硬伤**：无。技术表述均正确，"客户端收到 SYN+ACK 发 ACK 后进入 ESTABLISHED" 这一常被讲错的点，原文是对的。
- **扣分点**：
  - B 扣 6：**半连接队列/accept 队列 + SYN Flood + syncookies 是本题的第一大追问点**，原文一个字没提。面试官问"SYN Flood 怎么防"会直接卡住。另缺 SYN 重传与"第三次可带数据"。
  - C 扣 5：状态机只给了四个状态点的点亮，没有讲"为什么 SYN_RCVD 是半连接""队列满了服务端丢包而不回 RST"这种机制层因果；`net.core.somaxconn` 与 `tcp_max_syn_backlog` 两个队列的关系（accept 队列 vs 半连接队列）缺失，而这正是区分"背过"和"懂"的分水岭。
  - E 扣 2：章节开头的项目锚点（Druid 建连、Feign 调用）没有落到本题正文，属于"锚点在页首、题内无故事"。
- **可加分但没说的**：
  - 半连接队列与全连接队列的溢出行为差异：SYN 队列满 → 服务端丢弃 SYN（客户端表现为超时重传）；accept 队列满 → 服务端通常丢弃或（`tcp_abort_on_overflow=1` 时）回 RST。
  - "三次握手不可省略第三次"的 TCP 层理由：服务端在第三次握手前不分配完整连接资源（socket/缓冲区），这本身就是抗攻击设计。
  - ISN 随机化实现口径：Linux 用 hash(四元组) + 时钟驱动，同一四元组短时间重建也不会复用 ISN。
- **面试官追问（3 个，附一句话标准答法）**：
  1. **SYN Flood 怎么防？内核做了哪些事？** —— 开 `net.ipv4.tcp_syncookies=1`（半连接队列满时用 cookie 代替入队，不占内存），配合 `tcp_max_syn_backlog`/`somaxconn` 调大队列，再加 SYN 代理或限速；应用层治本是把 accept 队列消费干净（线程池/连接池别堵）。
  2. **服务端 listen 的 backlog 到底是哪个队列？** —— backlog 主要约束**全连接队列**（已完成三次握手待 accept 的连接数，`ss -lnt` 的 Send-Q 就是它）；半连接队列由 `tcp_max_syn_backlog` 单独控制，两者不是一回事。
  3. **为什么第三次握手可以带数据，前两次不行？** —— 前两次握手时对端还没确认自己的序列号与接收能力，带数据可能被拒收/重放；第三次握手后客户端已确认服务端可达，服务端也已有接收窗口，可安全捎带（但存在被用于反射/放大攻击的风险，需谨慎）。
- **改法（可直接替换进稿子的一段话）**：
  > 三次握手的第三步不只是"礼貌回复"：服务端到收到 ACK 才真正分配连接资源，所以第三次是**防资源耗尽**的关键。工程上要关心两个队列——半连接队列（收到 SYN、回 SYN+ACK 后等 ACK 的会话，由 `tcp_max_syn_backlog` 控制）和全连接队列（已完成握手等应用 accept，长度就是 listen 的 backlog，`ss -lnt` 的 Send-Q）。SYN Flood 打的就是半连接队列，兜底手段是 `tcp_syncookies=1`；线上真正的坑往往是全连接队列溢出——应用 accept 太慢，表现是"偶发连接超时"，我们在 Druid/Feign 的高并发池上调过 `somaxconn` 并压测验证过。

### 6a-2 TCP 四次挥手的过程以及为什么是四次 —— 81 分（良好）

- **得分**：A39 / B16 / C14 / D9 / E3
- **必答点核对**：
  - FIN / ACK / FIN / ACK 四步 ✅
  - 全双工、两个方向各关一次、FIN 与 ACK 不能合并 ✅（解释到位）
  - TIME_WAIT 两个作用 ✅（保证最后 ACK 可达 + 让旧报文在网络中消亡）
  - 2MSL 推导 ✅（对端重发 FIN、我方重发 ACK，一来一回最坏 2MSL）
  - **Linux MSL 默认 60s、TIME_WAIT 120s ✅ 且明确标注是 Linux 默认值**（这点做得规范，很多人直接写"2 分钟"却不说明来源）
  - TIME_WAIT 由谁进入 ⚠️ 隐式（写的是"主动关闭方"），但没点明"服务端主动关闭时 TIME_WAIT 压在服务端"
  - TIME_WAIT 危害 ❌ 缺失（端口/四元组耗尽、`Cannot assign requested address`、内存占用）
  - TIME_WAIT 调优 ❌ 缺失（`tcp_tw_reuse` + `tcp_timestamps`、`tcp_max_tw_buckets`、`SO_LINGER`、长连接/连接池从根上规避）
  - CLOSE_WAIT 含义与危害 ❌ **完全缺失**（这是四次挥手题最高频追问）
  - 挥手状态机（FIN_WAIT_1/FIN_WAIT_2/CLOSING/LAST_ACK/TIME_WAIT/CLOSED）❌ 缺失（Q1 给了握手状态机，Q2 反而没给）
  - 半关闭（shutdown 写端、TCP 半关闭不等于进程关闭）⚠️ 未提
  - FIN 占一个序号、FIN 可携带数据 ⚠️ 未提
- **硬伤**：无。MSL=60s 已正确标注为 Linux 默认值，2MSL=120s 的推导也正确（正文第 60-62 行）。附录 2.2 写"2MSL（通常 2 分钟）"与正文一致，不算冲突。
- **扣分点**：
  - B 扣 9：**TIME_WAIT 的危害与调优 + CLOSE_WAIT 含义**是本题两大必答追问，原文只有机制没有工程面。原文虽在页首锚点写了"TIME_WAIT → 秒杀短连接堆积（keep-alive + 连接池规避）"，但正文完全没有展开，锚点等于没用上。
  - C 扣 6：没有状态机迁移图；没有解释"为什么 TIME_WAIT 要存在而不是靠 RST 了事"；没有 `tcp_tw_reuse` 为何必须配合 `tcp_timestamps`（PAWS 时间戳防旧报文）这层因果——这是区分"背过"和"调过"的地方。
  - D 扣 1：第二次挥手写"此时主动方向的连接关闭"，措辞含糊（应为"主动关闭方的**发送通道**关闭，被动方仍可发数据"），口语表达时容易被抓字眼。
  - E 扣 2：锚点未落地（见上）。
- **可加分但没说的**：
  - `tcp_tw_reuse` 只在**主动发起连接**的一方生效，且内核要求开启 `tcp_timestamps`，否则会破坏 PAWS 而有串包风险；`tcp_tw_recycle` 在 NAT 环境下有严重问题，已在新内核（4.12+）移除，**不要提"开 recycle"**。
  - 大量 CLOSE_WAIT = 应用层收到 FIN 后没有 `close()`（连接泄漏/线程池卡死/HTTP 客户端未归还连接），这个是要改代码不是改内核参数——这是 P8 最爱问的"归因方向"题。
  - TIME_WAIT 过多时首选方案是**减少短连接**（HTTP keep-alive、连接池、RPC 长连接），内核参数只是缓解。
- **面试官追问（3 个，附一句话标准答法）**：
  1. **服务器上大量 CLOSE_WAIT 是什么原因？** —— 对端已发 FIN，我方应用没调用 `close()`：连接泄漏、连接池未归还、或线程池打满导致 IO 线程读不到 EOF；排查看 `ss -tan state close-wait` 对应的进程 fd，修代码而不是调内核。
  2. **TIME_WAIT 太多影响什么？怎么优化？** —— 影响主要是本地**端口/四元组**耗尽（`Cannot assign requested address`）和少量内存；优化顺序是"先长连接/连接池，再 `tcp_tw_reuse=1` 且必须开 `tcp_timestamps`，必要时调 `tcp_max_tw_buckets`"，绝不能开已废弃的 `tcp_tw_recycle`。
  3. **为什么 TIME_WAIT 是 2MSL 而不是 1MSL？** —— 我的 ACK 最多走 1 个 MSL 到对端，对端若没收到会重发 FIN，FIN 最多再走 1 个 MSL 回来；2MSL 保证"我的 ACK 能到 + 对端的重发 FIN 能被我收到并再回 ACK"，同时也保证本连接双向残留报文全部过期。
- **改法（可直接替换进稿子的一段话）**：
  > 2MSL 不是可选的"等待"，它同时承担两件事：让最后一个 ACK 有机会重发成功，以及让本连接的所有旧报文在网络中彻底消亡，避免污染下一个复用同一四元组的连接。代价是主动关闭方要占着 TIME_WAIT 一段时间（Linux 默认 MSL 60s，即 120s）。线上高频短连接会把端口耗干，我们的处理顺序是：先改成 keep-alive/连接池从根上减少 TIME_WAIT，再考虑 `tcp_tw_reuse=1`（必须同时开 `tcp_timestamps` 以防旧包串入）。另外要会看 CLOSE_WAIT——那个方向的问题永远在应用代码里，是连接没 close，调内核参数没用。

### 6a-3 TCP 和 UDP 的区别 —— 76 分（及格）

- **得分**：A39 / B14 / C11 / D9 / E3
- **必答点核对**：
  - 面向连接 vs 无连接 ✅
  - 可靠（序列号 + 确认应答 + 超时重传）vs 不可靠 ✅
  - 字节流 vs 数据报、消息边界与粘包 ✅（提到"需要处理粘包"，是加分表述）
  - 流量控制/拥塞控制 ✅（TCP 侧）
  - 适用场景 ✅（文件/网页/邮件 vs 视频/直播/游戏）
  - **首部开销 20 字节 vs 8 字节 ❌ 完全缺失**（含选项字段最多 60 字节的常识）
  - **分片/IP 层分片 ❌ 完全缺失**（UDP 保留边界但超 MTU 会在 IP 层分片、任一分片丢失整包丢弃；TCP 按 MSS 分段，由传输层负责重组）
  - 一对一 / 一对多 / 多对多（广播、组播仅 UDP 支持）❌ 缺失
  - UDP 无连接、无状态、不维护连接资源 ⚠️ 只说了"无连接"，没落到"服务端不需要为每个客户端维护连接状态"这个可扩展性差异
  - 应用层需自行实现可靠性（重传、序号、拥塞控制）⚠️ 未提
  - QUIC 基于 UDP ✅（明确的加分点）
- **硬伤**：无。没有说反的地方（"网叶浏览"是抽取错字，不计）。
- **扣分点**：
  - B 扣 11：**首部 20 vs 8 字节**与**IP 分片**是这道题的两张"硬指标牌"，一个都没有；缺一对多/广播组播；缺"UDP 上做可靠性"的责任转移表述。本题必答点覆盖不到 60%。
  - C 扣 9：全篇是"特性罗列 + 场景罗列"，没有一条落到机制：TCP 首部有哪些字段（seq/ack/window/flags）、为什么是 20 字节；UDP 校验和可选、没有序号所以谈不上重排；TCP 的"字节流"如何由 seq 编号 + 重组实现。属于典型"只背结论"。
  - E 扣 2：QUIC 一句是亮点，但没接到项目（如 SSE/WebSocket 走 TCP 的队头阻塞代价）。
- **可加分但没说的**：
  - 首部对比可以一句话出彩："TCP 首部最少 20 字节（带选项可到 60），UDP 固定 8 字节——只占 4 个字段，这就是它开销小的原因"。
  - 分片的正确口径：UDP 大包在 IP 层被分片，任何一个分片丢失整个 UDP 报文被丢弃（且很多中间设备直接丢分片），所以应用层要自己控制包大小（DNS 的 512B/EDNS0 就是这个原因）。
  - UDP 也可"可靠"：QUIC 在用户态实现序号、重传、拥塞控制（CUBIC/BBR）、0-RTT，本质是"把 TCP 的机制搬到应用层换掉内核队头阻塞"。
- **面试官追问（3 个，附一句话标准答法）**：
  1. **TCP 首部和 UDP 首部分别多大？UDP 为什么不带序号？** —— TCP 定长部分 20 字节（加选项最多 60），字段里 seq/ack/window/flags 全是可靠传输和流控的支撑；UDP 固定 8 字节（源/目的端口、长度、校验和），设计上就不保证有序可靠，所以不需要序号，需要的话由应用层自己加。
  2. **UDP 会不会分片？丢了怎么办？** —— 超过 MTU 时由 IP 层分片，只要一片丢失整包丢弃且接收端无法重组，所以 UDP 应用要自己把包控制在 MTU 内（DNS 512B、EDNS0 扩到 1232/4096）；要可靠就在应用层做 QUIC/KCP。
  3. **为什么说 TCP 是字节流、UDP 是数据报？工程后果是什么？** —— TCP 不保留消息边界，一次 read 可能拿到半个包或多个包，所以要有"长度字段/分隔符"的粘包拆包协议；UDP 一次 send 对应一次 recv，边界天然保留，但要求应用自己处理乱序和丢失。
- **改法（可直接替换进稿子的一段话）**：
  > 差异落到三个硬指标上：**首部** TCP 最少 20 字节、UDP 固定 8 字节；**边界** TCP 是字节流无消息边界（所以要自定义长度头解决粘包），UDP 一次发一次收边界天然保留，但超 MTU 会被 IP 层分片、丢一片整包作废；**连接状态** TCP 每个连接都要在内核维护状态（四元组 + 收发缓冲 + 窗口），UDP 无状态，所以一个 socket 就能服务海量客户端，广播/组播也只有 UDP 支持。QUIC 就是把这套可靠性搬到用户态跑在 UDP 上，绕开内核 TCP 的队头阻塞和握手延迟。

  - BBR 的对比句式："CUBIC 把丢包当拥塞信号，在高丢包/高 BDP 链路上会误降速；BBR 用带宽时延积建模，主动探测瓶颈带宽与最小 RTT，YouTube/Google 边缘实测吞吐提升明显"。
  - 一整套串联话术："rwnd 管接收方吃不消，cwnd 管网络吃不消，发送窗口取两者最小值——所以一条链路上谁先成为瓶颈，谁的窗口说话"。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **接收方窗口变成 0 了会怎样？发送方一直等吗？** —— 发送方进入零窗口状态并启动**坚持定时器（persist timer）**周期性发窗口探测，接收方窗口恢复后用 ACK 通告新 rwnd；没有这个机制双方会死锁在互相等待上。
  2. **为什么快重传是 3 个重复 ACK，不是 2 个也不是 5 个？** —— 轻微乱序通常只造成 1-2 个重复 ACK，3 个是"基本可判定真丢包"的经验阈值；同时它把"等超时（秒级）"缩短成"几个 RTT"，代价远小于超时（超时会把 cwnd 打回 1 MSS）。
  3. **CUBIC 和 BBR 的本质区别？** —— CUBIC 是"丢包驱动"：以丢包为拥塞信号，用三次函数在丢包后快速恢复到上次窗口附近；BBR 是"模型驱动"：持续估计瓶颈带宽和最小 RTT 来算发送速率，不把丢包等同于拥塞，所以在有随机丢包的链路上不会误降速。
- **改法（可直接替换进稿子的一段话）**：
  > 流量控制看的是**接收方**，拥塞控制看的是**网络**，发送窗口取两者的 min。流量控制的边界是零窗口：接收方缓冲满时通告 rwnd=0，发送方启动坚持定时器发探测包，否则双方死锁；另外 rwnd 字段只有 16 位（64KB 上限），高带宽时延积链路必须靠窗口扩大因子（Window Scale）才能跑满。拥塞控制这边，超时和 3 个重复 ACK 是两种不同严重度的信号：3 dupACK 说明 ACK 流还在、只是某段丢了，走快重传 + 快恢复（ssthresh=cwnd/2，直接进拥塞避免）；超时说明连 ACK 都没了，cwnd 打回 1 重新慢启动。初始 cwnd 老教材写 1 MSS，RFC 6928 已改成 10 MSS，所以严格说"初始 cwnd 恒为 1"是过时口径。

  2. **为什么现在都用 ECDHE 而不是 RSA 密钥交换？** —— ECDHE 提供**前向安全**：每次握手生成临时密钥对，服务器长期私钥将来泄露也解不开历史流量；RSA 密钥交换用长期公钥加密 PMS，私钥一泄露历史全破，而且 TLS1.3 已删除该方式。
  3. **抓包能看到 HTTPS 的内容吗？怎么排查线上 HTTPS 问题？** —— 内容看不到（对称加密），但能看到 SNI、证书、TLS 版本和握手耗时；排查靠 `openssl s_client -connect host:443 -servername 域名` 看证书链和协商套件，或用浏览器/网关的 TLS 握手耗时指标判断是证书链不全还是 RTT 太高。
- **改法（可直接替换进稿子的一段话）**：
  > 两者的区别可以压成七个维度：端口 80 vs 443、URL scheme、明文 vs TLS 加密、无证书 vs CA 证书链校验、协议栈多了 TLS 层（可用 ALPN 协商到 h2）、性能多了握手 RTT 与加解密开销、以及 SEO 加权和浏览器"不安全"告警及部分 Web API 的强制要求。握手这块要分版本讲：TLS1.2 完整握手 2-RTT——ClientHello（版本/套件/Client Random/SNI/ALPN）→ ServerHello（Server Random + 证书 + **ServerKeyExchange（ECDHE 参数与签名）** + ServerHelloDone）→ ClientKeyExchange（客户端临时公钥）+ CCS + Finished → 服务端 CCS + Finished；现代主流是 ECDHE，PMS 由双方各自算出而不是 RSA 加密传输，这也带来前向安全；会话复用（Session ID/Ticket）降到 1-RTT；TLS1.3 靠 ClientHello 里直接带 key_share 做到 1-RTT，PSK 恢复可 0-RTT，同时删掉了 RSA 密钥交换和静态 DH。

  - Feign 的落地实话："Feign 默认走 HTTP/1.1 + JSON，性能不如 Dubbo，但胜在通用、可被网关统一治理；要提性能就上 gRPC 或换 OkHttp 连接池"。
- **面试官追问（3 个，附一句话标准答法）**：
  1. **gRPC 不就是 HTTP/2 吗？那还谈什么 RPC 和 HTTP 的区别？** —— 对，gRPC 正是"RPC 调用模型 + HTTP/2 传输"的组合：它用 HTTP/2 的多路复用和头部压缩，但用 Protobuf 二进制体 + IDL 代码生成，所以"RPC vs HTTP"本质是**私有二进制协议 vs 通用文本协议**的权衡，不是传输层之争。
  2. **为什么 RPC 比 HTTP 快？具体快在哪？** —— 三层：报文头（Dubbo 头部约 16 字节 vs HTTP 文本头数百字节）、序列化（Protobuf/Hessian2 二进制，体积和解析 CPU 都远小于 JSON）、连接（长连接复用，省掉每次三次握手和慢启动）。
  3. **RPC 这么好，为什么对外还提供 HTTP 接口？** —— 通用性和可调试性：跨语言、跨组织、能被浏览器/Postman/网关直接消费，无需分发 IDL 和 SDK；RPC 的强绑定换来性能与治理，但也带来跨语言成本和版本耦合。
- **改法（可直接替换进稿子的一段话）**：
  > 先说清关系：RPC 是**远程调用的编程模型**（Remote Procedure Call，远程过程调用），HTTP 是**应用层协议**，两者不在一个层面——RPC 可以跑在 TCP 自定义协议上（Dubbo、Thrift），也可以跑在 HTTP/2 上（gRPC）。真正的对比是"私有二进制协议 + 代码生成 + 服务治理" vs "通用文本协议 + 松耦合"。所以工程结论是：对外用 HTTP（通用、跨语言、易调试、能被网关和浏览器直接消费），对内用 RPC（更小的报文头、Protobuf/Hessian2 二进制序列化、长连接多路复用省掉重复握手和慢启动、框架自带负载均衡/熔断/重试/链路追踪）。代价是 RPC 强绑定框架和 IDL，跨语言、跨团队协作成本更高。

**总体判断**：传输层（握手/挥手/拥塞控制）是本稿的**强区**——机制讲得对、口径规范（MSL 标注 Linux 默认值、cwnd 主动补 RFC 6928），已接近可背诵标准答案；应用层（HTTP/HTTPS/RPC）是本稿的**弱区**——存在"承诺了维度但没内容""只讲结论不讲机制""术语错误"三类系统性问题。全章无 90+，核心原因不是错得多，而是**每道题都缺 2-3 个必答追问点的答案**，且 6a-7/6a-9 各有一处会被当场打穿的口径错误。

### 2) 最容易被面试官击穿的 5 个点（按严重度排序）

1. **6a-7 承诺"七大维度对比"后直接跳到握手（第 268-269 行），对比表不存在** —— 这是全章最严重的结构性缺陷。面试官听到"我从七个维度对比"就会盯着这七个维度，"端口、证书、SEO、TLS1.2/1.3 RTT" 一个都答不上来，比"从来没提"更扣分。
2. **6a-7 / 6a-8 把 HTTPS 握手讲成 RSA 密钥交换一条路：漏 ServerKeyExchange，PMS 用服务器公钥加密当通用路径，"两次往返"当通用结论** —— 现代主流是 ECDHE（有前向安全），TLS1.3 已删除 RSA 密钥交换。追问一句"ECDHE 下 PMS 怎么来的？"就会卡死；再追"TLS1.3 为什么 1-RTT"同样卡死（缺 key_share）。
3. **6a-8 三随机数的作用解释错误："即使其中一个被破解也不会影响整个会话"** —— 会话密钥 = PRF(PMS, CR/ SR)，**PMS 泄露即会话全破**。这是全章唯一的"硬事实错误"，且出现在最该讲准的密钥派生环节。
4. **6a-1 缺半连接队列/accept 队列 + SYN Flood；6a-2 缺 TIME_WAIT 危害调优 + CLOSE_WAIT** —— 传输层机制全对，但一到"线上出问题怎么查/怎么调"就空白。P8 面试几乎必问"服务端大量 CLOSE_WAIT 什么原因""SYN Flood 怎么防"，这两处会直接把 86/81 打成追问尴尬。
5. **6a-5 "Token 安全性最高 > Session > Cookie" + 缺 HttpOnly/SameSite；6a-9 "远程核心调用" + 未提 gRPC over HTTP/2** —— 前者是过度结论（Token 放 localStorage 反而怕 XSS、且不可吊销），后者是术语错误 + 概念关系没理清（RPC 与 HTTP 不是同层对立）。

### 3) 最值得保留的 3 个亮点

1. **6a-1 的 ISN 随机化双理由**（防旧连接报文串号 + 防序列号预测/伪造攻击）与**完整握手状态迁移** —— 多数稿子只写"为了安全"，这里给了两条互不重叠的技术动机，且状态机落在正确的边（客户端收到 SYN+ACK 才 ESTABLISHED）。
2. **6a-4 的口径自觉**：主动区分"老教材初始 cwnd=1 MSS"与"RFC 6928(2013) 的 10 MSS"并给出动机，还提到 CUBIC/BBR 与 keep-alive 复用避免反复慢启动 —— 这是本章唯一具备"版本演进意识 + 工程联动"的题，A 项满分当之无愧。
3. **6a-8 的三条误区澄清**（会话密钥从不上网、默认只验证服务端身份、**0-RTT 有重放风险不能传敏感数据**）+ **6a-7 的"加密防看/摘要防改/证书防假"口诀** —— 前者证明作者读过 TLS1.3 的真实细节，后者是极好的口述记忆钩子，两者都应该保留并推广到其他章节。
