## 二、逐题点评

### 6b-3 TCP 的滑动窗口和拥塞控制 —— 71 分（及格）

- **得分**：A37 / B16 / C10 / D7 / E1

**必答点核对**

| 必答点 | 覆盖 |
|---|---|
| 滑动窗口目的（防止发送方压垮接收方 = 流量控制） | ✅ |
| 发送窗口三段结构（已确认 / 已发送未确认 / 可发送）+ 左边界滑动 | ✅ 图示清楚 |
| 接收窗口 + rwnd 通过 ACK 通告 | ✅ |
| **发送窗口 = min(rwnd, cwnd)** | ❌ **最关键一点缺失**（原文把两套机制并列讲，从未合流） |
| 窗口字段只有 16 位 → 窗口缩放 wscale（RFC1323） | ❌ |
| 零窗口 + 坚持定时器 / 窗口探测 | ❌ |
| 累积确认 / SACK（选择确认） | ❌ |
| 慢启动：cwnd 每 RTT 翻倍，到 ssthresh 切换 | ✅ 公式对 |
| 拥塞避免：每 RTT +1 MSS（线性） | ✅ 公式对 |
| RTO 超时：ssthresh=cwnd/2、cwnd=1 | ✅ 完全正确 |
| 3 重复 ACK：快重传（立即重传，不等 RTO） | ⚠️ 只写了 cwnd 参数，**没写"立即重传丢失段"这个动作**，把"快重传"漏成了"快恢复" |
| 3 重复 ACK：快恢复 ssthresh=cwnd/2、cwnd=ssthresh | ✅ 数值等价的写法（`cwnd=cwnd/2`）。Reno 严格写法是 `cwnd=ssthresh+3*MSS` 膨胀、收到新 ACK 后收敛到 ssthresh —— 原文未提 |
| 概念区分：流量控制 vs 拥塞控制（端到端 vs 网络） | ⚠️ 靠两个小标题隐含，未显式对比 |
| 算法演进（CUBIC / BBR） | ❌ |

**硬伤**：无。`ssthresh=cwnd/2, cwnd=1`、`每 ACK +1/cwnd` 等易错公式全部正确，`cwnd=cwnd/2` 与 `cwnd=ssthresh` 数值等价，不算错。
**唯一算"似是而非"的一处**：`cwnd = 1 MSS` 起手 —— 这是经典教材值，**现代 Linux 初始窗口已是 10 MSS（RFC 6928）**，原文未加注，面试官问"你抓过包吗，初始 cwnd 是几"会尴尬。

**扣分点**
- B（-9）：最致命的不是漏细节，而是**流量控制和拥塞控制各说各话、没合成 `发送窗口 = min(rwnd, cwnd)`**。面试官问"到底能发多少"时，答不出"取两者较小值"等于这题没答完。
- C（-10）：全篇是结论清单，没有讲清"窗口靠 16 位字段承载 → 长肥管道必须靠 wscale"这条因果，也没有 TCP 状态机/算法演进视角。属于"能背不能推"。
- D（-3）：两个模块之间没有过渡句；缺一句"两者是两道独立闸门"的总纲，听完仍是碎片。
- E（-4）：没有一个可讲的故事锚点（例如"线上跨国同步大文件吞吐只有 20Mbps，最后定位到 wscale 未协商 + BDP 过大"）。

**可加分但没说的**
- 零窗口死锁与探测计时器（真实的"连接卡死"根因之一）。
- 糊涂窗口综合症（SWS）与 Nagle / delayed ACK 的相互作用。
- 接收窗口还受**接收缓冲区**限制、发送窗口受**发送缓冲区**限制，"窗口不是凭空来的"。
- CUBIC 是 Linux 默认、BBR 不依赖丢包建模（这一句就能把 C 项拉回来）。

**面试官追问（3 个，附一句话标准答法）**
1. **"流量控制和拥塞控制到底怎么共存？发送方一次能发多少？"**
   → `发送窗口 = min(rwnd, cwnd)`：rwnd 是接收方通告的处理余量，cwnd 是发送方探测到的网络余量，取小者才不会撞破任一方的墙。
2. **"rwnd 只有 16 位、最大 65535 字节，千兆长肥管道怎么跑满？"**
   → 靠 RFC1323 的窗口缩放选项，握手时协商 shift count，实际窗口 = 字段值 << shift，最大可到 2^30；不协商则 BDP 大的链路吞吐被硬卡死。
3. **"快重传和快恢复什么区别？收到 3 个重复 ACK 具体发生什么？"**
   → 快重传是**动作**（立刻重传疑似丢失的那一段，不等 RTO 超时），快恢复是**状态**（ssthresh=cwnd/2、cwnd=ssthresh 后直接进拥塞避免，不回慢启动）。

**改法（可直接背的一段）**
> "TCP 的发送窗口取 `min(rwnd, cwnd)`：rwnd 由接收方在 ACK 的 16 位窗口字段里通告（有 wscale 缩放可达 2^30），管的是'别把接收方打爆'；cwnd 由发送方按拥塞状态机维护，管的是'别把网络打爆'。cwnd 演进三条线：慢启动每收一个 ACK +1 MSS，等效每 RTT 翻倍，到 ssthresh 转拥塞避免，每 RTT 线性 +1 MSS；RTO 超时判定为严重拥塞，ssthresh=cwnd/2、cwnd=1 重新慢启动；收到 3 个重复 ACK 判定为单段丢失，立刻重传该段（快重传），ssthresh=cwnd/2、cwnd=ssthresh(+3MSS 膨胀)进入快恢复，收到新 ACK 后回落到 ssthresh 继续拥塞避免。接收窗口为 0 时发送方启动 persist timer 做零窗口探测，否则双方会互相等死。"

### 6b-5 HTTPS 的工作原理 —— 70 分（及格）

- **得分**：A36 / B15 / C10 / D8 / E1

**必答点核对**

| 必答点 | 覆盖 |
|---|---|
| HTTPS = HTTP over TLS，解决 明文/篡改/冒充 三问题 | ⚠️ 隐含未点明 |
| ClientHello（版本/套件/随机数）→ ServerHello | ✅ |
| Certificate（证书链）+ ServerHelloDone | ✅ 只提"下发"，未提"验证" |
| **客户端校验证书**：CA 签名逐级验到受信根、域名 SAN、有效期、吊销(CRL/OCSP) | ❌ **本题最大缺口** |
| ClientKeyExchange（公钥加密 PreMasterSecret） | ✅ |
| ChangeCipherSpec / Finished（握手摘要校验） | ✅ |
| 由 pre_master + client_random + server_random 派生 master_secret / key block | ⚠️ 只说"派生对称密钥"，未提随机数的防重放作用 |
| 业务数据用对称加密 | ✅ |
| 数据完整性（MAC / AEAD、MAC-then-Encrypt → AEAD 演进） | ❌ |
| 为什么不用纯非对称（性能 100~1000 倍） | ✅ 口径标准，可直接用 |
| 非对称既做密钥交换**也做签名/身份认证** | ❌ 只讲了密钥交换 |
| 前向安全（PFS）与 RSA 密钥交换的淘汰 | ❌ **深度分水岭** |
| SNI（一 IP 多域名 / ECH） | ❌ |
| TLS1.3：1-RTT、0-RTT(PSK)、废弃 RSA 交换、只留 AEAD、证书加密传输 | ❌ |
| 会话复用（Session ID / Session Ticket） | ❌ |

**硬伤**：无。8 步时序、`PreMasterSecret 用服务端公钥加密`、`非对称仅交换密钥、业务走对称`、`慢 100~1000 倍` 全部正确，编号与报文名也没写错。

**扣分点**
- A（-4）：把 **RSA 密钥交换**当作"HTTPS 的握手"来完整呈现，却没标注这是**已被 TLS1.3 删除、且不提供前向安全的老方案**。事实没错，但属 rubric 明确要扣的"过时表述"——现在生产是 ECDHE。
- B（-10）：**证书验证整段缺失**。这题面试官的第一反应就是"你怎么确认对面不是中间人"，缺了这段等于"HTTPS 为什么安全"只答了一半（只有加密，没有认证）。
- C（-10）：停在"流程复述"层，没有 master_secret 派生、没有 PFS 原理、没有 TLS1.3 精简动机，属于"背过文档但没想通设计"。
- D（-2）：时序图漂亮可讲，但缺开篇一句结论（"HTTPS 干三件事：认证、协商密钥、加密+完整性"），结尾也没有把"为什么安全"收口。
- E（-4）：无项目锚点（如"证书过期导致线上 502，用 openssl s_client 排到链不全"）。

**可加分但没说的**
- 中间人攻击的完整推演：为什么"公钥直接给"不行、CA 的信任锚从哪来（操作系统/浏览器内置根证书）。
- 双向认证 mTLS（内网服务间调用常用）。
- RSA 交换 vs ECDHE 交换的报文差异（ServerKeyExchange 只在后者出现，且带签名）——这一点能证明真读过抓包。
- OCSP Stapling / HSTS / Certificate Transparency。

**面试官追问（3 个，附一句话标准答法）**
1. **"中间人把服务器公钥换成自己的，客户端怎么发现？"**
   → 证书由受信根 CA 逐级签名，浏览器用内置根公钥验签整条链，再校验 SAN 域名、有效期和吊销状态；攻击者拿不到 CA 私钥就伪造不出能验过的链——这才是 HTTPS 的"认证"，不是加密本身。
2. **"为什么握手要传两个随机数？只传 premaster 不够吗？"**
   → 保证每次会话密钥都不同，防重放和预计算攻击；RSA 模式下随机数还参与 premaster 混淆，ECDHE 模式下双方随机数共同参与密钥派生。
3. **"TLS1.3 为什么能 1-RTT？前向安全是什么？"**
   → 客户端在 ClientHello 里就带上猜好的 key_share，服务端一次回完参数，省掉一个往返（PSK 还能 0-RTT，但有重放风险）；前向安全指长期私钥泄露也解不开历史流量，ECDHE 每次临时密钥用完即弃，而 RSA 密钥交换不满足、所以被 TLS1.3 删除。

**改法（可直接背的一段）**
> "HTTPS 就是 HTTP 套在 TLS 上，一次握手同时办成三件事：**认证**（服务端出示证书链，客户端用内置根 CA 公钥逐级验签，并校验域名、有效期、吊销状态）、**协商密钥**（ECDHE 交换出只有双方知道的共享密钥，具备前向安全）、**后续数据的机密性与完整性**（AES-GCM 这类 AEAD 套件）。TLS1.2 完整握手 2-RTT：ClientHello（版本、套件、client_random、SNI）→ ServerHello + Certificate + ServerKeyExchange(带签名) + ServerHelloDone → 客户端验证书、发 ClientKeyExchange + CCS + Finished → 服务端 CCS + Finished；双方用 pre_master 加两个随机数经 PRF 派生出 master_secret 和会话密钥。老教材里的 RSA 密钥交换只用于交换密钥、且私钥泄露可解历史流量，TLS1.3 已删除它，同时把握手压到 1-RTT（PSK 支持 0-RTT）、只保留 AEAD 套件、连证书都加密传输。之所以不全程用非对称，是因为 RSA-2048 比 AES 慢 100~1000 倍，只适合做一次性的密钥交换和签名。"

### 6b-6 连接池（数据库/HTTP/Redis）的原理 —— 66 分（不合格）

- **得分**：A35 / B12 / C9 / D8 / E2

**必答点核对**

| 必答点 | 覆盖 |
|---|---|
| 池化动机一：省 TCP 握手 + TLS 握手 + 认证的固定 RTT | ✅ 且有量化（1.5 + 1~2 + 0.5 RTT） |
| 池化动机二：**给后端加并发上限、保护 DB 不被打爆** | ❌ **只讲了省时间，没讲限流保护** |
| 生命周期：预热 → 借出 → 使用 → 归还 → 健康检测 → 销毁 | ✅ 完整 |
| `close()` 被代理拦截，实际是归还不是关闭 | ✅ 写得很准 |
| 容量参数：maxPoolSize / minIdle / connectionTimeout / idleTimeout / maxLifetime | ⚠️ 只提了 `initialSize=5`，**没有上限参数**，等于没讲"池"的核心约束 |
| 池满时排队 + 获取超时（connectionTimeout 抛异常） | ❌ |
| 健康检测（testOnBorrow/testWhileIdle/validationQuery/keepalive） | ✅ 提了 testWhileIdle（注意这是 Druid/DBCP 参数名，HikariCP 用 keepaliveTime/isValid） |
| 泄漏检测（leakDetectionThreshold） | ❌ |
| **数据库 / HTTP / Redis 三类池的差异** | ❌ **题目点名的三分之内容量，零区分** |
| 常见实现：HikariCP(ConcurrentBag) / Druid / HttpClient 连接池 / Lettuce / Jedis | ❌ |
| HTTP 池的 keep-alive 语义与 stale connection 处理 | ❌ |
| 池大小怎么估算（DB 连接数 ≈ CPU核数×2+磁盘数，或 TPS×平均耗时） | ❌ |

**硬伤**：无（`initialSize=5`、`destroy-method="close"` 是配置示例，不是规范断言）。
**一处口径不严谨**：`建立 TCP 连接: 1.5 RTT` —— 严格说客户端收完 SYN-ACK 即可发数据，是 **1 RTT**；1.5 RTT 是"含第三次 ACK 抵达服务端"的算法，属常见教材口径，算"似是而非"而非硬伤，但面试官抠细节时会问。

**扣分点**
- B（-13）：**题目问的是"数据库/HTTP/Redis"三种池的原理，答案只给了一个通用池化的模板**。三者恰恰是三种不同范式——DB 连接是**有状态会话**（必须一借一还、事务绑定）、HTTP 连接是 **keep-alive 复用同一 TCP**（还要处理服务端先关的 stale 连接）、Redis 的 Lettuce 是**单连接多路复用、压根不需要池**。这一层没答，"原理"就是空的。
- A（-5）中的 1.5 RTT 口径 + `testWhileIdle` 参数名混用不同产品。
- C（-11）：没有并发数据结构（HikariCP 的 ConcurrentBag + ThreadLocal 缓存 lastReturned）、没有"归还即 reset 会话状态"这条关键机制、没有池大小估算公式。
- D（-2）：流程图清晰，但缺"先给结论再展开"和三类池对比表。
- E（-3）：无调优/踩坑（如"连接池 maxPoolSize 设成 100 反而把 DB 打挂"）。

**可加分但没说的**
- 连接是**有状态资源**：归还前要 reset autoCommit、隔离级别、临时表、会话变量、`SET NAMES`，否则脏状态串到下个业务。
- 池化 + 线程池的联动关系（Web 线程池 200、DB 池 20，就是排队放大的经典事故）。
- HikariCP 快在哪：无锁 ConcurrentBag + 代理 Connection + 字节码优化（Javassist）、放弃 Statement 缓存。
- Redis：Jedis 每线程一连接必须 JedisPool；Lettuce 基于 Netty，一条连接多路复用、线程安全，池只用于阻塞命令（BLPOP）场景。

**面试官追问（3 个，附一句话标准答法）**
1. **"Redis 客户端为什么很多场景不用连接池？"**
   → 因为 Lettuce 基于 Netty，一条连接上多路复用所有请求、天然线程安全；只有 Jedis 这种同步阻塞、一连接一线程的模型才必须要 JedisPool，池的意义从"省握手"变成了"支持并发"。
2. **"连接池里的连接被服务端单方面关了（MySQL wait_timeout、Nginx keepalive_timeout），会发生什么？"**
   → 借出一条已死的连接，第一次读写报 `Communications link failure` / `NoHttpResponseException`；靠 keepalive 探活、maxLifetime 短于服务端超时、以及有限重试兜住。
3. **"maxPoolSize 设多大？是不是越大越好？"**
   → 不是，DB 连接数是硬资源，经验值约 `CPU核数×2 + 磁盘数`（HikariCP 官方口径），或用 TPS×平均SQL耗时 估；设太大只会把数据库的连接数、上下文切换和锁竞争打爆，业务侧 RTT 反而更长。

**改法（可直接背的一段）**
> "连接池把'有状态的长连接'当资源池化，收益有两条：一是省掉每次新建的固定开销（TCP 三次握手 + TLS 握手 + 认证，跨公网 50~200ms，池里借出只要 0.1~1ms）；二是给后端加一道并发上限（maxPoolSize），防止流量突刺把 DB 打挂——第二条比第一条更重要。机制上：启动预热 minIdle 条；借出走空闲队列，HikariCP 用 ConcurrentBag 加 ThreadLocal 缓存上次归还的连接，多数场景近似无锁，池空未达上限则新建，达上限就按 connectionTimeout 排队；业务调 `close()` 时被代理 Connection 拦截，实际动作是 **reset 会话状态后归还**而不是关闭；idleTimeout/maxLifetime 驱逐空闲与超龄连接，keepalive 定时保活，leakDetectionThreshold 抓未归还的泄漏。三类池的差别在协议语义：数据库连接是有状态会话，必须一借一还并与事务绑定；HTTP 池靠 keep-alive 复用同一条 TCP（maxTotal/maxPerRoute），要额外处理服务端已先关的 stale 连接；Redis 的 Lettuce 是单连接多路复用、不需要池，Jedis 才必须配 JedisPool。"

### 6b-7 JDBC 的 Connection 是不是线程安全的 —— 70 分（及格）

- **得分**：A36 / B14 / C9 / D8 / E3

**必答点核对**

| 必答点 | 覆盖 |
|---|---|
| 结论：不保证线程安全（JDBC 规范明确 Connection 无需线程安全） | ✅ 结论先行，干脆 |
| 原因一：一个 Connection 挂一个事务上下文（autoCommit/隔离级别/commit）共享可变状态 | ✅ 代码例子举得很到位 |
| 原因二：底层一条 TCP + 一个数据库会话，协议请求-应答**严格串行**，并发会响应错配 | ❌ **深度分水岭缺失** |
| Statement/ResultSet 与创建它的 Connection 绑定，同样非线程安全 | ❌ |
| 正确做法：每线程/每请求从池借独立连接 + try-with-resources 归还 | ✅ |
| 连接与事务绑定（Spring DataSourceUtils + ThreadLocal；跨线程事务失效） | ❌ |

| 未关闭连接的危害（泄漏、耗尽池） | ❌ |
| 会话状态残留需 reset | ❌ |
| synchronized 方案的适用边界（能救急、生产不可取） | ❌ 反而被当成"正确做法"之一列出 |

**硬伤**：无。结论正确、错误用例（A 线程 setAutoCommit(false)+insert、B 线程 commit）是教科书级的准确反例。

**扣分点**
- A（-4）：`方式2: 同一个 Connection，用 synchronized 包裹事务操作` 被归到**"正确的多线程连接管理"**标题下。技术上加锁确实能互斥，所以不算硬伤；但它把并发退化成串行、锁范围必须覆盖 Statement/ResultSet 全生命周期、事务边界还容易跨业务——**把它和"每线程一个连接"并列，会被面试官当场反问**。这是全篇最值得改的一处"似是而非"。
- B（-11）：缺"为什么"的第二层（协议串行/会话有状态）、缺事务与连接的绑定机制（这是 Spring 事务八股的入口）、缺泄漏危害。
- C（-11）：只到"状态互相覆盖"这一句，没有往协议层/会话层下探，也没有 HikariCP ProxyConnection 的语义。
- D（-2）：结构不错（结论 + 错例 + 正例），但"方式1/方式2/项目做法"平铺，没有给出"推荐度"排序与取舍。
- E（-2）：有 `openSession() + try-with-resources` 这个项目锚点，是本章唯一有"我在项目里这么写"味道的题，值得再加一句踩坑。

**可加分但没说的**
- 为什么 HikariCP 敢把同一个物理连接给不同线程用：因为它保证**同一时刻只有一个线程持有**，归还时会 reset 会话并清空 Statement 缓存，所以"先后复用安全、并发不安全"。
- MyBatis 的 `DefaultSqlSession` 同样非线程安全，`SqlSessionTemplate` 是用动态代理绑定到线程上才安全的——这个例子能把 Spring 与 MyBatis 串起来。
- 连接泄漏的排查：池 active 贴在 maxPoolSize、借连接超时，开 `leakDetectionThreshold` 打印持有点堆栈。
- 数据库端会话副作用：`last_insert_id`、`@@session` 变量、临时表都是跟着连接走的，跨线程复用会串数据。

**面试官追问（3 个，附一句话标准答法）**
1. **"那我在同一个 Connection 外面加把 synchronized 锁，行不行？"**
   → 能保证不出错，但等于把并发串行化，而且锁粒度必须覆盖 Statement/ResultSet 的整个使用期、极易漏锁，事务边界也会被拉长；连接池存在的意义就是让并发不共享连接，所以生产上不用这条路。
2. **"Spring 事务方法里另起一个线程，能拿到同一个 Connection 吗？"**
   → 不能，Connection 由 `TransactionSynchronizationManager` 绑在 ThreadLocal 上，新线程拿不到就是重新从池借一条、等于新事务；这也是 `@Async`、`@Transactional` 自调用在跨线程场景失效的根因。
3. **"连接泄漏怎么发现、怎么防？"**
   → 现象是池 active 数长期贴着上限、业务侧大量获取超时；HikariCP 打开 `leakDetectionThreshold` 会打印借用堆栈定位；防法是 try-with-resources + MyBatis/Spring 模板统一托管。

**改法（可直接背的一段）**
> "不保证线程安全，JDBC 规范只要求 Driver 和 DataSource 线程安全，Connection 没这个要求。原因有两层：一层是**会话状态**——一个 Connection 对应一条 TCP 和一个数据库会话，会话上挂着 autoCommit、隔离级别、当前事务、临时表、`last_insert_id` 这些可变状态，两个线程一起改就会互相覆盖，A 线程 `setAutoCommit(false)` 而 B 线程 `commit()` 直接就把别人的事务提交了；另一层是**协议串行**——同一时刻一条连接上只能有一个请求在飞，并发写 SQL 会让回来的 ResultSet 张冠李戴，而 Statement/ResultSet 又都绑定在创建它们的 Connection 上。正确做法是连接跟着事务走：每请求/每线程从池里借一条独立的连接，用 try-with-resources 保证归还；Spring 把 Connection 绑到 ThreadLocal（`DataSourceUtils` + `TransactionSynchronizationManager`），同事务内多次 DAO 调用复用同一条，跨线程就失效。HikariCP 交给业务的是 ProxyConnection，close() 是归还并重置会话状态，所以同一连接被不同线程**先后**使用是安全的，**并发**使用才不安全。"

**可加分但没说的**
- 缓存键设计错误造成的两类事故：键太粗 → 串内容（A 用户看到 B 用户数据）；键太细（把随机 query 全算进去）→ 命中率趋零、回源打爆源站。

**面试官追问（3 个，附一句话标准答法）**
1. **"CDN 是怎么把用户导到最近节点的？"**
   → 权威 DNS 把业务域名 CNAME 到 CDN 厂商域名，厂商的 GSLB 结合 EDNS Client Subnet 里的客户端网段、节点健康与负载、运营商归属，返回最优边缘 IP；此外还有 302 调度和 Anycast 两种方案。
2. **"发了新版本，用户还看到旧图，怎么办？"**
   → 两条腿：purge 刷新（推到全边缘失效，有秒级到分钟级延迟）和预热（发布前主动回源拉热，避免首批用户打穿源站）；工程上更稳的是文件名带 content hash，URL 变了缓存键自然变，再配一年 max-age。
3. **"CDN 的缓存键是什么？搞错了会怎样？"**
   → 默认是 host + path，可按需把 query string、指定 Vary 头、cookie 纳入；少算了会串内容，多算了（比如把随机参数算进去）会让命中率崩掉、请求全打回源站。

**改法（可直接背的一段）**
> "CDN 本质是**分布在各地的反向代理 + 多级缓存**，靠'就近接入'把 RTT 和源站压力同时降下来。链路是：用户请求业务域名 → 权威 DNS 返回 CNAME 指向 CDN 厂商域名 → 厂商 GSLB 结合客户端网段（EDNS Client Subnet）、运营商、节点健康与负载，返回最优边缘节点 IP → 边缘按缓存键（默认 host+path，可选 query/Vary/cookie）查本地缓存，命中直接返回，未命中就回源（一般先到中间层父节点、再收敛到源站，压回源率），拿到后按 Cache-Control/max-age 落缓存再返回。运维上两个动作：**预热**（发布前主动把热点资源拉到边缘）和**刷新**（内容变更后推失效，有延迟）；配合文件名 content hash 才能既长缓存又秒级生效。动态内容可以走动态加速：边缘到源站走专线/最优路径、长连接复用回源、协议优化。另外证书和 TLS 通常终结在边缘。"

- 强缓存命中时连 HTTP 请求都不发（`from disk cache`），协商缓存命中发请求收 304 不传 body——**这是"完整过程"里最容易加分的一句**。
- `defer` vs `async` 的准确区别（async 下载完立刻执行、顺序不保证；defer 在解析完成后按序执行、早于 DOMContentLoaded）。
- transform/opacity 走合成层，不触发重排重绘，这也是"为什么动画推荐 transform"。
- 服务端那段可以落到 Java 语境：Nginx 反代 → Tomcat NIO 线程池 → Spring MVC DispatcherServlet → 业务 → 模板/JSON。

**面试官追问（3 个，附一句话标准答法）**
1. **"第二次访问同一个页面，哪些步骤会省掉？"**
   → DNS 有缓存直接命中、TCP/TLS 靠 keep-alive 与会话复用、强缓存未过期时连 HTTP 请求都不发，直接 `from cache` 出页面；只有协商缓存命中才发一次带 If-None-Match 的请求收 304。
2. **"defer 和 async 有什么区别？为什么说 JS 会阻塞解析？"**
   → 两者都并行下载、不阻塞解析；async 下载完立刻执行且顺序不保证，defer 等 HTML 解析完按文档顺序执行、在 DOMContentLoaded 之前。普通 `<script>` 没有这两个属性时，解析器必须停下等它下载并执行完，因为脚本可能 `document.write` 改文档结构。
3. **"重排和重绘、合成的区别？为什么动画推荐 transform？"**
   → 几何属性变化要重新布局（reflow，最贵），只改颜色等走重绘（repaint），transform/opacity 可以只在合成层做（composite，最便宜）；所以动画优先 transform/opacity，避免布局抖动。

**改法（可直接背的一段，也是这题的标准骨架）**
> "我会分网络、服务端、渲染三段讲。**网络段**：先解析并规范化 URL（协议、域名、端口、路径、query，注意 HSTS 和搜索词判定）→ 查缓存决定要不要发请求（强缓存 Cache-Control/Expires 未过期直接 from cache；过期则带 If-None-Match/If-Modified-Since 走协商，服务端回 304 就复用本地副本）→ DNS 解析：浏览器缓存 → 系统缓存/hosts → 本地 DNS 递归查根、顶级、权威得到 A/CNAME 记录 → 若已有 keep-alive 连接可复用，否则 TCP 三次握手，HTTPS 再走 TLS 握手（TLS1.3 1-RTT）→ 发 HTTP 请求（请求行 + Host + Cookie 等头）→ 服务端（Nginx → Tomcat 线程池 → Spring MVC）处理并返回响应，其间可能有 301/302 重定向要重走前面几步。**渲染段**：解析 HTML 建 DOM，同时预加载扫描器提前拉资源；CSS 建 CSSOM（CSS 是渲染阻塞资源，因为要等 CSSOM 才能生成渲染树，且会阻塞其后 script 执行）；DOM + CSSOM 合成渲染树（不含 display:none 和 head）→ 布局算几何位置 → 绘制 → 分层合成上屏（transform/opacity 只走合成，不触发重排重绘）。遇到 script 时解析器会暂停等它下载执行，除非标了 async（下载完就执行、顺序不定）或 defer（解析完按序执行、早于 DOMContentLoaded）。"

### 最容易被面试官击穿的点（按严重度排序）
1. **6b-6：题目点名"数据库/HTTP/Redis"三类池，答案零区分。** 这是最严重的结构性失分——面试官下一句必然是"那 Redis 为什么很多场景不需要连接池"，答案会立刻露馅。
2. **6b-5：整段没有"证书是怎么被验证的"。** HTTPS 被问"怎么防中间人"答不出，等于只讲了加密没讲认证；再加上只讲已被 TLS1.3 删除的 RSA 密钥交换、完全不提前向安全，会被判定为"看过博客没抓过包"。
3. **6b-3：流量控制和拥塞控制各说各话，没有合成 `发送窗口 = min(rwnd, cwnd)`。** 两道闸门不合流，"一次到底能发多少"这一问就是死穴。
4. **6b-9：完全没有 HTTP 缓存，也没有 CSSOM/合成。** "到页面显示"这题考的就是"到底发不发请求""为什么要等 CSS"，两处都空。
5. **6b-7：把 `synchronized (conn) { ... }` 写进"正确的多线程连接管理"。** 不算硬伤，但被反问"加锁就安全了？"时会解释不清，且会把"连接池的意义"讲反。

### 全章共性缺口（补一次，六题同时受益）
- **缺"取 min / 取小"这类合流句**：两套机制并列讲完不收口（6b-3 的 rwnd×cwnd、6b-6 的省时间×限流）。
- **缺"失效/异常路径"**：只讲 happy path —— 零窗口、stale connection、证书过期、缓存穿透、连接泄漏全无。
- **缺工程数字**：仅 6b-6 有 RTT 量化，其余没有一条可讲的参数或实测（wscale shift、初始 cwnd 10 MSS、maxPoolSize 估算、max-age 与 purge 延迟）。

### 最值得保留的 3 条亮点
1. **6b-3 的窗口 ASCII 图 + 四分支公式表**（超时 `ssthresh=cwnd/2, cwnd=1`；3 dup ACK `ssthresh=cwnd/2, cwnd=cwnd/2`）。数值全对，是全篇最"可直接背"的资产，稍加 `min()` 与 wscale 就能上 90。
2. **6b-6 用 RTT 拆解复用收益**（TCP 1.5 + TLS 1~2 + 认证 0.5 = 50~200ms/次 vs 池内 0.1~1ms）。这种"用数量级说话"的讲法比"省资源"高级一档，是本章唯一有工程味的论证（只需把 1.5 RTT 改成 1 RTT 的口径说明）。
3. **6b-7 的结构**：结论先行 → 错误代码 → 正确写法 → 项目里 `openSession() + try-with-resources`。这是六题里唯一"有项目锚点"的答案，把它的写法复制到其他五题（每題加一句"我在项目里遇到…"），E 项能整体从 1-3 分提到 4-5 分。
