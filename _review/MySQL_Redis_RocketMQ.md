### Q1\. 执行一条SQL请求的过程是什么？

面试官您好，一条 SQL 在 MySQL 中的执行流程，分为**客户端、Server 层、存储引擎层**三大部分，我按步骤说：

第一步是**连接器**，客户端先和 MySQL 建立 TCP 连接，验证账号密码和权限，通过后分配连接线程。

~~第二步是~~**~~查询缓存~~**~~，不过 MySQL 8\.0 已经删掉了，因为表一更新缓存就失效，命中率太低。~~

第三步是**分析器**，对 SQL 做词法和语法分析，检查语法对错、表和字段是否存在，生成解析树。

第四步是**优化器**，这是核心，它会选择最优的索引、确定表关联顺序，生成最终的执行计划。

第五步是**执行器**，根据执行计划调用存储引擎的接口，开始真正执行 SQL。

第六步是**存储引擎**，比如 InnoDB，负责从磁盘或内存读取 / 修改数据，返回给执行器。最后执行器把结果返回给客户端。

如果是**更新 SQL**，除了上面流程，还会额外写 undo 日志（回滚）、redo 日志（持久化）和 binlog 日志（主从复制），保证数据安全和事务特性。

> **优化补充**：更新 SQL 的日志写入顺序是：① 写 **undo log**（记录旧值，用于回滚）；② 执行更新，修改 Buffer Pool 中的数据页（脏页）；③ 写 **redo log**（prepare 状态，记录物理修改，用于崩溃恢复）；④ 写 **binlog**（记录逻辑操作，用于主从复制）；⑤ redo log 提交（commit 状态）。redo log 和 binlog 的**两阶段提交**（2PC）是保证两者一致性的关键机制。
> 
> **"redo log 和 binlog 为什么要两阶段提交？"**
> 
> 如果没有两阶段提交：① 先写 redo log 再写 binlog，崩溃后 redo log 有记录但 binlog 没有，主从数据不一致；② 先写 binlog 再写 redo log，崩溃后 binlog 有记录但 redo log 没有，主库回滚但从库已经执行，同样不一致。两阶段提交保证要么两者都提交，要么都回滚，保持一致。
> 
> **"Buffer Pool 是什么？"**
> 
> InnoDB 的内存缓冲区，将磁盘数据页缓存在内存中，读写操作优先走 Buffer Pool，避免频繁磁盘 IO。修改后的页成为**脏页**，由后台线程按一定策略异步刷回磁盘（checkpoint 机制）。Buffer Pool 的大小直接影响数据库性能，生产中通常设置为物理内存的 50%\~80%。
> 
> 

这就是一条 SQL 完整的执行过程。

### Q2\. 说一下mysql的innodb与MyISAM的区别？

InnoDB 和 MyISAM 是 MySQL 两大存储引擎，我从核心区别和适用场景来讲：

第一，**事务支持**：InnoDB 完整支持 ACID 事务、可以提交回滚；MyISAM 完全不支持事务，操作不能回滚。

第二，**锁机制**是最大区别。InnoDB 支持**行级锁**，走索引就锁行，读写可以并发；只有没索引才退化成表锁。而 MyISAM 只有**表级锁**，只要有写操作，就锁住整张表，阻塞所有读写，并发很差。

第三，**MVCC 和并发**：InnoDB 支持多版本并发控制，实现读不加锁、读写互不阻塞；MyISAM 没有 MVCC，不支持事务隔离。

第四，**数据安全与崩溃恢复**：InnoDB 有 redo 和 undo 日志，服务器宕机可以自动恢复数据，很安全；MyISAM 没有事务日志，宕机容易表损坏、数据丢失，还要手动修复。

第五，**索引结构**：InnoDB 是聚簇索引，主键叶子存整行数据，二级索引需要回表；MyISAM 是非聚簇索引，索引和数据分离，不用回表。

> **"为什么 InnoDB 推荐使用自增主键？"**
> 
> 自增主键保证新数据总插入到 B\+ 树的最右端，页分裂和页合并概率最低，插入性能最好。如果用 UUID 这类随机主键，新数据会插入到 B\+ 树的随机位置，频繁触发页分裂，导致索引碎片化，性能下降，~~且 UUID 占用 36 字节远大于 bigint 的 8 字节，二级索引的叶子节点存储主键值会占用更多空间。~~
> 
> 

另外还有几个小点：InnoDB 支持外键，MyISAM 不支持；InnoDB 缓存索引和数据，MyISAM 只缓存索引；MyISAM 原生支持全文索引，InnoDB 后期才支持。

适用场景上，现在**业务系统全部用 InnoDB**，支持事务、高并发、数据安全；MyISAM 已经基本淘汰，只适合那种只读、几乎不修改的静态历史表。

### Q3\. MySQL 怎么连表查询？

数据库有以下几种联表查询类型：

1. 内连接 \(INNER JOIN\)：返回两个表中有匹配关系的行

2. 左外连接 \(LEFT JOIN\)：左外连接返回左表中的所有行，即使在右表中没有匹配的行。未匹配的右表列会包含NULL

3. 右外连接 \(RIGHT JOIN\)：右外连接返回右表中的所有行，即使左表中没有匹配的行。未匹配的左表列会包含NULL。

4. 全外连接 \(FULL JOIN\)：全外连接返回两个表中所有行，包括非匹配行，在MySQL中，FULL JOIN 需要使用 UNION 来实现。因为 MySQL 不直接支持 FULL JOIN

```SQL
SELECT employees. name, departments. name
FROM employees
LEFT JOIN departments
ON employees.department_id = departments.id

UNION

SELECT employees. name, departments. name
FROM employees
RIGHT JOIN departments
ON employees.department_id = departments.id;
```

### Q4\. MySQL如何避免重复插入数据？

方式一：使用UNIQUE约束，在创建表时，在表的相关列上添加UNIQUE\[juˈniːk\]约束，确保每个值在该列中唯一

```SQL
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(255) UNIQUE,
    name VARCHAR(255)
);
```

> **优化补充**：UNIQUE 约束底层是通过**唯一索引**实现的。InnoDB 在 B\+ 树索引中对唯一键加了**唯一性约束检查**，插入或更新时先查索引确认不存在重复值，存在则抛出 `Duplicate entry` 错误（错误码 1062）。因此 UNIQUE 约束的性能开销和普通索引差不多，只是多了一次唯一性校验。
> 
> 

方式二：使用`INSERT ... ON DUPLICATE KEY UPDATE`，在插入记录时处理重复键的情况，如果插入的记录与现有记录冲突，可以选择更新现有记录

```SQL
INSERT INTO users (email, name) 
VALUES ('example@example.com', 'John Doe')
ON DUPLICATE KEY UPDATE name = VALUES(name);
```

方式三：使用`INSERT IGNORE`：该语句会在插入记录时忽略那些因重复键而导致的插入错误。

选择哪种方法取决于具体的需求：

- 如果需要保证全局唯一性，使用UNIQUE约束是最佳做法。

- 如果需要插入和更新结合可以使用`ON DUPLICATE KEY UPDATE`。

- 对于快速忽略重复插入，`INSERT IGNORE`是合适的选择。

> **优化补充**：`INSERT IGNORE` 不仅忽略主键/唯一键冲突，还会**静默忽略几乎所有的错误和警告**，包括数据截断、类型不匹配、NOT NULL 约束违反等。这意味着你可能插入了不符合预期的数据却毫不知情。因此生产中慎用 `INSERT IGNORE`，优先使用 `ON DUPLICATE KEY UPDATE`，异常处理更可控。
>

### Q5\. CHAR 和 VARCHAR有什么区别？

- CHAR是固定长度的字符串类型，定义时需要指定固定长度，存储时会在末尾补足空格。CHAR适合存储长度固定的数据，如固定长度的代码、状态等，存储空间固定，对于短字符串效率较高。

- VARCHAR是可变长度的字符串类型，定义时需要指定最大长度，实际存储时根据实际长度占用存储空间。VARCHAR适合存储长度可变的数据，如用户输入的文本、备注等，节约存储空间\.

### Q6\. VARCHAR后面代表字节还是会字符？

`VARCHAR` 后面括号里的数字代表的是字符数，而不是字节数。其中，字符的字节长度取决于所使用的字符集。

- 如果字符集是 ASCII 字符集：ASCII 字符集每个字符占用 1 个字节

- 如果字符集是 UTF \- 8 字符集，它的每个字符可能占用 1 到 4 个字节

### Q7\. MySQL的关键字in和exist

在MySQL中，`IN` 和 `EXISTS` 都是用来**处理子查询的关键词**，但它们在功能、性能和使用场景上有各自的特点和区别。

- IN关键字：用于检查左边的表达式是否存在于右边的列表或子查询的结果集中。如果存在，则`IN` 返回`TRUE`，否则返回`FALSE`。

    ```SQL
    SELECT column_name(s)
    FROM table_name
    WHERE column_name IN (SELECT column_name FROM another_table WHERE condition);
    ```

- EXISTS关键字: `EXISTS` 用于判断子查询是否至少能返回一行数据。它不关心子查询返回什么数据，只关心是否有结果。如果子查询有结果，则`EXISTS` 返回`TRUE`，否则返回`FALSE`。

    ```SQL
    SELECT column_name(s)
    FROM table_name
    WHERE EXISTS (SELECT column_name FROM another_table WHERE condition);
    ```

- 性能差异：在很多情况下，`EXISTS` 的性能优于 `IN`，特别是当子查询的表很大时。这是因为`EXISTS` 一旦找到匹配项就会立即停止查询，而`IN`可能会扫描整个子查询结果集。

- 使用场景：如果子查询结果集较小且不频繁变动，`IN` 可能更直观易懂。而当子查询涉及外部查询的每一行判断，并且子查询的效率较高时，`EXISTS` 更为合适。

- NULL值处理：`IN` 能够正确处理子查询中包含NULL值的情况，而`EXISTS` 不受子查询结果中NULL值的影响，因为它关注的是行的存在性，而不是具体值

### QXX\. DELETE、TRUNCATE 和 DROP 有什么区别？

> "DELETE 是 DML，按行删除数据，可以加 WHERE，走事务、产生 undo 和 redo，所以提交前能回滚，会逐行触发 DELETE 触发器，加的是行锁；但它删完不释放磁盘空间，MySQL 8\.0 之后即使全表删除再重启，自增计数器也不会重置。
> 
> TRUNCATE 和 DROP 都是 DDL，执行时会隐式提交，没法用 ROLLBACK 撤销。**TRUNCATE 的本质是 DROP TABLE 再 CREATE TABLE**，所以它清空全表、不能加 WHERE、重置自增、不触发 DELETE 触发器、需要 DROP 权限、还会释放磁盘空间，速度比 DELETE 快很多。
> 
> DROP 最彻底，表结构、数据、索引、约束、触发器一起删掉。
> 
> 补充一点：如果这张表正被其他表用外键引用，TRUNCATE 和 DROP 都会直接失败。"
> 
> 

- DELETE：删除表中的记录，可以带 WHERE 条件，表结构保留。对于 InnoDB，它是事务操作，在事务提交前可以回滚，会产生 undo 和 redo，也会逐行触发 DELETE 触发器。

- TRUNCATE：清空整张表，不能带 WHERE，表结构保留，通常会重建表并重置自增计数器，不会逐行触发 DELETE 触发器。

- DROP：删除整张表，表结构和数据都不再保留。





### QXX\. NULL 和空字符串有什么区别？

"NULL 和空字符串本质不同：NULL 表示值未知、缺失，是一种状态；空字符串是长度为 0 的确定值。

因为 NULL 代表未知，它和任何值比较、包括和它自己比较，结果都是 NULL，所以判断 NULL 必须用 IS NULL，不能用等号；而空字符串可以正常用 = 比较。

函数层面，COUNT 列会忽略 NULL 但会统计空字符串；CONCAT 只要遇到 NULL 整个结果就是 NULL；LENGTH \(NULL\) 是 NULL，LENGTH 空串是 0。

还有两个常考点：唯一索引里可以存多个 NULL，但**只能存一个空字符串**；排序时 NULL 被当作最小值排最前。

开发中我会尽量把字段设为 NOT NULL 并给默认值，避免 NULL 带来的三值逻辑和统计问题。"



### QXX\. IP地址如何在数据库里存储？

IPv4 地址是一个 32 位的二进制数，通常以点分十进制表示法呈现，因此有两种方式存储：

- 字符串类型的存储方式：直接将 IP 地址作为字符串存储在数据库中,比如可以用 `VARCHAR(15)`来存储

    - 优点：直观易懂，方便直接进行数据的插入、查询和显示，不需要进行额外的转换操作。

    - 缺点：占用存储空间较大，字符串比较操作的性能相对较低，不利于进行范围查询。

- 整数类型的存储方式：将 IPv4 地址转换为 32 位无符号整数进行存储

    - 优点：占用存储空间小，整数比较操作的性能较高，便于进行范围查询。

    - 缺点：需要进行额外的转换操作，不够直观，增加了开发的复杂度。

    ```SQL
    -- 创建一个表,使用INT UNSIGNED类型存储IPv4地址
    CREATE TABLE ip_records (
    id INT AUTO_INCREMENT PRIMARY KEY,
    ip_address INT UNSIGNED
    
    -- 插入数据,需要先将IP地址转换为整数
    INSERT INTO ip_records (ip_address) VALUES (INET_ATON('192.168.1.1'));
    
    -- 查询时将整数转换回IP地址
    SELECT INET_NTOA(ip_address) FROM ip_records;
    ```

### QXX\. 数据库的三大范式？

1. 第一范式（1NF）：要求数据库表的每一列都是不可分割的原子数据项。

2. 第二范式（2NF）：在1NF的基础上，非码属性必须完全依赖于候选码（在1NF基础上消除非主属性对主码的部分函数依赖）

    1. 第二范式需要确保数据库表中的每一列都和主键相关，而不能只与主键的某一部分相关

3. 第三范式（3NF）：在2NF基础上，任何非主属性不依赖于其它非主属性（在2NF基础上消除传递依赖）

    1. 第三范式需要确保数据表中的每一列数据都和主键直接相关，而不能间接相关。



### QXX\. 如何用 MySQL 实现一个可重入的锁？

首先，创建一个保存锁记录的表：

```SQL
CREATE TABLE `lock_table' (
'id` INT AUTO_INCREMENT PRIMARY KEY,
// 该字段用于存储锁的名称,作为锁的唯一标识符。
`lock_name` VARCHAR(255) NOT NULL,
// holder_thread 该字段存储当前持有锁的线程的名称,用于标识哪个线程持有该锁。
`holder_thread` VARCHAR(255),
// reentry_count 该字段存储锁的重入次数,用于实现锁的可重入性
`reentry_count` INT DEFAULT 0
);
```

**加锁的实现逻辑**

1. 开启事务

2. 执行SQL, 查询是否存在该记录:

    ```SQL
    SQL SELECT holder_thread, reentry_count FROM lock_table WHERE lock_name = ? FOR UPDATE,
    ```

    - 如果记录不存在,则直接加锁, 执行

        ```SQL
        INSERT INTO lock_table(lock_name,holder_thread, reentry_count) VALUES (?,?, 1)
        ```

    - 如果记录存在, 且持有者是同一个线程,则可冲入,增加重入次数,执行

        ```SQL
        UPDATE lock_table SET reentry_count = reentry_count + 1 WHERE lock_name =?
        ```

3. 提交事务

**解锁的逻辑：**

1. 开启事务

2. 执行SQL, 查询是否存在该记录：

    ```SQL
    SELECT holder_thread, reentry_count FROM lock_table WHERE lock_name = ? FOR UPDATE
    ```

    - 如果记录存在，且持有者是同一个线程，且可重入数大于 1 ，则减少重入次数 

        ```SQL
        UPDATE lock_table SET reentry_count = reentry_count - 1 WHERE lock_name = ?
        ```

    - 如果记录存在，且持有者是同一个线程，且可重入数小于等于 0 ，则完全释放锁

        ```SQL
        DELETE FROM lock_table WHERE lock_name = ?
        ```

3. 提交事务

### Q1\. MySQL 索引优化？

关于 MySQL 索引优化，我从核心本质、索引设计原则、常见失效场景、SQL 编写优化、执行计划调优和实际开发应用六个方面来回答：

首先，MySQL 索引优化的核心本质是**通过合理设计和使用索引，减少磁盘 IO 次数，避免全表扫描****，将查询时间复杂度从 O \(n\) 降低到 O \(log n\)，同时平衡查询性能和写入性能**。索引本质是 B \+ 树数据结构，优化的核心就是让 SQL 尽可能命中最优的索引，避免索引失效。

接下来是索引设计的七大核心原则，这是优化的基础。

第一，**主键优先使用自增整数**，有序插入可以避免 B \+ 树频繁的页分裂和页合并，提升写入性能。

第二，优先给经常出现在`where、order by、group by、join`子句中的字段建立索引。

第三，选择**区分度高**的字段建索引，像性别、状态这种只有少数几个值的低区分度字段，不建议单独建索引。

第四，联合索引要遵循**等值条件放前面，范围条件放最后**的原则。

第五，控制索引数量，索引不是越多越好，过多的索引会严重降低`insert、update、delete`的写入性能。

第六，长字符串字段使用**前缀索引**，只对前几位建立索引，节省索引空间。

第七，避免创建冗余索引，能复用已有联合索引的就不新建单独索引。

然后是面试必考的八大索引失效场景，开发中一定要避开。

第一，违背联合索引的**最左前缀原则**，跳过首列或者中间断列会导致索引失效。

第二，索引列上做**运算、函数调用、隐式类型转换**，比如给索引字段加减乘除、使用日期函数、字符串数字不加引号。

第三，模糊查询使用**左模糊****`%xx`****或者全模糊****`%xx%`**，只有右模糊`xx%`能走索引。

第四，使用`or`连接的条件中，只要有一个字段没有索引，整体索引就会失效。

第五，联合索引中，**范围条件后面的列会失效**。

第六，使用`!=、<>、is not null`这些反匹配条件。

第七，使用`not in、not exists`大概率会导致索引失效。

第八，MySQL 优化器判断**全表扫描比走索引更快**时，会主动放弃索引，比如小表查询或者索引区分度极低的情况。

在编写业务代码的过程中，我认为：SQL 编写层面的优化技巧。第一，杜绝`select *`，只查询需要的字段，尽量让查询走**覆盖索引**，避免回表操作，这是性能提升最大的优化手段。第二，联合索引中，范围条件一定要放在最后。第三，能用`in`就尽量不用`or`。第四，多表关联查询时，**关联字段必须建立索引**，并且尽量让小表驱动大表。第五，大分页查询使用**延迟关联或者主键分页**优化，避免`limit 10000,10`这种深分页导致的全表扫描。第六，排序和分组尽量利用索引的天然有序性，避免出现`Using filesort`文件排序和`Using temporary`临时表。

然后是执行计划调优，这是定位索引问题的核心工具。使用`explain`关键字分析 SQL 执行计划，重点看三个字段：第一是`type`，表示访问类型，从优到劣依次是`system > const > eq_ref > ref > range > index > all`，坚决避免`all`全表扫描，至少要达到`range`级别。第二是`key`，表示实际使用的索引，如果为 null 说明没有走索引。第三是`Extra`，如果出现`Using filesort`或者`Using temporary`，说明需要立即优化 SQL 和索引。

这里我想重点澄清两个常见误区：第一，不是索引越多越好，每增加一个索引，写入时都需要维护对应的 B \+ 树，会显著降低写入性能；第二，数据量很小的表不需要建索引，全表扫描比走索引更快。

最后是实际开发中的应用。在项目中，我会在表设计阶段就根据业务查询场景提前设计好索引；开启慢查询日志，把阈值设置为 1 秒，定期分析慢查询日志优化 SQL；定期清理无用和冗余的索引；对于大表，会避免频繁的批量更新，防止索引重构；同时会根据业务需求，在查询性能和写入性能之间做合理的平衡。

### Q2\. MySQL中的索引是怎么实现的 ？

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZWYyYTUxZWM5M2Q1ZDFhYWUxMWQyZDU4ZjQ4NGVlZGZfYTI1YTg2NTZjZmExNDBiYzhlMmE5MzZmMjIwZjU2YjBfSUQ6NzY0NDYxNDgzODg1NzA0Mjg4NF8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

MySQL 索引的核心是用 **B\+ 树** 实现，根据存储引擎分为聚簇和非聚簇两种：

第一，为什么用 B\+ 树？因为它是多路平衡矮胖树，非叶子节点不存数据，能大幅减少磁盘 IO，且每个节点里的数据是按主键顺序存放的；叶子节点是有序链表，天然支持范围查询、排序，查询效率稳定。

> **优化补充**：InnoDB 中一个页（Page）默认 **16KB**，非叶子节点存储键值和子节点指针，一个页大约能存 **1000 个左右的键指针对**；叶子节点存完整行数据，一页大约存 **15\~100 行**（取决于行大小）。一棵高度为 3 的 B\+ 树，可以存储约 1000 × 1000 × 100 = **1 亿行数据**，只需要 **3 次磁盘 IO**（根页常驻内存实际只需 2 次）。这就是 B\+ 树在大数据量下仍然高效的根本原因。
> 
> 

第二，**InnoDB 是聚簇索引**（默认）：主键索引的叶子节点直接存整行数据，表数据和索引绑在一起；二级索引叶子只存索引键和主键，查询需要回表查主键索引。InnoDB 必须有主键，推荐自增主键避免页分裂。

第三，**MyISAM 是非聚簇索引**：索引和数据完全分离，所有索引叶子节点存数据的物理地址，不用回表；但它不支持事务和行锁，现在已经淘汰。

### Q3\. MySQL为什么用B\+树结构？和其他结构比的优点？

关于 MySQL 为什么用 B \+ 树结构，我从核心本质、其他数据结构的局限性、B \+ 树的五大核心优点、关键设计细节、常见误区和实际开发应用六个方面来回答：

首先，MySQL 选择 B \+ 树做索引的核心本质是**适配数据库的磁盘 IO 瓶颈**。数据库数据量远大于内存，查询必须读写磁盘，而磁盘 IO 的速度比内存慢几万倍，所以索引设计的第一目标就是**尽可能减少磁盘 IO 次数**。B \+ 树是经过大量验证，在减少 IO 和支持业务查询场景之间综合性能最优的数据结构，完美解决了数据库索引的核心需求。

接下来是其他数据结构**为什么不适合做数据库索引，**这也是面试常考的对比点。

第一种是**二叉查找树**，数据有序时会退化成链表，树高无限大，查询需要多次 IO，效率极差。

第二种是**红黑树**，虽然是平衡二叉树，但每个节点只能存 1 个键，百万级数据树高就会达到 20 层以上，每一层都要做一次磁盘 IO，IO 次数爆炸，只适合内存操作。

第三种是**B 树**，也就是 B \+ 树的前身，它的所有节点都存数据，导致单个节点能存的键数量极少，树高更高，而且范围查询需要回溯父节点，效率很低。B树的叶子节点没有链表连接。

> - **B 树**非叶子节点也存数据，同页能容纳的键更少，树更高，IO 更多
> 
> - **B 树**范围查询需要中序遍历整棵树，穿插访问不同层节点，IO 不连续
> 
> 

第四种是**哈希表**，**仅支持等值查询**，完全不支持范围查询、排序、模糊查询和分组，而业务中 90% 以上的 SQL 都需要这些功能，所以不能作为主流索引。

> **优化表述**：红黑树是二叉树，存储 100 万条数据树高约为 log⁡2\(106\)≈20log2\(106\)≈20 层，存储 1 亿条约需 27 层，每层一次磁盘 IO，查询一条数据需要 20\~27 次 IO，而 B\+ 树只需 3 次。这个对比数字在面试中非常有说服力。
> 
> 

然后是 B \+ 树的五大核心优点，这也是它被选中的根本原因。第一，**多路平衡矮胖树，磁盘 IO 极少**，一个节点可以存储成百上千个索引键，百万级数据树高只有 3\~4 层，查询只需要 3\~4 次磁盘 IO，速度极快。第二，**非叶子节点不存数据，只存索引键**，节点空间全部用来存索引键，能容纳更多的键，进一步降低树高，减少 IO 次数。第三，**叶子节点用双向有序链表连接**，天然支持范围查询、排序、模糊查询和分页，不需要回溯父节点，效率极高。第四，**查询效率绝对稳定**，所有数据都存在叶子节点，任何查询都必须走到叶子节点，性能无波动。第五，**全表扫描效率更高**，只需要遍历叶子节点的链表即可，不用遍历整棵树，IO 开销远小于 B 树。第六，自平衡，B\+树在插入、删除和更新操作后会**自动重新平衡**，确保树的高度保持相对稳定，从而保持良好的搜索性能。

接下来是两个关键的设计细节。第一，为什么非叶子节点不存数据？因为磁盘 IO 是以页为单位的，InnoDB 默认一页是 16KB，如果非叶子节点存数据，一页只能存几个键，树高会大幅增加；而只存键的话，一页可以存上千个键，树高直接降到 3 层以内。第二，为什么叶子节点要连成双向链表？因为单向链表只能从前往后遍历，双向链表可以支持正序和倒序的范围查询，比如`order by asc`和`order by desc`，更加灵活。

~~这里我想重点澄清两个常见误区。第一，很多人以为哈希表比 B \+ 树快，其实只有纯等值查询场景哈希表更快，只要涉及范围、排序、分页，B \+ 树的性能就远超哈希表。第二，B 树不是比 B \+ 树差，而是 B 树更适合文件系统，B \+ 树更适合数据库索引，因为数据库更看重范围查询和查询稳定性。~~

最后是实际开发中的应用。基于 B \+ 树的特性，我们在设计索引时，主键优先使用自增整数，有序插入可以避免 B \+ 树频繁的页分裂和页合并；联合索引要遵循最左前缀原则，利用 B \+ 树的有序性；尽量使用覆盖索引，避免回表操作；同时要避免在索引列上做运算，破坏 B \+ 树的有序性导致索引失效。

### Q4\. 索引失效有哪些？

面试官您好，MySQL 索引失效主要有**9 个高频场景**，核心是违背索引规则或优化器主动放弃索引：

第一，**违背最左前缀原则**，联合索引必须从第一个字段连续匹配，跳过或断列就失效。

第二，**索引列做运算、函数、隐式类型转换**，比如给索引字段加减、用日期函数、字符串数字不加引号。

第三，**模糊查询左模糊或全模糊**，只有右模糊能走索引。

第四，**OR 连接的字段有一个没索引**，整体索引失效。

第五，**联合索引范围条件后列失效**，范围查询后的索引列无法匹配。

第六，使用 \!=、\<\>、is not null 会导致失效。

第七，**not in、not exists** 反查询大概率失效。

第八，**数据量太小、索引区分度太低**，优化器主动放弃索引。

第九，**排序分组不遵循索引顺序**，触发文件排序，索引失效。

### Q5\. 什么是索引？

> 帮助存储引擎快速获取数据的一种数据结构
> 
> 

- 如果查询的时候，没有用到索引就会全表扫描，这时候查询的时间复杂度是 O\(N\)

- 如果用到了索引，那么查询的时候，可以基于二分查找算法，通过索引快速定位到目标数据，MySQL 索引的数据结构一般是 B\+ 树，其搜索复杂度为O\(log\(d\)N\)，其中 d 表示节点允许的最大子节点个数

### Q6\. 索引的分类

MySQL可以按照四个角度来分类索引。

- 按数据结构分类：B\+tree索引、Hash索引、Full\-text索引

- 按物理存储分类：聚簇索引（主键索引）、二级索引

- 按字段特性分类：主键索引、唯一索引【唯一索引建立在 UNIQUE 字段上的索引，一张表可以有多个唯一索引，索引列的值必须唯一，但是允许有空值。】、普通索引、前缀索引

- 按字段个数分类：单列索引、联合索引【将多个字段组合成一个索引，该索引就被称为联合索引。】

在创建表时，InnoDB 存储引擎会根据不同的场景选择不同的列作为索引：

- 如果有主键，默认会使用主键作为聚簇索引的索引键（key）；

- 如果没有主键，就选择第一个不包含 NULL 值的唯一列作为聚簇索引的索引键（key）；

- 在上面两个都没有的情况下，InnoDB将自动生成一个隐式自增id字段作为聚簇索引的索引键；

其他索引都属于辅助索引，也称为二级索引。创建的主键索引和二级索引默认使用的是B\+Tree索引

**按物理存储分类:**

- 主键索引的 B\+Tree 的叶子节点存放的是实际数据，所有完整的用户记录都存放在主键索引的 B\+Tree 的叶子节点里；

- 二级索引的 B\+Tree 的叶子节点存放的是主键值，而不是实际数据。

**什么是覆盖索引：在查询时使用了二级索引，如果查询的数据能在二级索引里查询的到，那么就不需要回表，这个过程就是****覆盖索引****。**

所以，在查询时使用了二级索引，如果查询的数据能在二级索引里查询的到，那么就不需要回表，这个过程就是覆盖索引。如果查询的数据不在二级索引里，就会先检索二级索引，找到对应的叶子节点，获取到主键值后，然后再检索主键索引，就能查询到数据了，这个过程就是回表。

什么是**回表**：如果查询的数据不在二级索引里，就会先检索二级索引，找到对应的叶子节点，获取到主键值后，然后再检索主键索引，就能查询到数据了，这个过程就是回表

### Q7\. 如果聚簇索引的数据更新，它的存储要不要变化？

- 如果更新的数据是非索引数据，也就是普通的用户记录，那么存储结构是不会发生变化

- 如果更新的数据是索引数据，那么存储结构是有变化的，因为要维护 b\+树的有序性

### Q8\. 什么字段适合当做主键？

- 字段具有唯一性，且不能为空的特性

- 字段最好的是有递增的趋势的，如果字段的值是随机无序的，可能会引发页分裂的问题，造成性能影响

- 不建议用业务数据作为主键，比如会员卡号、订单号、学生号之类的，因为我们无法预测未来会不会因为业务需要，而出现业务字段重复或者重用的情况。

- 通常情况下会用自增字段来做主键，对于单机系统来说是没问题的。分布式环境下，要考虑分布式 id 的方案了

### Q9\. 如果一个列既是单列索引，又是联合索引，单独查它的话先走哪个？

mysql 优化器会分析每个索引的查询成本，然后选择成本最低的方案来执行 sql。

例如：如果单列索引是 a，联合索引是（a ，b），那么针对下面这个查询：

```SQL
select a, b from table where a = ? and b = ?
```

优化器会选择联合索引，因为查询成本更低，查询也不需要回表，直接索引覆盖了。

**索引下推**

- 可以在联合索引遍历过程中，对联合索引中包含的字段先做判断，直接过滤掉不满足条件的记录，减少回表次数

> ```SQL
> SELECT * FROM users
> WHERE name LIKE '张%' AND age = 20;
> ```
> 
> 

> - 没有索引下推时，先根据 name 找到候选记录，再逐条回表读取整行，之后判断 age 是否等于 20。
> 
> - 有索引下推时，在二级索引里就判断 age 是否等于 20，不满足的记录直接跳过，只有满足的记录才回表。

## 事务篇

### Q1\. 事务的特性是什么？如何实现的？

MySQL 事务有四大特性也就是 ACID，分别是原子性、一致性、隔离性、持久性，我分别说下含义和底层怎么实现：

第一，**原子性**：事务是最小执行单元，不可拆分，要么全部成功，要么全部回滚。底层是靠 undo log 回滚日志实现的，修改数据前先记录原始数据，一旦出错就通过 undo log 回滚恢复。

第二，**一致性**：事务执行前后，数据库约束和业务数据状态保持一致，比如转账金额总额不变。它不是靠某一个单独日志实现的，是由原子性、隔离性、持久性，再加上数据库主键、外键约束和业务代码共同保证的。

第三，**隔离性**：多个并发事务之间互相隔离，避免脏读、不可重复读、幻读。底层靠**行锁加 MVCC** 实现，写操作加行锁防止并发修改，读操作通过 MVCC 读取**数据快照**，做到读写互不阻塞，~~同时支撑四种隔离级别~~。

第四，**持久性**：事务一旦提交，数据永久生效，就算服务器宕机也不会丢失。底层依靠 redo log 重做日志，采用 WAL 预写机制，先写日志再刷磁盘，宕机重启自动回放 redo log 恢复数据。

另外 InnoDB 默认隔离级别是**可重复读**，能解决脏读和不可重复读，但存在幻读；串行化能解决所有问题，但是并发性能最低。

### Q2\. mysql的是怎么解决并发问题的？

MySQL InnoDB 解决事务并发问题，主要靠 **MVCC、行级锁、临键锁** 三套机制配合：

首先，并发主要会出现脏读、不可重复读、幻读三个问题。

第一，用 **MVCC 多版本并发控制** 解决**读写冲突**。底层依靠 undo log 版本链和 ReadView 读视图，普通 select 走快照读，读取数据历史版本，**读不加锁、读写互不阻塞**，解决了脏读和不可重复读，也是数据库高并发的核心。

> **优化补充**：MVCC 依赖三个核心组件：① 每行数据隐藏字段 `trx_id`（最后修改该行的事务 ID）和 `roll_pointer`（指向 undo log 版本链）；② **undo log 版本链**——同一行数据的所有历史版本通过 roll\_pointer 串联；③ **Read View**——事务开始时生成，记录当前活跃事务列表（未提交的事务 ID 集合），读操作用它判断版本链上哪个版本对当前事务可见，找到满足条件的最新版本返回。
> 
> 

> **优化补充**：MySQL 的读分两种：**快照读**（Snapshot Read）—— 普通 `SELECT`，通过 MVCC 读历史版本，无锁；**当前读**（Current Read）—— `SELECT FOR UPDATE`、`SELECT LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT`，读取当前最新数据并加锁。临键锁只在当前读时生效，这也解释了为什么在 RR 级别下混用快照读和当前读的极端场景仍可能出现幻读。
> 
> 

第二，用 **行级锁加意向锁** 解决**写写冲突**。多个事务同时修改同一行时，加排他行锁，让更新串行执行，防止数据覆盖；而且 InnoDB 是索引行锁，粒度很小，并发性能高，如果不走索引会退化成表锁。

> **优化补充**：意向锁是表级锁，分意向共享锁（IS）和意向排他锁（IX）。事务在给某行加行锁前，会先给整张表加对应的意向锁。意向锁的作用是让表级锁操作（如 `ALTER TABLE`、`LOCK TABLE`）能**快速判断**表内是否有行锁存在，而不必逐行检查，大大提升了锁冲突检测的效率。意向锁之间互不阻塞。
> 
> 

第三，用 **间隙锁和临键锁** 专门解决**幻读**。在默认的可重复读隔离级别下，InnoDB 采用临键锁，包含行锁和间隙锁，锁住索引记录和中间的空白区间，禁止其他事务插入新数据，从根源解决幻读。

最后配合四种事务隔离级别，通过 MVCC 和锁的组合，逐级解决并发异常，平衡隔离性和并发性能。

### Q3\. 介绍MVCC实现原理

关于 MySQL MVCC 实现原理，我从核心本质、三大底层组件、核心执行流程、隔离级别实现差异、常见误区和实际开发应用六个方面来回答：

首先，MVCC 全称是**多版本并发控制**，是 InnoDB 存储引擎专属的并发控制机制。它的**核心目的**是实现**读不加锁、读写互不阻塞**，在保证事务隔离性的同时，大幅提升数据库的高并发性能。MVCC 只在**读已提交 RC**和**可重复读 RR**两种隔离级别下生效，而且只针对普通的`select`快照读；像`update、delete、select ... for update`这种属于当前读，会走行锁，不使用 MVCC。

接下来是 MVCC 的三大底层核心组件，缺一不可。

第一种是**行隐藏字段**，InnoDB 每一行数据都会自动添加三个隐藏列：一是`DB_TRX_ID`，记录最近修改这条数据的事务 ID；二是`DB_ROLL_PTR`回滚指针，指向 undo log 中这条数据的上一个历史版本；三是`DB_ROW_ID`，当表没有显式定义主键时，InnoDB 自动生成的隐藏主键。

第二种是**undo log 版本链**，每次事务修改数据时，不会直接覆盖旧数据，而是先把修改前的原始数据保存到 undo log 中，再更新最新数据；然后通过回滚指针，把一条数据的所有历史版本串成一条单向链表，这就是多版本的来源。

第三种是**ReadView 读视图**，是事务查询时生成的一个一致性快照，里面保存四个关键信息：当前系统中正在活跃未提交的事务 ID 集合、活跃事务的最小 ID、下一个待分配的事务 ID、以及当前事务自身的 ID，它的核心作用是提供数据版本的可见性判断规则。

然后是 MVCC 的核心执行流程。当我们执行一条普通的`select`快照读时，首先事务会生成或复用 ReadView 视图；然后读取该行数据的最新版本，拿到它的`DB_TRX_ID`；接着按照 ReadView 的可见性规则进行判断：如果版本事务 ID **小于**活跃事务最小 ID，说明早已提交，可见；如果在活跃事务集合中，说明还未提交，不可见；如果大于等于下一个待分配的事务 ID，说明是未来事务，不可见；如果等于当前事务 ID，说明是自己修改的数据，可见。如果当前版本不可见，就顺着回滚指针遍历 undo log 版本链，往前找历史版本，直到找到第一条对当前事务可见的版本，返回给客户端。

接下来是隔离级别的实现差异，这也是面试的核心考点。**RC 读已提交**和**RR 可重复读**这两种隔离级别，本质上就是通过 ReadView 的生成时机不同来实现的。InnoDB 默认的**RR 可重复读**，整个事务只在第一次查询时生成一次 ReadView，后续所有查询都复用这同一个视图，所以同一事务多次查询看到的是同一个数据快照，结果完全一致，解决了不可重复读问题。而**RC 读已提交**，每执行一次查询都会重新生成一个全新的 ReadView，能实时看到其他事务已经提交的最新数据，但也正因为视图每次都刷新，所以会产生不可重复读问题。

这里我想重点澄清两个非常常见的误区：第一，很多人以为 MVCC 能解决幻读，其实不是，MVCC 只能解决脏读和不可重复读，**幻读是靠间隙锁和临键锁来解决的**；第二，undo log 不是事务提交后就立即删除的，而是由后台的 purge 线程异步清理，因为可能还有其他事务正在引用这些历史版本。

最后是实际开发中的应用。在项目中，我会尽量使用普通的`select`快照读，利用 MVCC 的读不加锁特性提升并发性能；只有在需要保证数据强一致性的场景，比如扣库存、转账，才会使用加锁的当前读；同时会尽量缩短事务执行时间，避免长事务持有旧版本引用，导致 undo log 无法清理，占用过多磁盘空间。

### Q4\. 并行事务会引发什么问题？

**在同时处理多个事务的时候，就可能出现脏读（dirty read）、不可重复读（non\-repeatable read）、幻读（phantom read）的问题**。

**脏读: **如果一个事务「读到」了另一个「未提交事务修改过的数据」，就意味着发生了「脏读」现象**。**

**不可重复读**: 在一个事务内多次读取同一个数据，如果出现前后两次读到的数据不一样的情况，就意味着发生了「不可重复读」现象。

**幻读**: 在一个事务内多次查询某个符合查询条件的「记录数量」，如果出现前后两次查询到的记录数量不一样的情况，就意味着发生了「幻读」现象。

### Q6\. 快照读和当前读有什么区别？

> - **快照读 = "看照片"**：读取数据的**历史版本**（拍一张快照），通过 MVCC 实现，**不加锁**，读写互不阻塞；
> 
> - **当前读 = "看真人 \+ 抓住他"**：读取数据的**最新版本**，并且**加锁**，防止别人在你读取后修改。
> 
> 

"MySQL 的读分快照读和当前读。快照读就是普通 SELECT，读的是数据的历史版本，通过 MVCC 的 ReadView 加 undo 版本链实现，不加锁，读写不阻塞；RC 下每次查询都生成新的 ReadView，所以能读到最新已提交数据，RR 下第一次查询生成后复用，所以能可重复读。

当前读读的是最新版本并且加锁，包括 SELECT FOR UPDATE、LOCK IN SHARE MODE，以及 INSERT、UPDATE、DELETE，因为要修改数据必须基于最新版本。

两者解决幻读的方式也不同：快照读靠 MVCC 让幻影行不可见，当前读靠临键锁锁住间隙，让别的事务插不进来。

实际开发中普通查询用快照读保证并发，而扣库存、查后更新这类需要强一致的场景，我会用 FOR UPDATE 当前读。"



### Q7\. 如何用 MySQL 扣减库存，避免超卖？

> " 用 MySQL 防超卖，核心是一条带条件的更新：`UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0`。

> 它比 ' 先 SELECT 查库存再 UPDATE' 可靠，后者在并发下两个事务都可能读到旧值导致超卖。

## 锁

### Q1\. 讲一下mysql里有哪些锁？

我从整体分类体系、按锁粒度划分、按读写兼容性划分、按锁算法划分、辅助意向锁和实际开发应用六个方面来回答：

首先，MySQL 的锁主要是指 InnoDB 存储引擎的锁体系，MyISAM 只有表级锁，并发性能极差，现在基本被淘汰。InnoDB 设计了一套完整的多粒度锁机制，用来控制事务并发、保证隔离级别，解决脏读、不可重复读和幻读三大并发问题。

接下来是**按锁的粒度划分**，分为表级锁和行级锁。第一种是**表级锁**，直接锁住整张数据表，锁粒度最大、并发性能最差。分为表读锁和表写锁，一旦加锁会阻塞整张表的所有读写操作。InnoDB 一般不会主动使用表锁，只有三种情况会触发：手动执行 lock table 语句、SQL 语句没走索引导致行锁退化、还有部分 DDL 语句。第二种是**行级锁**，这是 InnoDB 的核心优势，只锁住命中索引的单行记录，锁粒度极小、并发性能极高。这里有一个非常重要的前提：**行锁必须基于索引实现。**如果 SQL 没有走索引，会导致全表扫描，InnoDB 会对扫描到的每一行都加记录锁，在 RR 隔离级别下还会加间隙锁。

> 澄清一个常见误区：**InnoDB 并没有锁升级机制，无索引时不是 "行锁退化成表锁"，而是对全表每一行都加了行锁和间隙锁**，锁的本质仍然是行锁，但实际效果等同于锁住了整张表，会导致并发性能暴跌。
> 
> 



然后是**按读写兼容性划分**，分为共享锁 S 和排他锁 X。第一种是**共享锁 S**，也叫读锁，多个事务可以同时加共享锁，读读兼容，互相不阻塞。第二种是**排他锁 X**，也叫写锁，是独占锁，写写互斥、读写也互斥，只要一个事务加了排他锁，其他事务既不能读也不能改这行数据。语法上，select \.\.\. lock in share mode 手动加共享锁，select \.\.\. for update 加排他锁；而普通的 select 快照读走 MVCC 多版本并发控制，**不加任何锁**，实现读写互不阻塞。

接下来是**按锁算法划分**，这也是面试的核心考点，在 InnoDB 默认的 RR 可重复读隔离级别下，有三种行锁算法。第一种是**记录锁**，只锁住索引上已经存在的真实记录，只锁行，不锁空隙。第二种是**间隙锁**，专门锁住两条索引记录中间的空白间隙，不锁已有数据，只禁止其他事务往这个间隙插入新数据，它只存在于 RR 隔离级别，主要用来防范幻读的插入操作。第三种是**临键锁**，是 InnoDB 默认的行锁算法，**等于记录锁加间隙锁**，采用左开右闭区间，既锁住已有的索引记录，又锁住前后的空白间隙，从根源上彻底解决了幻读问题。

> **间隙锁之间并不冲突，多个事务可以同时持有同一个间隙的间隙锁**。
> 
> 

然后是辅助意向锁，分为意向共享锁 IS 和意向排他锁 IX。它不是用来锁数据的，只是一个表级标记。事务要加行锁之前，会先在表上加对应的意向锁；作用是快速判断整张表有没有其他行锁，不用遍历每一行，大大提升了加锁检测效率。意向锁之间互相兼容，但表锁和意向锁互相互斥。

这里我想重点讲两个开发中最容易踩的坑：第一，行锁强依赖索引，一旦用了函数、隐式类型转换、左模糊查询导致索引失效，行锁就会退化成表锁，直接拖垮整个系统的并发性能；第二，长事务会导致锁长时间不释放，引发大量锁等待甚至死锁，开发中一定要尽量缩短事务执行时间。

最后是实际开发中的应用注意事项。在项目中，我会尽量让 SQL 走索引，避免行锁退化成表锁；合理控制事务长度，避免长事务占用锁资源；对于高并发的扣库存、秒杀场景，会优先使用乐观锁，通过版本号做冲突校验，减少数据库锁的竞争；同时会根据业务需求选择合适的隔离级别，平衡隔离性和并发性能。

以上就是我对 MySQL 锁机制的理解，如果您想了解更多关于死锁的产生原因和解决方法，我可以再详细讲一下。

### Q2\. 数据库的表锁和行锁有什么作用？

**表锁的作用：**

- 整体控制：表锁可以用来控制整个表的并发访问，当一个事务获取了表锁时，其他事务无法对该表进行任何读写操作，从而确保数据的完整性和一致性。

- 粒度大：表锁的粒度比较大，在锁定表的情况下，可能会影响到整个表的其他操作，可能会引起锁竞争和性能问题。

- 适用于大批量操作：表锁适合于需要大批量操作表中数据的场景，例如表的重建、大量数据的加载等

**行锁的作用**：

- 细粒度控制：行锁可以精确控制对表中某行数据的访问，使得其他事务可以同时访问表中的其他行数据，在并发量大的系统中能够提高并发性能。

- 减少锁冲突：行锁不会像表锁那样造成整个表的锁冲突，减少了锁竞争的可能性，提高了并发访问的效率。

- 适用于频繁单行操作：行锁适合于需要频繁对表中单独行进行操作的场景，例如订单系统中的订单修改、删除等操作。

### Q3\. MySQL两个线程的update语句同时处理一条数据，会不会有阻塞？

如果是两个事务同时更新了 id = 1，比如 update \.\.\. where id = 1，那么是会阻塞的。因为 InnoDB 存储引擎实现了行级锁。

当A事务对 id =1 这行记录进行更新时，会对主键 id 为 1 的记录加X类型的记录锁，这样第二事务对 id = 1 进行更新时，发现已经有记录锁了，就会陷入阻塞状态



### Q4\. 如果2个范围不是主键或索引？还会阻塞吗？

如果2个范围查询的字段不是索引的话，那就代表 update 没有用到索引，这时候触发了全表扫描，全部索引都会加行级锁，这时候第二条 update 执行的时候，就会阻塞了。

因为如果 update 没有用到索引，在扫描过程中会对索引加锁，所以全表扫描的场景下，所有记录都会被加锁，也就是这条 update 语句产生了 4 个记录锁和 5 个间隙锁，相当于锁住了全表\.

## 日志

### Q1\. 日志文件是分成了哪几种？

关于 MySQL 日志文件分类，我从整体层级划分、InnoDB 引擎层核心日志、MySQL Server 层通用日志、关键日志核心区别和实际开发应用五个方面来回答：

首先，MySQL 日志整体分为两大层级，分别是**InnoDB 存储引擎层专属日志**和**MySQL Server 层通用日志**，总共包含六种核心日志：undo log、redo log、binlog、错误日志、慢查询日志和通用查询日志。引擎层日志主要服务于事务特性、崩溃恢复和 MVCC 多版本并发控制；Server 层日志是所有存储引擎通用的，主要服务于主从复制、数据恢复、故障排查和 SQL 性能调优。

接下来是 InnoDB 引擎层的两种专属日志，这也是事务 ACID 特性的核心支撑。第一种是**undo log 回滚日志**，它主要有两个作用：一是保证事务的原子性，当事务执行失败或者手动回滚时，通过 undo log 恢复数据到修改前的状态；二是支撑 MVCC 多版本并发控制，保存数据的历史版本，形成版本链，让普通快照读可以不加锁，实现读写互不阻塞。第二种是**redo log 重做日志**，核心作用是保证事务的持久性和崩溃恢复。InnoDB 采用 WAL 预写日志机制，先写日志再刷磁盘数据页，事务提交只要 redo log 落盘就算永久生效；哪怕数据库突然宕机，重启后自动回放 redo log，就能把已提交事务的数据恢复回来，不会丢失。

然后是 MySQL Server 层的四种通用日志，所有存储引擎都可以使用。第一种是**binlog 二进制日志**，记录所有的 DDL 和 DML 语句，它有两个核心作用：一是主从复制，主库把 binlog 同步给从库，从库回放实现数据同步；二是数据备份与恢复，可以基于时间点或者位置点恢复误操作的数据，有 statement、row、mixed 三种格式，现在生产环境一般用 row 格式。第二种是**错误日志**，记录 MySQL 启动、关闭、异常崩溃、配置错误、运行时报错等所有异常信息，数据库无法启动或者莫名宕机时，第一时间看错误日志排查原因。第三种是**慢查询日志**，专门用于 SQL 性能调优，记录执行时间超过指定阈值的 SQL 语句，我们平时优化索引、优化 SQL 语句，都是通过慢查询日志定位问题。第四种是**通用查询日志**，记录客户端执行的所有 SQL 语句，默认是关闭的，因为性能开销极大，日志量会暴涨，只在临时调试追踪 SQL 时才短暂开启，生产环境绝对不能打开。

这里我想重点讲一下两个最容易混淆的核心日志的区别，也就是 redo log 和 binlog。第一，归属不同：redo log 是 InnoDB 引擎独有的，binlog 是 Server 层通用的；第二，日志类型不同：redo log 是物理日志，记录数据页的修改内容；binlog 是逻辑日志，记录 SQL 语句或者行的变更；第三，写入方式不同：redo log 是循环顺序写，大小固定；binlog 是追加写，写满一个文件再写下一个；第四，作用不同：redo log 用于崩溃恢复，保证事务持久性；binlog 用于主从复制和数据恢复。为了保证这两份日志的数据一致性，InnoDB 事务采用了两阶段提交机制，先写 redo log 准备状态，再写 binlog，最后提交 redo log，避免主从数据不一致。

最后是实际开发中的应用注意事项。在项目中，我会默认开启错误日志和慢查询日志，把慢查询阈值设置为 1 秒，定期分析慢查询日志优化 SQL；通用查询日志生产环境绝对关闭，避免性能问题；binlog 一定要开启，不仅用于主从复制，也是数据误删后恢复的最后一道防线；同时会定期清理过期的 binlog 文件，避免磁盘空间被占满。

### Q2\. 讲一下binlog

关于 MySQL 的 binlog，我从核心本质、三大核心作用、三种日志格式对比、写入与刷盘机制、主从复制原理、常见应用场景和最佳实践七个方面来回答：

首先，binlog 的核心本质是MySQL Server 层生成的二进制日志文件，它记录了所有对数据库数据进行修改的 SQL 语句（DDL、DML、DCL），但不记录查询语句（SELECT、SHOW）。binlog 是 MySQL 实现高可用、数据恢复和数据同步的核心基础，也是所有 MySQL 中间件（Canal、Debezium）的底层依赖。

接下来是 binlog 的三大核心作用，这也是它存在的意义：

1. 数据恢复：当发生误删数据、删库等事故时，可以通过 binlog 进行时间点恢复，将数据库恢复到事故发生前的任意时刻

2. 主从复制：MySQL 主从架构的核心就是基于 binlog，主库将 binlog 发送给从库，从库重放 binlog 实现数据同步

3. 数据审计：通过分析 binlog，可以追踪所有对数据库的修改操作，实现数据变更审计和安全合规

然后是面试必考的三种 binlog 日志格式对比，这也是开发中最容易踩坑的地方：

这里我想重点讲一下 ROW 格式的两个变种：`binlog_row_image=FULL`记录整行的前后值，`binlog_row_image=MINIMAL`只记录变化的列，后者可以大幅减少日志体积，是生产环境的推荐配置。

接下来是 **binlog 的写入与刷盘机制**，这关系到数据的安全性和性能：

1. 当执行修改操作时，MySQL 会先将 binlog 写入内存中的 binlog buffer

2. 当事务提交时，会将 binlog buffer 中的内容写入到操作系统的页缓存（Page Cache）

3. 然后根据`sync_binlog`参数的值决定何时刷盘： 

    - `sync_binlog=0`：由操作系统决定何时刷盘，性能最好，但崩溃时可能丢失数据

    - `sync_binlog=1`：每次事务提交都强制刷盘，数据最安全，但性能最差

    - `sync_binlog=N`：每 N 个事务提交后刷盘，是性能和安全的折中

生产环境中，对于核心业务，建议设置`sync_binlog=1`，保证数据不丢失；对于非核心业务，可以设置为 100 或 1000，提升性能。

然后是**基于 binlog 的主从复制原理**，这也是面试的核心考点。MySQL 主从复制是**异步**的，分为三个核心步骤：

1. 主库写入 binlog：主库执行完修改操作后，将变更记录写入 binlog

2. 从库拉取 binlog：从库的 IO 线程连接到主库，请求拉取指定位置之后的 binlog，主库通过 dump 线程将 binlog 发送给从库，从库将收到的 binlog 写入本地的 relay log（中继日志）

3. 从库重放 binlog：从库的 SQL 线程读取 relay log，重放其中的 SQL 语句，将变更应用到从库数据库中

这里我想重点澄清一个常见误区：很多人以为主从复制是同步的，其实**默认是异步的**，主库提交事务后不需要等待从库确认，所以存在主从延迟的问题。如果需要强一致性，可以使用半同步复制。

接下来是 binlog 的常见应用场景：

- 误删数据恢复：使用`mysqlbinlog`工具解析 binlog，将指定时间范围内的 SQL 语句重放，恢复误删的数据

- 数据同步：使用 Canal、Debezium 等工具监听 binlog，将数据同步到 Redis、Elasticsearch、数据仓库等

- 数据备份：配合全量备份，实现增量备份和时间点恢复

- 读写分离：基于主从复制实现读写分离，主库写，从库读，提升系统吞吐量

最后是实际开发中的最佳实践：

1. 强制使用 ROW 格式，设置`binlog_row_image=MINIMAL`，兼顾一致性和性能

2. 设置合理的 binlog 保留时间，一般 7\-15 天，避免磁盘空间被占满

3. 核心业务设置`sync_binlog=1`和`innodb_flush_log_at_trx_commit=1`，保证数据不丢失

4. 定期备份 binlog，不要只备份数据库文件

5. 不要手动修改 binlog 文件，避免主从复制中断

6. 监控 binlog 的生成速度和磁盘使用情况，及时预警

### Q3\. UndoLog日志的作用是什么？

关于 MySQL UndoLog 日志，我从核心本质、两大核心作用、工作原理与生命周期、与 RedoLog 的核心区别、常见误区和实际开发应用六个方面来回答：

首先，UndoLog 的核心本质是InnoDB 存储引擎层生成的逻辑回滚日志，它是 InnoDB 实现事务原子性、隔离性和 MVCC 多版本并发控制的核心基础。和 Server 层的 binlog 不同，UndoLog 只存在于 InnoDB 引擎中，MyISAM 引擎没有 UndoLog，这也是 MyISAM 不支持事务和行级锁的根本原因。

接下来是 UndoLog 的两大核心作用，这也是它存在的意义：

1. 实现事务的原子性（回滚）：这是 UndoLog 最原始的作用。当事务执行过程中发生错误或者用户手动调用`ROLLBACK`时，InnoDB 可以根据 UndoLog 中记录的数据修改前的状态，将数据回滚到事务开始前的样子，保证事务要么全部成功，要么全部失败。

2. 实现 MVCC 多版本并发控制：这是 UndoLog 现在最重要的作用。当一个事务修改数据时，InnoDB 会将修改前的数据版本保存到 UndoLog 中，形成一个数据版本链。这样不同的事务可以读取到自己应该看到的数据版本，实现了非锁定的一致性读，大大提升了数据库的并发性能。

然后是 UndoLog 的工作原理与生命周期。UndoLog 是逻辑日志，它记录的不是数据页的物理变化，而是 "如何撤销这次修改" 的逻辑操作。比如执行`UPDATE`语句时，UndoLog 会记录一条相反的`UPDATE`语句；执行`DELETE`语句时，UndoLog 会记录一条对应的`INSERT`语句。

UndoLog 的生命周期分为三个阶段：

1. 生成阶段：事务执行修改操作时，同步生成对应的 UndoLog 记录

2. 使用阶段：事务回滚时使用 UndoLog 恢复数据；其他事务进行一致性读时，通过 UndoLog 读取历史版本数据

3. 删除阶段：当没有任何事务再引用这个 UndoLog 版本时，由后台的 Purge 线程定期清理删除

这里我想重点讲一下两种不同类型的 UndoLog：

- Insert Undo：对应`INSERT`操作，只在事务回滚时需要，事务提交后可以立即删除

- Update Undo：对应`UPDATE`和`DELETE`操作，不仅用于回滚，还用于 MVCC，所以事务提交后不能立即删除，需要等到没有任何事务引用这个历史版本时才能删除

接下来是面试必考的 UndoLog 与 RedoLog 的核心区别：

这里我想重点澄清两个非常常见的误区：第一，很多人以为 UndoLog 是 RedoLog 的逆过程，其实完全不是，RedoLog 是物理日志，记录页的修改；UndoLog 是逻辑日志，记录如何回滚，两者是完全独立的。第二，很多人以为 UndoLog 只用于事务回滚，其实现在 MVCC 才是 UndoLog 更重要的作用，也是 InnoDB 并发性能远超其他引擎的关键。

### Q4\. 有了undolog为啥还需要redolog呢？

> " 核心是：undo 和 redo 保护的是事务的两个不同阶段。
> 
> 先说前提，InnoDB 用了 Buffer Pool，读写都先在内存里做，而内存断电就没了。
> 
> undo log 记录的是事务**开始前的旧值**，任务是回滚和 MVCC。但你想，如果事务**已经提交**了呢？提交意味着这个修改要永久生效，可这时候数据页可能还在内存里、没刷盘。万一此刻宕机，undo 里只有旧值，它没法帮你把 ' 已经提交的新值 ' 找回来 ——undo 只知道怎么**撤销**，不知道怎么**重做**。
> 
> 所以还需要 redo log。它记录的是数据页**应该变成什么样**，比如 ' 哪个表空间的哪个页、偏移量多少、改成了什么 '。事务提交时只要 redo log 刷到磁盘，就算持久化了，数据页可以之后慢慢刷。
> 
> 这样崩溃恢复时：**已提交但没刷盘的，靠 redo 重做**（保持久性）；**没提交的，靠 undo 回滚**（保原子性），一个往前、一个往后。
> 
> 而且 redo 是顺序追加写，比随机写快几个数量级，这也是 InnoDB 高并发写入的关键。"
> 
> 

Buffer Pool 是提高了读写效率没错，但是问题来了，Buffer Pool 是基于内存的，而内存总是不可靠，万一断电重启，还没来得及落盘的脏页数据就会丢失。

为了防止断电导致数据丢失的问题，当有一条记录需要更新的时候，InnoDB 引擎就会先更新内存（同时标记为脏页），然后将本次对这个页的修改以  redo log 的形式记录下来，这个时候更新就算完成了

后续，InnoDB 引擎会在适当的时候，由后台线程将缓存在 Buffer Pool 的脏页刷新到磁盘里，这就是 WAL （Write\-Ahead Logging）技术。

> WAL 技术指的是， MySQL 的写操作并不是立刻写到磁盘上，而是先写日志，然后在合适的时间再写到磁盘上。
> 
>

redo log 是物理日志，记录了某个数据页做了什么修改，比如对 XXX 表空间中的 YYY 数据页 ZZZ 偏移量的地方做了AAA 更新，每当执行一个事务就会产生这样的一条或者多条物理日志。

在事务提交时，只要先将 redo log 持久化到磁盘即可，可以不需要等到将缓存在 Buffer Pool 里的脏页数据持久化到磁盘。**当系统崩溃时**，虽然脏页数据没有持久化，但是 redo log 已经持久化，接着 MySQL 重启后，可以根据 redo log 的内容，将所有数据恢复到最新的状态。

redo log 和 undo log 这两种日志是属于 InnoDB 存储引擎的日志，它们的区别在于：

- redo log 记录了此次事务「完成后」的数据状态，记录的是更新之后的值；

- undo log 记录了此次事务「开始前」的数据状态，记录的是更新之前的值；

- **详细描述**：UndoLog 是在事务执行过程中写入的，记录的是修改前的数据版本。当事务提交时，UndoLog 已经写入完成，但此时数据可能还在内存中，没有刷到磁盘。如果此时数据库宕机，内存中的数据会丢失，而 UndoLog 中只有修改前的版本，无法恢复已经提交的修改。而 RedoLog 是在事务提交时必须写入磁盘的，只要 RedoLog 写入成功，即使数据还没刷到磁盘，事务也被认为是持久化的，宕机后可以通过 RedoLog 恢复。

UndoLog 是随机写入的，因为不同事务修改的数据页是分散的。而 RedoLog 是顺序写入的，所有的修改都追加到 RedoLog 文件的末尾，顺序写入的性能比随机写入高几个数量级。这也是 InnoDB 能够支持高并发写入的关键原因之一。

接下来是两者协同工作的完整流程，以一个 UPDATE 事务为例：

1. 事务开始，执行 UPDATE 语句，先将数据页从磁盘读到内存中

2. 生成 UndoLog，记录修改前的数据版本，写入 Undo 缓冲区

3. 修改内存中的数据页

4. 生成 RedoLog，记录数据页的修改内容，写入 Redo 缓冲区

5. 事务提交，将 Redo 缓冲区中的内容强制刷到磁盘（根据 innodb\_flush\_log\_at\_trx\_commit 参数）

6. 后台线程异步将内存中的脏数据页刷到磁盘

7. 当没有事务引用 UndoLog 时，由 Purge 线程清理 UndoLog

如果在步骤 5 之后、步骤 6 之前数据库宕机，重启后会通过 RedoLog 将内存中的修改重新应用到磁盘，保证事务的持久性；如果在步骤 5 之前数据库宕机，重启后会通过 UndoLog 回滚未提交的事务，保证事务的原子性。

### Q6\. binlog 两阶段提交过程是怎么样的？

关于 MySQL binlog 两阶段提交，我从核心本质、为什么需要两阶段提交、完整两阶段提交流程、崩溃恢复判断逻辑、为什么不能反过来、常见误区和实际开发应用七个方面来回答：

首先，binlog 两阶段提交的核心本质是MySQL 为了解决 Server 层 binlog 和 InnoDB 层 redo log 的数据一致性问题，设计的内部原子性提交协议。因为 binlog 属于 Server 层，redo log 属于 InnoDB 存储引擎层，两者是完全独立的日志系统，如果没有协调机制，可能会出现两个日志不一致的情况，导致崩溃恢复后数据错误或者主从复制数据不一致。两阶段提交就是为了保证这两个日志的原子性：要么都写成功，要么都写失败。

接下来是为什么必须要有两阶段提交，这是理解这个问题的基础。如果没有两阶段提交，无论先写哪个日志，都会出现一致性问题：

- 先写 redo log，再写 binlog：如果 redo log 写完后，写 binlog 之前数据库宕机，那么 redo log 中有这个事务的记录，崩溃恢复后会提交这个事务，但 binlog 中没有记录，主从复制时从库不会执行这个事务，导致主从不一致。

- 先写 binlog，再写 redo log：如果 binlog 写完后，写 redo log 之前数据库宕机，那么 binlog 中有这个事务的记录，从库会执行这个事务，但 redo log 中没有记录，崩溃恢复后会回滚这个事务，导致主库和从库数据不一致。

只有通过两阶段提交，才能保证两个日志的原子性，彻底解决这个问题。

然后是面试必考的**完整两阶段提交流程**，以一个普通的 UPDATE 事务为例，整个过程分为两个阶段：

**第一阶段：准备阶段（Prepare Phase）**

1. 事务执行过程中，先修改内存中的数据页，同时生成对应的 redo log 和 undo log，写入各自的缓冲区

2. 事务执行完成，调用提交接口，进入两阶段提交

3. InnoDB 将 redo log 缓冲区中的内容强制刷到磁盘，并将事务状态标记为`PREPARED`（准备状态）

4. 此时事务已经具备了崩溃恢复的能力，即使数据库宕机，重启后也能知道这个事务的状态

**第二阶段：提交阶段**（Commit Phase）

1. Server 层将 binlog 缓冲区中的内容强制刷到磁盘，写入 binlog 文件

2. Server 层调用 InnoDB 的提交接口，InnoDB 将 redo log 中的事务状态从`PREPARED`修改为`COMMITTED`（提交状态）

3. 事务正式提交完成，释放锁和资源

整个过程中，只要 redo log 和 binlog 都成功写入磁盘，事务就被认为是持久化的，即使之后数据库宕机，也能正确恢复。

接下来是崩溃恢复的判断逻辑，这是两阶段提交的核心，也是面试的高频考点。数据库重启后，会扫描最后一个检查点之后的所有 redo log，对于每个处于`PREPARED`状态的事务，执行以下判断：

1. 如果 binlog 中存在这个事务的完整记录：说明提交阶段已经完成了 binlog 的写入，只是还没来得及修改 redo log 的状态，此时自动提交这个事务；如果 binlog 中不存在这个事务的完整记录：说明提交阶段还没开始写 binlog，此时自动回滚这个事务

MySQL 判断 binlog 是否完整的依据是：每个事务的 binlog 末尾都有一个特殊的`XID_EVENT`事件，只要 binlog 中存在这个事件，就认为这个事务的 binlog 是完整的。

这里我想重点讲一个问题：为什么不能反过来，先写 binlog 再写 redo log 的 prepare？ 因为 redo log 是 InnoDB 崩溃恢复的唯一依据。如果先写 binlog 再写 redo log 的 prepare，中间宕机的话，binlog 已经写入磁盘，从库会执行这个事务，但 redo log 中没有任何记录，崩溃恢复后主库会回滚这个事务，导致主从不一致。而现在的顺序，只要 redo log 是 prepare 状态，即使 binlog 没写，也可以安全回滚，不会影响从库。

然后是常见误区部分，我想澄清两个非常常见的错误认知： 第一，很多人以为这个两阶段提交是分布式事务的两阶段提交，其实不是，这是数据库内部的单机两阶段提交，是为了协调两个不同层级的日志系统，和分布式事务的 XA 两阶段提交是完全不同的概念。 第二，很多人以为两阶段提交会严重影响性能，其实 MySQL 做了大量的优化，最核心的是组提交（Group Commit），可以将多个事务的刷盘操作合并成一次，大大降低了磁盘 IO 的开销，现在的性能已经非常高了。

### Q7\. update语句的具体执行过程是怎样的？

" 我以 `UPDATE t_user SET name='xiaolin' WHERE id=1` 为例，整个过程分三大块：**执行器找数据、InnoDB 做更新、事务提交走两阶段**。

第一步，执行器找 id=1 这行：先看 Buffer Pool 里有没有，有就直接用；没有就从磁盘把数据页读到 Buffer Pool。

第二步，执行器对比更新前后的值，一样就不做任何操作；不一样才把新旧记录交给 InnoDB。

第三步，InnoDB 真正更新，而且**先写 undo log**，把旧值记下来，用于回滚和 MVCC。

第四步，更新内存里的数据页并标记为脏页，同时把这次物理修改写到 redo log buffer—— 这就是 WAL，先写日志，脏页之后由后台线程异步刷盘。

第五步，这条语句的 binlog 先写到 binlog cache，还不刷盘。

最后事务提交，走两阶段提交：**先把 redo log 刷盘、状态置为 prepare；再把 binlog 刷盘；然后把 redo log 状态改成 commit**，事务才算完成。

这样一条更新语句，既保证崩溃可恢复，又保证 redo 和 binlog 一致。"

### Q8\. MySQL是如何保障数据不丢失的？

关于 MySQL 如何保障数据不丢失，我从核心本质、四大核心保障机制、崩溃恢复完整流程、常见误区和实际开发最佳实践五个方面来回答：

首先，MySQL 保障数据不丢失的**核心本质**是基于 WAL 预写日志技术构建的多层级、多日志协同的持久化体系。将随机磁盘写转化为顺序日志写，在保证极致写入性能的同时，通过 Redo Log、Undo Log、Binlog 三大日志和两阶段提交协议，从机制上杜绝了数据丢失的可能性。即使数据库突然宕机、服务器断电甚至磁盘损坏，也能通过日志完整恢复数据。

接下来是四大核心保障机制，这是 MySQL 数据不丢失的基石：

1. **WAL 预写日志技术**（Write\-Ahead Logging）

这是整个持久化体系的基础，核心原则是所有修改先写日志，再写内存，最后异步刷盘。

- 任何对数据的修改都不会直接写入磁盘，而是先写入日志文件

- 只要日志成功写入磁盘，事务就被认为是持久化的，即使内存中的数据还没刷盘

- 脏数据页的刷盘由后台线程异步完成，不影响事务提交性能

- 它将随机磁盘写转化为顺序日志写，性能提升了几个数量级

2. **Redo Log：崩溃恢复的核心保障**

Redo Log 是 InnoDB 存储引擎层的物理日志，是保证事务持久性的关键。

- 物理日志：精确记录每个数据页的修改内容，而不是 SQL 语句

- 循环写入：固定大小的日志文件组（默认 2 个 1GB 文件），写满后循环覆盖

- 强制刷盘：事务提交时，Redo Log 必须强制刷到磁盘（由`innodb_flush_log_at_trx_commit=1`控制）

- 崩溃恢复：数据库宕机重启后，自动重放最后一次检查点之后的 Redo Log，将所有已提交但未刷盘的修改重新应用到磁盘

3. 两阶段提交协议：保证双日志一致性

专门用于协调 Server 层 Binlog 和 InnoDB 层 Redo Log 的原子性，彻底解决主从不一致问题。

- Prepare 阶段：先将 Redo Log 刷盘，标记事务为`PREPARED`状态

- Commit 阶段：再将 Binlog 刷盘，然后将 Redo Log 标记为`COMMITTED`状态

- 崩溃恢复判断逻辑： 

    - 如果 Redo Log 是`PREPARED`且 Binlog 完整：自动提交事务

    - 如果 Redo Log 是`PREPARED`但 Binlog 不存在：自动回滚事务

- 保证了两个日志要么都写成功，要么都写失败，永远不会出现一个有一个没有的情况

4. Binlog：数据恢复与主从一致性保障

Binlog 是 MySQL Server 层的逻辑日志，是数据备份和主从复制的基础。

- 逻辑日志：记录 SQL 语句或行的变化，与存储引擎无关

- 追加写入：不循环覆盖，按文件大小滚动生成新文件

- 强制刷盘：事务提交时，Binlog 必须强制刷到磁盘（由`sync_binlog=1`控制）

- 数据恢复：配合全量备份，可以将数据库恢复到任意时间点

- 主从复制：主库将 Binlog 发送给从库，从库重放 Binlog 实现数据同步

然后是面试必考的**崩溃恢复完整流程**，这是数据不丢失的最后一道防线：

1. 数据库重启后，首先扫描 Redo Log，找到最后一次检查点的位置

2. 从检查点开始重放所有 Redo Log 记录，将数据页恢复到宕机前的状态

3. 对于所有处于`PREPARED`状态的事务，检查 Binlog 中是否存在对应的完整记录

4. 如果 Binlog 存在，提交该事务；如果 Binlog 不存在，回滚该事务

5. 回滚所有未提交的事务，释放锁和资源

6. 数据库恢复完成，可以正常提供服务

整个过程完全自动执行，不需要人工干预，通常只需要几秒钟就能完成。

这里我想重点澄清三个非常常见的误区： 第一，事务提交时不会刷脏页，事务提交只保证 Redo Log 和 Binlog 刷盘，脏页刷盘是后台异步进行的。这是 WAL 技术的核心，也是 MySQL 高性能的关键。 第二，Binlog 不能替代 Redo Log，两者作用完全不同：Redo Log 用于崩溃恢复，Binlog 用于数据恢复和主从复制。没有 Redo Log，InnoDB 的崩溃安全就失去了基础。 第三，双 1 参数不会严重影响性能，MySQL 通过组提交（Group Commit）技术，将多个事务的刷盘操作合并成一次，大大降低了磁盘 IO 开销，现在的性能已经完全可以满足绝大多数业务需求。

## 性能调优

### Q1\. mysql的explain有什么作用？

关于 MySQL 的 EXPLAIN，我从它是什么、能解决什么问题、怎么看结果、常见坑和实际怎么用这几个方面来给您说一下。

首先，EXPLAIN 说白了就是 MySQL 给我们提供的一个SQL 执行计划模拟器。我们写的 SQL 最终是怎么被 MySQL 执行的，有没有用到索引，扫了多少行数据，这些我们肉眼是看不到的。EXPLAIN 就能把这个过程模拟出来，让我们一眼就能看到 SQL 的性能瓶颈在哪里。可以说它是我们做 MySQL 性能优化的第一神器，只要是写 SQL 的后端开发，这个工具是必须要会的。

接下来是它的核心作用，主要有六个： 第一，能看复杂 SQL 里各个子查询和表连接的执行顺序； 第二，能看 MySQL 是按什么顺序访问各个表的； 第三，也是最重要的，能看 SQL 到底有没有用到索引，用了哪个索引； 第四，能看表之间是用什么方式连接的； 第五，能预估 MySQL 需要扫描多少行才能得到结果，这个是判断 SQL 快慢最直观的指标； 第六，能看到一些额外的关键信息，比如有没有用临时表，有没有做文件排序这些。

然后是怎么看 EXPLAIN 的结果，其实不用记所有字段，重点看五个就够了： 第一个是`id`，用来判断执行顺序。id 越大越先执行，id 相同就从上到下执行。 第二个是`type`，这是最重要的字段，表示 MySQL 访问表的方式，性能从好到坏依次是：system \> const \> eq\_ref \> ref \> range \> index \> ALL。

- 最好的情况是 const 和 eq\_ref，一般是主键或者唯一索引的等值查询；

- 然后是 ref，非唯一索引的等值查询，这个性能也很好；

- 再往下是 range，索引范围查询，比如大于小于、between 这些，一般也能接受；

- 再往下是 index，扫描整个索引树，比全表扫描好一点，但也很慢；

- 最差的是 ALL，全表扫描，这个是必须要优化的。 第三个是`key`，表示 MySQL 实际用了哪个索引。这里要注意，`possible_keys`是可能用到的索引，`key`才是真正用到的，很多时候 possible\_keys 里有很多，但 key 可能是 null，说明没用到索引。 第四个是`rows`，预估扫描的行数，这个值越小越好。比如一个查询 rows 是 10，和 rows 是 100 万，性能差了十万八千里。 第五个是`Extra`，这是第二重要的字段，包含了很多关键信息：

- 看到`Using index`是最好的，说明用了覆盖索引，查询的字段都在索引里，不需要回表查数据；

- 看到`Using filesort`就不好了，说明 MySQL 需要额外做排序，不能用索引排序，这个必须优化；

- 看到`Using temporary`就更差了，说明 MySQL 需要创建临时表来存结果，常见于 group by 和 order by 没用到索引的情况，这个也必须优化。

### Q2\. 给你张表，发现查询速度很慢，你有那些解决方案

遇到慢查询，我的核心思路是**先定位根因、再按成本从低到高优化，绝不一上来就盲目加索引**。

**第一步，定位问题。**

先开启慢查询日志，把阈值设为 1 秒，把慢 SQL 抓出来；然后用 `EXPLAIN` 分析执行计划，重点看四个字段：**type** 看有没有全表扫描、**key** 看实际用了哪个索引、**rows** 看扫描了多少行、**Extra** 看有没有文件排序、临时表。这样就能判断慢在索引缺失、索引失效，还是扫描行数太多。

另外我也会用 `SHOW PROCESSLIST` 排除是不是锁等待导致的慢，而不是 SQL 本身。

**第二步，针对性优化，我按成本从低到高讲。**

**第一是索引优化，这是最有效、成本最低的手段。** 给 WHERE、ORDER BY、GROUP BY、JOIN 的字段建索引；多字段查询优先建联合索引，遵循最左匹配原则；最好能做成覆盖索引，让查询字段都在索引里，避免回表。同时要避免索引失效，比如左模糊、在索引字段上做函数计算、隐式类型转换。这里我想强调一点：**索引走不走，最终是优化器基于成本决定的，不是操作符机械决定的**—— 像 `!=`、`OR` 不一定失效，OR 两边都有索引时还可能走索引合并，要以 EXPLAIN 为准。

**第二是 SQL 本身优化。** 避免 `SELECT *`，只查需要的列，也更容易用上覆盖索引；联表查询遵循小表驱动大表，被驱动表的连接字段要有索引；复杂的统计计算放到应用层。

**第三是深分页优化。** `LIMIT 100000, 10` 会扫描前 10 万行再丢弃，我会改成游标分页，比如 `WHERE id > 20000 LIMIT 10`，或者用延迟关联先查主键再回表，代价是游标法不能跳页，适合 "加载更多" 场景。

**第四是表结构优化。** 单表数据量到千万级这个经验值时，考虑水平分表或垂直拆分宽表；选择更紧凑的数据类型；并尽量避免 NULL，因为它带来三值逻辑和统计问题 —— 不过要说明，NULL 本身是可以走索引的。

**第五是引入缓存。** 热点数据用 Redis 做旁路缓存，读的时候先查缓存，写的时候先更新数据库再删除缓存，保证最终一致性。

**第六是架构层面。** 做读写分离、用连接池，报表统计类查询交给 ES、ClickHouse，同时避免长事务长时间持有锁。

**最后说一下项目落地。** 我在券享购项目里，就是通过慢查询日志定位到优惠券查询的全表扫描，给用户和券的联合字段建了覆盖索引，查询性能从 P99 两秒降到了几十毫秒；热点数据再走 Redis，命中率做到 90% 以上。

总的来说，慢查询 90% 是索引和 SQL 的问题，我会优先用低成本手段解决，再考虑表结构和架构。

# Redis

## 数据结构

### Q1\. 讲一下Redis底层的数据结构

> 我从 "**对象外壳、底层结构、编码切换**" 三个层次来讲。
> 
> **首先，Redis 每种数据类型在内部都不是写死一个结构，而是包了一层 RedisObject 对象头**，它有 5 个字段：type 是对外类型，encoding 是底层编码，ptr 指向真正的数据，refcount 是引用计数，lru 记录最后访问时间、用于内存淘汰。这层外壳让 Redis 能根据数据量自动切换底层结构，实现多态。
> 
> **然后是底层数据结构，一共 8 种，我分组讲。**
> 
> 第一类是字符串，用的是自研的 **SDS**，不是 C 原生字符串。它有 len 字段，取长度 O \(1\)；用 len 而不是 `\0` 判断结束，二进制安全；还会自动扩容、预分配空间，不会缓冲区溢出。
> 
> 第二类是列表相关的，有**双向链表、压缩列表、快速列表、listpack**。双向链表头尾操作 O \(1\)；压缩列表是连续内存、没有指针，省内存，适合少量数据；快速列表是 Redis 3\.2 把双向链表和压缩列表结合，是现在 List 的默认结构；listpack 是 5\.0 设计、7\.0 全面替换压缩列表，解决了压缩列表的连锁更新问题。
> 
> 第三类是**哈希表 dict**，用链地址法解决冲突，内部有两个哈希表做渐进式 rehash，把扩容迁移分摊到每次操作，避免一次性阻塞；正常负载因子到 1 就扩容、低于 0\.1 缩容。
> 
> 第四类是**跳表**，是 ZSet 大量数据时的底层，多层索引、查找 O \(logn\)，比红黑树实现简单、范围查询方便，层高上限 32、随机生成。
> 
> 还有**整数集合 intset**，专门存整数，内存极省，能从 int16 自动升级到 int64。
> 
> **最后是编码切换，举几个典型：** String 整数用 int、短字符串不超过 44 字节用 embstr、长的用 raw；Set 全是整数且少于 512 用 intset，否则用 dict；ZSet 少量用 listpack（7\.0 前是 ziplist），大量用跳表加 dict。
> 
> 场景上，String 做缓存和计数、List 做简单队列、Hash 存对象和购物车、Set 做标签和抽奖、ZSet 做排行榜。
> 
> 

Redis 提供了丰富的数据类型，常见的有五种数据类型：String（字符串），Hash（哈希），List（列表），Set（集合）、Zset（有序集合）。

每种类型都对应多种底层编码。每个 RedisObject 包含 **5** 个核心字段：

- `type`：对外的数据类型，比如 String、List

- `encoding`：底层使用的编码方式，也就是具体的数据结构

- `ptr`：指向底层数据结构的指针

- `refcount`：引用计数，用于内存回收

- `lru`：最后一次访问时间，用于内存淘汰

然后是 8 种核心底层数据结构详解，这是面试的核心考点：

1. 简单动态字符串（SDS）

这是 Redis 最基础的结构，代替了 C 语言的原生字符串。核心特点：

- 二进制安全，可以存储任意二进制数据

- 获取字符串长度 O \(1\)，因为内部维护了 len 字段

- 自动扩容，避免缓冲区溢出

- 预分配内存和惰性释放，减少内存分配次数

2. 双向链表（Adlist）

经典的双端链表结构，每个节点有 prev 和 next 指针。核心特点：

- 头尾操作 O \(1\) 时间复杂度

- 支持双向遍历

- 无环，头尾节点指向 NULL

- 每个节点可以存储不同类型的数据

3. 压缩列表（ZipList）

为了节省内存设计的连续内存结构，没有指针，用偏移量访问。核心特点：

- 内存利用率极高，没有额外的指针开销

- 适合存储少量小数据

- 插入和删除操作 O \(n\) 时间复杂度

- 是很多数据类型在数据量小时的默认编码

4. 哈希表（Dict）

Redis 最核心的结构，几乎所有数据类型都用到。核心特点：

- 采用链地址法解决哈希冲突

- 每个哈希表有两个 ht \[0\] 和 ht \[1\]，用于渐进式 rehash

- 渐进式 rehash：分多次完成 rehash，避免一次性阻塞整个 Redis

- 负载因子超过 1 时自动扩容，低于 0\.1 时自动缩容

5. 跳表（SkipList）

有序集合 ZSet 的底层实现，是平衡树的替代方案。核心特点：

- 多层索引结构，平均查找复杂度 O \(logn\)

- 实现比红黑树简单得多

- 支持范围查询，这是比哈希表更适合做有序集合的原因

- 每个节点可以有多个层级，最高 32 层

6. 整数集合（IntSet）

专门用于存储整数的集合结构。核心特点：

- 内存利用率极高，没有额外开销

- 自动升级编码：从 int16 升级到 int32 再到 int64

- 只支持整数，不支持其他类型

- 数据量小时性能远超哈希表

7. 快速列表（QuickList）

Redis 3\.2 引入，是压缩列表和双向链表的结合。核心特点：

- 将多个压缩列表用链表连接起来

- 兼顾了压缩列表的内存优势和链表的操作性能

- 是现在 List 类型的默认底层结构

Redis 五种数据类型的应用场景：

- String 类型的应用场景：缓存对象、常规计数、分布式锁、共享 session 信息等。

- List 类型的应用场景：消息队列（但是有两个问题：1\. 生产者需要自行实现全局唯一 ID；2\. 不能以消费组形式消费数据）等。

- Hash 类型：缓存对象、购物车等。

- Set 类型：聚合计算（并集、交集、差集）场景，比如点赞、共同关注、抽奖活动等。

- Zset 类型：排序场景，比如排行榜、电话和姓名排序等。

### Q2\. Redis 中 set和zset区别是什么？

> 我从 "**核心区别、底层实现、适用场景**" 三方面讲。
> 
> **首先核心区别**：Set 是无序不重复集合；ZSet 是有序不重复集合，给每个元素多带一个 score 分数，元素唯一、分数可以重复。
> 
> **然后是底层实现，这是关键。**
> 
> Set 有两种编码、自动切换：全是整数且数量少于 512 时用 **intset**，内存极省，还能从 int16 自动升级到 int64；不满足就用 **dict**，哈希表的 key 存元素、value 为 NULL，增删查都是 O \(1\)。
> 
> ZSet 也有两种：数据量小，元素少于 128 且每个小于 64 字节时，用连续内存的压缩列表（**Redis 7\.0 后改成 listpack**）；数据量大就用**跳表加字典**。
> 
> 这里我想重点讲一下**为什么 ZSet 要同时用跳表和字典这两个结构**—— 它们职责互补：跳表负责按分数排序和范围查询，比如 ZRANGE、排行榜；字典负责按元素 O \(1\) 查分数，比如 ZSCORE。如果只有跳表，查一个元素的分数要 O \(logn\)；只有字典，又没法排序和范围查询。所以用空间换时间，两个一起用。
> 
> **场景上**，Set 适合去重和集合运算，比如点赞、共同关注、黑白名单、抽奖；ZSet 适合排序，比如排行榜、延时任务、带权重的队列。
> 
> 至于**为什么用跳表不用红黑树**，主要是跳表范围查询方便，找到起点沿链表遍历即可，而且实现简单、插入是局部修改，不需要红黑树那样复杂的旋转。
> 
> 

Redis 中的 Set 和 ZSet（Sorted Set，有序集合）都是用于存储多个元素的集合类型，但它们的核心区别在于是否对元素进行排序以及排序方式，这直接影响了它们的适用场景。

- Set 是无序不重复集合，设计目标是快速判断元素是否存在，以及高效计算多个集合之间的交集、并集、差集

- ZSet 是有序不重复集合，也叫 Sorted Set，在 Set 的基础上给每个元素增加了一个分数 \(score\)，设计目标是支持按分数排序（元素唯一，但分数可重复）和范围查询

然后是各自的底层实现，这是理解性能差异的关键：

Set 有两种编码方式，会自动切换：

1. **intset 编码**：当所有元素都是整数，且元素个数小于 512 个时使用 

    - 内存利用率极高，没有额外开销

    - 自动升级编码，从 int16 到 int32 再到 int64

2. **dict 编码**：不满足 intset 条件时自动切换 

    - 用哈希表的 key 存储元素，value 固定为 NULL

    - 所有操作都是 O \(1\) 时间复杂度

ZSet 也有两种编码方式，同样会自动切换：

1. **ziplist 编码**：当元素个数小于 128 个，且每个元素大小小于 64 字节时使用 

    - 连续内存存储，内存利用率极高

    - 插入删除是 O \(n\) 时间复杂度

2. **skiplist\+dict 编码**：不满足 ziplist 条件时自动切换 

    - 跳表：用于按分数排序和范围查询，O \(logn\) 时间复杂度

    - 哈希表：用于 O \(1\) 时间查询元素的分数；它的 key 是 ZSet 的元素值，value 是对应的分数

    - 两者结合，兼顾了有序性和查询性能

接下来是两者的**典型适用场景**，这也是面试常考的点：

Set 的典型适用场景

1. 数据去重：比如用户点赞、收藏、浏览记录，保证一个用户只能点赞一次

2. 集合运算：计算共同好友、共同关注、用户标签交集等

3. 黑白名单：判断 IP 地址、用户 ID 是否在黑名单中

4. 随机抽奖：用`SRANDMEMBER`命令随机抽取中奖用户

ZSet 的典型适用场景

1. 排行榜系统：这是 ZSet 最经典的应用，比如商品销量榜、用户积分榜、热搜榜

2. 延时任务：用时间戳作为分数，定时查询分数小于当前时间的任务执行

3. 带权重的队列：优先级高的任务分数高，优先被处理

4. 范围查询：比如查询某个时间段内的用户注册数、订单数

**为什么 ZSet 用跳表而不用红黑树？**

1. 范围查询性能更好：跳表可以很方便地实现范围查询，只需要找到范围的起点，然后沿着链表遍历即可。而红黑树的范围查询实现起来非常复杂，性能也不如跳表

2. 实现和维护更简单：跳表的代码量只有红黑树的几分之一，不容易出 bug，维护成本低

3. 并发性能更好：跳表的修改操作只需要修改局部节点，不需要像红黑树那样进行复杂的旋转操作，对并发更友好



#### Zset 底层是怎么实现的？

> " 以 Redis 7\.0 为例，ZSet 有**两种编码**，根据数据量自动切换。
> 
> **数据量小的时候用 listpack**，条件是元素个数不超过 128、每个元素不超过 64 字节。它把成员和分值成对存在一个紧凑的连续内存容器里，不额外维护字典，内存很省；但按成员查需要遍历，是 O \(N\)。
> 
> **一旦超过限制，就转换成『跳表 \+ 字典』的组合：**
> 
> 跳表是一个多层有序链表，按 score 排序，支持平均 O \(logN\) 的插入、删除和排名定位，范围查询是 O \(logN \+ M\)；
> 
> 字典是哈希表，key 是成员、value 是 score，让 ZSCORE 这种按成员查分数的操作是 **O\(1\)**。
> 
> 两者同时维护、各司其职：**跳表负责有序和范围，字典负责单点查分数**。

> 
> 排序规则是**先按 score，score 相同再按成员字节序**。"

### Q3\. 跳表是怎么实现的？

> " 先说为什么需要它。普通有序链表只能从头逐个遍历，查找是 O \(N\)。跳表给底层链表加了一层层索引：**最底层 L0 是包含所有节点的完整链表，往上每一层都是它下一层的稀疏索引，节点更少、跨度更大**。
> 
> 查找时**从最高层开始**，像走高架桥一样先在高层大步跨越，一旦发现 ' 下一个节点比目标大 '，就下降一层继续找，逐层下降，直到在最底层精确定位，平均复杂度 O \(logN\)。
> 
> 举个例子，查找节点 4：在 L2 直接从 head 跳到节点 3，跳过了 1、2；节点 3 在 L2 没有后续，下降到 L1；L1 上下一个是 5、比 4 大，再下降到 L0；L0 上节点 3 的下一个就是 4，找到。普通链表要走 4 步，跳表只用 2 次定位。
> 
> **节点结构**上，每个节点包含：元素 ele、分数 score、后向指针，以及一个 level 数组。level 数组每个元素代表一层，里面有前向指针 **forward**（指向同层下一个节点）和跨度 **span**（记录这个指针跨过多少个底层节点）。
> 
> **跨度用来算排名**，查找时把沿途跨度累加就得到排名，ZRANK 不用从头数；**后向指针**指向前一个节点，方便从尾部倒序遍历。"
> 
> 跳表的**层高是随机生成的**，不是根据当前元素数量计算出来的。
> 
> 

首先，跳表的核心本质是一种基于**有序链表的多层索引结构**，通过 "空间换时间" 的思想，在普通有序链表的基础上增加了多层稀疏索引，将链表原本 O \(n\) 的查找、插入、删除时间复杂度降到了 O \(logn\)，同时保留了链表插入删除高效、实现简单的优点。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=OWE2OGI4MGRmZmE5NWQzMGViMzNkMzYwOWJjMjg5YzZfOWYzNTVmYmYzNWNhOTRkMmE3ZDBkZjgxMzc5NTcxYTZfSUQ6NzY0NTIzNTMzOTEyMzE5OTE2OV8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

```C++
typedef struct zskiplistNode {
    //Zset 对象的元素值
    sds ele;
    //元素权重值
    double score;
    //后向指针: 这里的后向指的是当前节点的前一个node
    struct zskiplistNode *backward;

    //节点的level数组,保存每层上的前向指针和跨度
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;
    } level[];
} zskiplistNode;
```

Zset 对象要同时保存「元素」和「元素的权重」，对应到跳表节点结构里就是 sds 类型的 ele 变量和 double 类型的 score 变量。每个跳表节点都有一个后向指针（struct zskiplistNode \*backward），指向前一个节点，目的是为了方便从跳表的尾节点开始访问节点，这样倒序查找时很方便。

跳表是一个带有层级关系的链表，而且每一层级可以包含多个节点，每一个节点通过指针连接起来，实现这一特性就是靠跳表节点结构体中的zskiplistLevel 结构体类型的 level 数组。

level 数组中的每一个元素代表跳表的一层，也就是由 zskiplistLevel 结构体表示，比如 leve\[0\] 就表示第一层，leve\[1\] 就表示第二层。zskiplistLevel 结构体里定义了「指向下一个跳表节点的指针」和「跨度」，跨度时用来记录两个节点之间的距离。

Redis 跳表在创建节点的时候，随机生成每个节点的层数

- 具体的做法是，跳表在创建节点时候，会生成范围为\[0\-1\]的一个随机数，如果这个随机数小于 0\.25（相当于概率 25%），那么层数就增加 1 层，然后继续生成下一个随机数，直到随机数的结果大于 0\.25 结束，最终确定该节点的层数。这样的做法，相当于每增加一层的概率不超过 25%，层数越高，概率越低，层高最大限制是 64。如果层高最大限制是 64，那么在创建跳表「头节点」的时候，就会直接创建 64 层高的头节点。

### Q4\. Redis为什么使用跳表而不是用B\+树?

> " 这是一个**工程选型问题，Redis 选跳表不是因为它更先进，而是场景匹配度更高**。核心原因有三点：
> 
> **第一，也是最重要的 —— 内存和磁盘的设计初衷不同。** B\+ 树是为磁盘 I/O 优化的，核心是**降低树高**：一个节点对应一个数据页、能存很多索引项，树高通常只有 3\~4 层，一次查找只要 3\~4 次磁盘 I/O。但 Redis 是纯内存操作，**没有磁盘 I/O 瓶颈，内存里指针跳转极快**，跳表虽然层数多一些，但多几次指针跳转的开销很小；反观 B\+ 树为压低树高而设计的复杂页管理机制，在内存里反而显得多余、笨重。
> 
> **第二，跳表实现简单、写入更平稳。** 跳表本质是多层链表，插入删除只改**局部指针**、按概率随机生成层高，不需要全局调整；而 B\+ 树插入删除要处理节点**分裂、合并、重平衡**，页分裂时还要移动大量数据，实现复杂、容易产生性能抖动。
> 
> **第三，跳表范围查询天然友好。** 找到起点后沿底层链表往后遍历即可，配合 span 还能算排名。
> 
> 当然要客观地说，**B\+ 树在内存里也有缓存局部性的优势**，不是说它在内存里就一定差，只是综合权衡，跳表更契合 Redis 的场景、实现成本更低。"
> 
> 

1. 内存 vs\. 磁盘的设计初衷 \(最重要的原因\)：

    - B\+ 树是为磁盘 I/O 优化的： B\+ 树的设计核心是降低树的高度，从而减少磁盘 I/O 次数

    - Redis 是纯内存操作： 在内存中，没有“磁盘 I/O”的瓶颈。内存中指针跳转的速度非常快。跳表虽然比 B\+ 树高（层数多），但在内存中多几次指针跳转的开销非常小。因此，B\+ 树为了减少高度而设计的复杂页管理机制，在内存场景下显得多余且笨重。

2. 实现复杂度与代码维护：

    - 跳表（SkipList）：本质上是“多层链表”。其插入、删除逻辑主要是修改指针，代码实现非常简洁

    - B\+ 树：插入和删除可能引发节点的分裂（Split）和合并（Merge），甚至需要对整棵树进行重平衡。实现一个健壮、高效的 B\+ 树非常复杂，代码量大且难以调试。

3. 写入性能与重平衡代价：

    - B\+ 树的写入抖动： 当插入数据导致页分裂时，可能需要移动大量数据或改变树结构，这会产生性能抖动。

    - 跳表的局部性： 跳表的插入和删除操作是局部的。插入一个节点只需要修改前后节点的指针，并根据概率随机生成层高。它不需要像红黑树或 B\+ 树那样进行全局的旋转或复杂的结构调整

Redis 选跳表而非 B\+ 树，不是因为跳表 “更先进”，而是场景匹配度更高

### Q5\. 压缩列表是怎么实现的？

压缩列表是 Redis 为了节约内存而开发的，它是由连续内存块组成的顺序型数据结构，有点类似于数组。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MjZkMDA3ZTRmNGVjYjllN2ViYmQ3YzE1ZWZlYzUzZjVfMDNjMDE4ZDE0MzhjZTdiOTE5OTgxZDEzZWE5NDRjOTJfSUQ6NzY0NTI1NTY5OTk0MTU1OTUyMF8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

压缩列表在表头有四个字段：

- *zlbytes* ，记录整个压缩列表占用的内存字节数；

- *zltail*，记录压缩列表「尾部」节点距离起始地址有多少字节，也就是列表尾的偏移量

- *zllen* ，记录压缩列表包含的节点数量；

- *zlend* ，标记压缩列表的结束点，固定值 0xFF（十进制 255）。

压缩列表节点（entry）包含三部分内容：

- prevlen，记录了「前一个节点」的长度，目的是为了实现从后向前遍历；

- encoding，记录了当前节点实际数据的「类型和长度」，类型主要有两种：字符串和整数

- data，记录了当前节点的实际数据，类型和长度都由 encoding 决定；

当我们往压缩列表中插入数据时，压缩列表就会根据数据类型是字符串还是整数，以及数据的大小，会使用不同空间大小的 prevlen 和 encoding 这两个元素里保存的信息，这种根据数据大小和类型进行不同的空间大小分配的设计思想，正是 Redis 为了节省内存而采用的。

压缩列表的缺点是会发生连锁更新的问题，因此连锁更新一旦发生，就会导致压缩列表占用的内存空间要多次重新分配，这就会直接影响到压缩列表的访问性能。虽然压缩列表紧凑型的内存布局能节省内存开销，但是如果保存的元素数量增加了，或是元素变大了，会导致内存重新分配，最糟糕的是会有「连锁更新」的问题。因此，压缩列表只会用于保存的节点数量不多的场景。

针对压缩列表在设计上的不足，在后来的版本中，新增设计了两种数据结构：quicklist（Redis 3\.2 引入） 和 listpack（Redis 5\.0 引入）。这两种数据结构的设计目标，就是尽可能地保持压缩列表节省内存的优势，同时解决压缩列表的「连锁更新」的问题。

> **QuickList 做了折中**：它用双向链表把一个个小容器（quicklistNode）串起来，每个小容器内部是一个压缩列表、存一批元素。这样**连锁更新被限制在单个小容器里，不会波及整个 List**；同时小容器内部连续紧凑，比纯链表省内存。
> 
> 

### Q6\. 介绍一下 Redis 中的 listpack

> "listpack 是 Redis **5\.0 引入**的，目的是**替代压缩列表**，它是一块连续内存、紧凑存储的结构。
> 
> **先说为什么需要它。** 压缩列表最大的问题是连锁更新，根源在于每个节点都用 **prevlen** 记录前一个节点的长度 —— 一旦某个节点变长，后面所有节点的 prevlen 都可能跟着改。旧版 quicklist 虽然通过控制节点大小缓解了，但没根治，因为节点内部还是压缩列表。
> 
> **listpack 的核心改进**：每个节点**不再记录前一个节点的长度，只记录自己的长度**。这样插入新元素时不会影响其他节点的长度字段，从根上消除了连锁更新。
> 
> **结构上**，头部有两个字段：**总字节数和元素数量**；末尾有一个结束标记。每个节点包含三部分：**encoding**（数据类型和长度）、**data**（实际数据）、**len**（encoding \+ data 的总长度）。
> 
> **应用上**，Redis 7\.0 起，小型 Hash、ZSet 直接用 listpack 作紧凑编码，quicklist 节点内部也从压缩列表改成 listpack，7\.2 起小型 List 也能直接用。
> 
> 不过要客观地说，**消除连锁更新不代表插入删除是 O \(1\)**，它还是连续内存，中间插入删除可能要移动后面数据，所以仍适合数据量较小的场景。"
> 
> 

于是，Redis 在 5\.0 新设计一个数据结构叫 listpack，目的是替代压缩列表，它最大特点是 listpack 中每个节点不再包含前一个节点的长度了，压缩列表每个节点正因为需要保存前一个节点的长度字段，就会有连锁更新的隐患。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YjZhZGIyMGI0MGEzMTRlODMxZDVhMDZjY2U1Y2EwNjhfOTFhNmI5MzgwN2RiNjVlMDNhMDNhMjNmNmY4NWU4ZWFfSUQ6NzY0NTI2MDE5ODk3MzY3MjY1Ml8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

Listpack entry 包含的属性：

- encoding，定义该元素的编码类型，会对不同长度的整数和字符串进行编码；

- data，实际存放的数据；

- len，encoding\+data的总长度；

可以看到，listpack 没有压缩列表中记录前一个节点长度的字段了，listpack 只记录当前节点的长度，当我们向 listpack 加入一个新元素的时候，不会影响其他节点的长度字段的变化，从而避免了压缩列表的连锁更新问题。

### Q7\. 哈希表是怎么扩容的？

> "Redis 的哈希表采用**渐进式 rehash**来扩容。我先说结构，再说流程。
> 
> Redis 每个字典都维护了**两个哈希表 ht \[0\] 和 ht \[1\]**。正常情况下数据都在 ht \[0\]，ht \[1\] 不分配空间。
> 
> 当数据增多、负载因子达到阈值，就触发 rehash：
> 
> 1. 先给 **ht \[1\] 分配空间，容量一般是 ht \[0\] 的两倍**；
> 
> 2. 然后把 ht \[0\] 的数据重新算桶位置、迁移到 ht \[1\]；
> 
> 3. 迁移完成后释放 ht \[0\]，把 ht \[1\] 设为新的 ht \[0\]，再准备一个空的 ht \[1\]。
> 
> **问题在于**：如果 ht \[0\] 数据量很大，一次性迁移会阻塞 Redis。所以 Redis 用了**渐进式 rehash**—— 不一次性搬完，而是在 rehash 期间，**每次处理增删改查时，顺便把 ht \[0\] 里的一个桶迁移到 ht \[1\]**；后台定时任务也会按时间预算推进。这样就把一次性的大开销分摊到了多次请求里。
> 
> **rehash 期间的操作规则**：
> 
> - 查、改、删：**先查 ht \[0\]，没有再查 ht \[1\]**；
> 
> - 新增：**直接写 ht \[1\]**，ht \[0\] 不再添加，保证 ht \[0\] 只减不增、最终自然变空。
> 
> **触发条件（负载因子 = 节点数 / 桶数）**：
> 
> - 没有 BGSAVE 等后台任务时，负载因子 **≥ 1** 就扩容；正在 BGSAVE/BGREWRITEAOF 时要 **≥ 5** 才扩容，这是为了配合写时复制、减少扩容带来的内存写入；
> 
> - 缩容：负载因子 **\< 0\.1** 时。"
> 
> 

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzI0YWNjMDcwNDU0Nzk0NjlmMmNiMmExYjg0NWJlY2RfODEzNTUwNGM2ZDUzNTgxYWEwOTY4ZjExNWFhNTgxNjNfSUQ6NzY0NTI2MDgwNTA2Mzc3MzM2OV8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

在正常服务请求阶段，插入的数据，都会写入到「哈希表 1」，此时的「哈希表 2 」 并没有被分配空间

随着数据逐步增多，触发了 rehash 操作，这个过程分为三步：

- 给「哈希表 2」 分配空间，一般会比「哈希表 1」 大 2 倍；

- 将「哈希表 1 」的数据迁移到「哈希表 2」 中；

- 迁移完成后，「哈希表 1 」的空间会被释放，并把「哈希表 2」 设置为「哈希表 1」，然后在「哈希表 2」 新创建一个空白的哈希表，为下次 rehash 做准备。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=OTg4MGFjYWM0MTljN2YwZjg1ZTYzMjBiN2NkNTNhMDJfMDAxYjUwNGZjOTgyYjAzOWJiODUyZGE0ZjI0YzFiNGFfSUQ6NzY0NTI2MjExNDU2NzI2MTE0NF8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

这个过程看起来简单，但是其实第二步很有问题，如果「哈希表 1 」的数据量非常大，那么在迁移至「哈希表 2 」的时候，因为会涉及大量的数据拷贝，此时可能会对  Redis 造成阻塞，无法服务其他请求。

为了避免 rehash 在数据迁移过程中，因拷贝数据的耗时，影响 Redis 性能的情况，所以 Redis 采用了渐进式 rehash，也就是将数据的迁移的工作不再是一次性迁移完成，而是分多次迁移。

渐进式 rehash 步骤如下：

- 给「哈希表 2」 分配空间；

- 在 rehash 进行期间，每次哈希表元素进行新增、删除、查找或者更新操作时，Redis 除了会执行对应的操作之外，还会顺序将「哈希表 1 」中索引位置上的所有 key\-value 迁移到「哈希表 2」 上；

- 随着处理客户端发起的哈希表操作请求数量越多，最终在某个时间点会把哈希表 1 」的所有 key\-value 迁移到「哈希表 2」，从而完成 rehash 操作。

巧妙地把一次性大量数据迁移工作的开销，分摊到了多次处理请求的过程中，避免了一次性 rehash的耗时操作。

在进行渐进式 rehash 的过程中，会有两个哈希表，所以在渐进式 rehash 进行期间，哈希表元素的删除、查找、更新等操作都会在这两个哈希表进行。比如，查找一个 key 的值的话，先会在「哈希表 1」 里面进行查找，如果没找到，就会继续到哈希表 2 里面进行找到。

另外，在渐进式 rehash 进行期间，新增一个 key\-value 时，会被保存到「哈希表 2 」里面，而「哈希表 1」 则不再进行任何添加操作，这样保证了「哈希表 1 」的 key\-value 数量只会减少，随着 rehash 操作的完成，最终「哈希表 1 」就会变成空表。

### Q8\. String 是使用什么存储的?为什么不用 c 语言中的字符串?

我从 "**String 怎么存、SDS 结构、为什么不用 C 字符串**" 来讲。

**首先，****Redis String 是多态的，有三种编码，根据内容自动切换****：**

- 整数用 **int** 编码，直接把整数值存在对象的 ptr 里，省掉字符串开销；

- 字符串不超过 **44 字节**用 **embstr**，RedisObject 对象头和 SDS 放在同一块内存、一次 malloc，更紧凑；

- 超过 44 字节用 **raw**，对象头和 SDS 分开分配、两次 malloc。

其中 embstr 是只读的，一旦做 APPEND 这类修改，**即使还很短也会转成 raw**。

**然后，embstr 和 raw 底层都用 SDS，也就是简单动态字符串，是 Redis 自己实现的，不用 C 原生字符串。** SDS 在字符数组之外加了几个字段：

- **len**：记录字符串长度；

- **alloc**：记录分配的总空间，`alloc − len` 就是剩余空间；

- **flags**：标识 SDS 类型，有 5 种头部（sdshdr5/8/16/32/64），适配不同长度、省元数据；

- **buf\[\]**：实际数据。

**为什么不用 C 字符串？它有三个缺陷，SDS 正好解决：**

第一，C 字符串没有长度字段，`strlen` 要从头遍历到 `\0`，O \(N\)；SDS 有 len，直接返回，O \(1\)。

第二，C 字符串靠 `\0` 判结尾，存不了中间带 `\0` 的二进制数据，比如图片、序列化对象；SDS 用 len 判长度，不依赖 `\0`，**二进制安全**；不过 SDS 结尾还是会补一个 `\0`，用来兼容 C 标准库函数。

第三，C 的 `strcat` 不检查空间，容易缓冲区溢出；SDS 用 `alloc − len` 先算剩余空间，不够会自动扩容，从根上杜绝溢出。



### Q9\. String 的 int、embstr、raw 编码区别

"String 是 Redis 对外的数据类型，而 int、embstr、raw 是它的**三种底层编码**，Redis 会根据存的内容自动选择，客户端无感知。

具体来说：

- **第一种 int 编码**，当值是 long 范围内的整数时使用，Redis 直接把整数值存在 RedisObject 的 ptr 字段里，不需要额外分配内存，最省空间。

- **第二种 embstr 编码**，用于短字符串，阈值是 **44 字节**。它把 RedisObject 对象头和 SDS 分配在**同一块连续内存、一次 malloc**，内存紧凑，还能利用 CPU 缓存；但 embstr 是只读的，没有为它实现修改函数。

- **第三种 raw 编码**，用于超过 44 字节的长字符串，对象头和 SDS **分开分配、两次 malloc**，可以正常修改。

**转换规则**上，只要对字符串做修改，比如 APPEND，embstr 会先转成 raw 再改，即使改完仍然很短也不会转回；int 做 APPEND 会变成字符串编码。

### Q10\. 缓存一个对象，用 String 还是 Hash？

" 两种都可以，我主要看**访问模式 —— 是整体读写，还是频繁操作部分字段**。

**如果对象总是整体返回**，比如商品详情、用户信息，我会用 **String**，把对象序列化成 JSON 存。好处是一次 GET 就能拿到完整结果，代码简单，也方便给整个对象统一设置过期时间。

**如果经常只读写其中几个字段**，比如购物车里某个商品的数量，我会用 **Hash**。可以用 HGET、HSET、HINCRBY 直接操作单个字段，不用每次把整个对象读出来、反序列化、改完再序列化回去，既省开销又直观。

第一，**Hash 不一定比 String 省内存**。小 Hash 用 listpack 编码时确实紧凑，但字段多了转成哈希表之后，字段和节点本身也有开销，最好用 MEMORY USAGE 实际对比。

第二，**过期时间是加在整个 Hash key 上的，不能让单个字段独立过期**，Redis 7\.4 才提供字段级过期，所以要结合版本。

总结就是：**整体读写用 String，部分字段频繁操作用 Hash。**"

## 线程模型

### Q1\. Redis为什么快

> " 我从五个方面回答，最后澄清一个最容易误解的点。
> 
> **第一，纯内存操作，这是最根本的原因。** 数据全在内存，内存随机读写约几十纳秒，而磁盘是几百微秒，差了几个数量级。
> 
> **第二，高效的底层数据结构。** 每种类型都有多种编码、按数据量自动切换：小数据用压缩列表、整数集合，大数据用哈希表、跳表，字符串用 SDS，保证 O \(1\) 或 O \(logN\)。
> 
> **第三，命令执行采用单线程模型。** 这里的单线程指**普通命令由主线程串行执行**，好处是避免多线程的上下文切换、锁竞争和死锁，代码也更易优化。需要说明的是，Redis 的**瓶颈在内存和网络带宽、不在 CPU，所以单线程够用**；但单线程确实无法利用多核，这是它的局限。
> 
> **第四，IO 多路复用。** 基于 epoll 用一个线程同时监听大量连接，只处理就绪的 socket，避免为每个连接建线程。
> 
> **第五，简单的 RESP 协议。** 格式简单、解析快、网络开销小。
> 
> **这里我要特别澄清『Redis 单线程』—— 它不是整个程序只有一个线程：**
> 
> - 一是 Redis 一直有 **BIO 后台线程**，异步处理关闭文件、AOF 刷盘、释放内存，比如删大 key 用 UNLINK 就是交给后台线程；
> 
> - 二是 **Redis 6\.0 引入可选 I/O 多线程**分担网络读写，**但默认关闭，且命令执行仍是单线程**。
> 
> 所以准确说法是：**命令执行单线程，网络 I/O 6\.0 后可多线程，后台还有 BIO 线程。**"
> 
> 

一、**纯内存操作**，这是 Redis 快的根本原因

Redis 所有的数据都存储在内存中，而内存的读写速度比磁盘快几个数量级。磁盘的随机读写速度大概是几百微秒，而内存的随机读写速度只有几十纳秒，差了一万倍以上。

这是 Redis 和 MySQL 最本质的区别：MySQL 是磁盘数据库，大部分操作都需要访问磁盘；而 Redis 是内存数据库，所有操作都在内存中完成，这是 Redis 性能碾压 MySQL 的根本原因。

二、**极致优化的底层数据结构**

Redis 的每一种数据类型都有多种底层编码，会根据数据量的大小自动选择最优的结构：

- 小数据量用压缩列表、整数集合，几乎没有额外开销

- 大数据量用哈希表、跳表，保证 O \(1\) 或 O \(logn\) 的时间复杂度

- 最基础的字符串用 SDS 代替 C 字符串，解决了 C 字符串的所有性能问题

这些数据结构都是专门为 Redis 设计的，比通用数据结构性能高很多。

三、**单线程模型，避免了多线程的所有开销**

这是 Redis 最有特色也最容易被误解的设计。**很多人会问：单线程怎么可能这么快**？

其实恰恰相反，单线程是 Redis 快的最重要原因之一：

- 避免了多线程上下文切换的开销

- 避免了锁竞争、死锁等多线程问题

- 代码更简单，更容易优化，没有多线程的各种坑

而且 Redis 的瓶颈根本不是 CPU，而是内存和网络带宽。单线程完全可以利用现代 CPU 的性能，处理每秒几十万的请求。

四、**IO 多路复用网络模型**

Redis 采用 epoll 实现的 IO 多路复用模型，可以用一个线程同时处理成千上万的网络连接。

简单来说，就是一个服务员同时服务多个顾客，而不是每个顾客一个服务员。这样就避免了为每个连接创建一个线程的巨大开销，大大提高了并发处理能力。

五、**简单高效的 RESP 协议**

Redis 设计了自己的通信协议 RESP，这个协议非常简单，解析速度极快。和 HTTP、JSON 这些复杂的协议相比，RESP 协议的解析开销几乎可以忽略不计。这也是 Redis 网络性能高的重要原因。

### Q2\. Redis哪些地方使用了多线程?

Redis 单线程指的是「接收客户端请求\-\>解析请求 \-\>进行数据读写等操作\-\>发送数据给客户端」这个过程是由一个线程（主线程）来完成的

但是，Redis 程序并不是单线程的，Redis 在启动的时候，是会启动后台线程（BIO）的：

- Redis 在 2\.6 版本，会启动 2 个后台线程，分别处理关闭文件、AOF 刷盘这两个任务；

> Redis 2\.6 版本会启动 2 个 BIO 线程：
> 
> 1. 关闭文件线程：负责异步关闭文件描述符
> 
> 2. AOF 刷盘线程：负责将 AOF 缓冲区的内容异步刷到磁盘
> 
> 

- Redis 4\.0 新增了一个专门的内存回收后台线程，专门解决大键删除阻塞主线程的问题。

> 主线程只做一件事：把要删除的键从键空间中移除，O \(1\) 时间完成
> 
> 然后把真正的内存释放工作交给后台线程去做
> 
> 主线程可以立即返回，继续处理其他请求
> 
> 

- Redis 6\.0 引入了多线程 IO 机制，专门解决网络 IO 瓶颈问题。但设计非常克制：只把网络 IO 操作交给多线程，命令执行仍然是单线程的

> 具体工作流程是：
> 
> 1. 主线程负责监听新连接，当有数据到达时，把 socket 分发给多个 IO 线程
> 
> 2. IO 线程并行读取网络数据，解析 RESP 协议
> 
> 3. 所有 IO 线程完成后，把解析好的命令交给主线程
> 
> 4. 主线程串行执行所有命令，生成响应结果
> 
> 5. 主线程把响应结果分发给 IO 线程，IO 线程并行写回客户端
> 
> 

Redis 的多线程设计非常有智慧，它遵循一个**核心原则**：只把可并行、无状态、不影响命令执行顺序的辅助任务交给多线程，核心命令执行永远保持单线程。

首先是，为什么需要IO多路复用？

> 先看一下传统阻塞 IO 模型的痛点：

>

## 事务

### Q1\. 如何实现redis 原子性？

首先，Redis 原子性的核心本质是**基于单线程命令执行模型的天然原子性**。Redis 的所有数据读写命令都由主线程串行执行，中间不会被任何其他命令打断，这是 Redis 原子性的基础。在此之上，Redis 又提供了事务、Lua 脚本等机制，来保证多个命令的组合操作也具有原子性。

**Redis 的所有单个命令都是原子执行的**，不需要任何额外的机制。

为什么？因为 Redis 的核心命令执行是单线程的。当一个命令开始执行后，直到它执行完成并返回结果，主线程不会处理任何其他命令。中间不会有上下文切换，不会有其他线程修改数据，所以不会出现并发问题。

比如我们最常用的`INCR`命令，它的执行过程是 "读取值→加 1→写回值"，这三个步骤在 Redis 中是一个不可分割的原子操作，即使有 1000 个客户端同时对同一个 key 执行 INCR，也不会出现计数错误的情况。

Redis 中所有的内置命令，包括 GET、SET、DEL、HSET、ZADD 等等，都是原子执行的。这是 Redis 和 MySQL 最大的区别之一：MySQL 的单个 SQL 语句不是原子的，需要加锁或者事务来保证原子性。

当我们需要执行多个命令，并且要求这多个命令作为一个整体要么全部执行，要么全部不执行时，就需要用到 Redis 提供的多命令原子性机制。主要有三种方案：

- Redis 事务（MULTI/EXEC）

> **执行流程**：
> 
> 1. 执行`MULTI`命令，开启事务
> 
> 2. 客户端发送所有要执行的命令，Redis 不会立即执行，而是把它们放到一个队列里
> 
> 3. 执行`EXEC`命令，Redis 会原子地、按顺序执行队列中的所有命令
> 
> 4. 执行完成后，返回所有命令的执行结果
> 
> 

- Lua脚本

Redis 保证**整个 Lua 脚本是原子执行的**。当一个 Lua 脚本开始执行后，直到它执行完成，主线程不会处理任何其他命令。所以我们可以把多个命令和逻辑都写在一个 Lua 脚本里，实现复杂的原子操作。

**优点**：

- 真正的原子性：整个脚本要么全部执行，要么全部不执行

- 支持复杂的逻辑判断和计算，可以在脚本中实现业务逻辑

- 减少网络往返：多个命令一次性发送给 Redis，执行完成后一次性返回结果

- 性能比事务更好

## 日志

### Q1\. Redis有哪2种持久化方式？分别的优缺点是什么？

> "Redis 持久化主要有两种：**RDB 快照和 AOF 日志**，4\.0 之后还有**混合持久化**。
> 
> **先说 RDB。** 它把某一时刻的内存数据，以二进制压缩格式整体存到磁盘。手动触发有 SAVE（阻塞主线程、生产不用）和 BGSAVE（fork 子进程异步生成）；也可配置自动触发，比如 `save 900 1` 表示 900 秒内至少 1 个 key 变化就自动 BGSAVE。
> 
> RDB 优点：**文件紧凑、体积小，适合备份传输；恢复直接加载，通常比 AOF 快很多**。 缺点：**两次快照之间的数据会丢；fork 会短暂阻塞主线程**；快照期间写入频繁时，**写时复制会复制内存页、额外占内存**。
> 
> **再说 AOF。** 它把每条写命令追加到日志，恢复时重放。命令先写到 **aof\_buf 缓冲区，再 write 到 page cache，由 fsync 决定何时真正落盘**。三种刷盘策略：
> 
> - **always**：每条命令都 fsync，最安全、性能最差；
> 
> - **everysec**：每秒 fsync，最多丢约 1 秒，默认推荐；
> 
> - **no**：交给操作系统，丢失风险最大。
> 
> AOF 一直追加会变大，所以有 **AOF 重写**：根据当前内存数据生成最小命令集（100 次 INCR → 一条 SET），由子进程完成。
> 
> AOF 优点：**数据安全性高，everysec 最多丢约 1 秒**；文本可读。 缺点：**文件比 RDB 大、恢复要重放命令较慢；fork 同样短暂阻塞**。
> 
> **最后是混合持久化**，4\.0 引入：AOF 重写时前半用 RDB 写当前数据、后半追加增量命令，恢复时先加载 RDB 再回放命令，兼顾恢复速度和数据安全。
> 
> 选型上，**只做缓存、数据可重建用 RDB；不能丢数据就用 AOF，生产一般开混合持久化**。"
> 
> AOF 重写是根据当前内存数据生成新的持久化内容，不是读取旧 AOF 再逐条合并命令
> 
> 

首先，Redis 持久化的核心本质是**解决内存数据库数据丢失的问题**。因为 Redis 所有数据都存在内存中，一旦服务器断电或进程退出，内存中的数据就会全部丢失。Redis 提供了两种不同的持久化机制：**RDB 快照持久化**和**AOF 日志持久化**，以及两者结合的混合持久化，来将内存中的数据保存到磁盘上，保证数据的持久性。

> - AOF 日志：**追加写日志**；每执行一条写操作命令，就把该命令以追加的方式写入到一个文件里；
> 
> - RDB 快照（默认）：将某一时刻的内存数据，以二进制的方式写入磁盘；
> 
> - 混合持久化：在 AOF 重写时会先以 RDB 的二进制格式写入内存当前状态，然后再把重写期间新收到的写命令以 AOF 的形式追加在后面。重启恢复时先加载 RDB 部分、再回放后续 AOF 命令，既拥有 RDB 快速恢复的特点，又保留了 AOF 低丢失率的优势。
> 
> 

**AOF日志：**

> AOF 的核心是**追加写日志**：将 Redis 执行的所有写命令（SET、DEL、HSET 等）以文本形式追加到 AOF 文件末尾。Redis 重启时，会重放 AOF 文件中的所有命令来恢复数据。
> 
> 

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODkyNGQ3NmFlYjQzNTlhNzRhZTE4MjllMzZlYWNmZmFfYzZiMzg5MjkyOTkzM2Y1MDViNWQ0NTM3NzZkMmM2ODlfSUQ6NzY0NjMzODkxMzQzOTA5MTkwOV8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

AOF 有三种刷盘策略，由`appendfsync`参数控制：

1. **always**：每个写命令执行完立即刷盘，数据绝对不丢失，但性能极差

2. **everysec**：每秒刷盘一次，最多丢失 1 秒的数据，性能良好，是默认推荐的策略

3. **no**：由操作系统决定什么时候刷盘，性能最好，但数据丢失风险最大

**AOF 重写机制**

因为 AOF 是追加写入，文件会越来越大。Redis 提供了 AOF 重写机制来压缩 AOF 文件：

- 遍历内存中的所有数据，生成对应的最小命令集

- 比如对同一个 key 执行了 100 次 INCR，重写后会变成一条`SET key 100`

- 重写也是 fork 子进程异步执行，不会阻塞主线程

> ![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MzA3MDMyMDQ2ZWY3ZGU0ZTczN2I4Mjg2YmM3ODhiNzFfYmM1YTMxOTQyMjQ3NGRiZTg0YjIxNWZmMDQ3MmMxNmRfSUQ6NzcwMTAxODQwMzI5Njg1NzEwOF8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)
> 
> 重写由子进程完成，主进程继续处理请求。那重写期间的新写入怎么办？这里要区分版本。
> 
> - Redis 7\.0 之前：主进程继续写原 AOF，同时把重写期间的增量写入保存到 AOF 重写缓冲区，最后补到新文件，再切换到新 AOF。
> 
> - Redis 7\.0 起：使用多部分 AOF。子进程生成新的 base 文件，主进程把重写期间的变化写到新的 incr 文件，完成后通过 manifest 切换到新的文件组合，减少了旧方案重写缓冲区和补写带来的开销。
> 
> 

**优点**

- **数据安全性高**：默认 everysec 策略最多丢失 1 秒的数据，远好于 RDB

- **文件可读性好**：AOF 是文本文件，可以直接查看和修改

- **适合实时持久化**：每秒刷盘一次，几乎不影响性能

**缺点**

- **恢复速度慢**：需要重放所有命令，数据量大时恢复时间很长

- **文件体积大**：AOF 文件比 RDB 文件大很多

- **AOF 重写会阻塞主线程**：和 RDB 一样，fork 子进程时会短暂阻塞

**RDB快照：**

> RDB 是 Redis 默认的持久化方式，它的核心是**全量快照**：在某个时间点，将 Redis 内存中的所有数据完整地保存到磁盘上的一个二进制文件中（默认文件名是 dump\.rdb）。
> 
> 

**触发方式**

1. **手动触发**：

    - `SAVE`：阻塞主线程执行快照，生产环境绝对不要用

    - `BGSAVE`：fork 一个子进程异步执行快照，主线程继续处理请求

2. **自动触发**：在配置文件中设置 save 参数，比如`save 900 1`表示 900 秒内至少有 1 个 key 发生变化就自动执行 BGSAVE

优点

- **恢复速度极快**：RDB 是二进制文件，加载速度比 AOF 快几个数量级，适合灾难恢复

- **文件体积小**：RDB 是压缩后的二进制文件，占用磁盘空间比 AOF 小很多

- **对性能影响小**：BGSAVE 是子进程执行，主线程几乎不受影响

缺点

- **数据丢失风险大**：RDB 是全量快照，两次快照之间的数据会全部丢失。比如每 5 分钟生成一次快照，如果在第 4 分 59 秒宕机，就会丢失近 5 分钟的数据

- **fork 子进程会阻塞主线程**：当 Redis 内存很大时，fork 操作可能会耗时几百毫秒甚至几秒，导致 Redis 短暂卡顿

- **不适合实时持久化**：频繁生成 RDB 会严重影响性能

**混合持久化：**

- AOF 重写时，先将当前内存中的数据生成 RDB 快照，写入 AOF 文件开头

- 然后将重写期间的所有写命令追加到 AOF 文件末尾

- 恢复时，先加载 RDB 快照，再重放后面的 AOF 命令



### Q2\. 同时开启 RDB 和 AOF，重启时加载哪个？

> 开启 AOF 后，Redis 重启会优先使用 AOF 恢复数据。
> 
> 如果使用混合持久化，AOF 的基础部分本身可能就是 RDB 格式，恢复时先加载这部分，再回放后面的增量命令。Redis 7\.0 的多部分 AOF 则按照 manifest 指定的 base 和 incr 文件顺序恢复。
>

## 缓存淘汰和过期删除

### Q1\. 过期删除策略和内存淘汰策略有什么区别？

```Plain Text
维度一：触发条件不同
  过期删除 ← key 的 TTL 到期（时间驱动，每个 key 各自算）
  内存淘汰 ← used_memory 超过 maxmemory（空间驱动，全局判断）

维度二：作用对象不同
  过期删除 ← 只作用于"设了过期时间"的 key
  内存淘汰 ← allkeys-* 作用于全库；volatile-* 只作用于设了 TTL 的 key

维度三：目的不同
  过期删除 ← 保证"数据不过期可用"，是正确性问题
  内存淘汰 ← 保证"进程不被 OOM kill"，是可用性问题

维度四：互不替代
  没到 maxmemory，过期 key 照样会被删；
  没到期的 key，内存满了照样可能被淘汰。
  所以 noeviction ≠ 关闭过期删除。

```

这两个其实是两个维度的事，我一般从触发条件上区分。

过期删除看的是**时间**：某个 key 的 TTL 到点了，它就该消失，这是每个 key 各自算的，目的是保证数据不会"过期了还能读到"。内存淘汰看的是**空间**：整个实例的 used\_memory 超过 maxmemory 了，我得挑一些 key 扔掉腾地方，目的是别让进程被系统 OOM 掉。

关键在于这两件事**互相不替代**。没到 maxmemory，过期 key 照样会被清；反过来，一个 key 就算还有一小时才过期，内存满了它也可能被淘汰掉。所以 `noeviction` 不等于关掉过期删除，它只是说"内存超了我也不淘汰，直接让写命令报 OOM"。

还有一个线上容易踩的点：如果配了 `volatile-lru` 这类策略，但库里所有 key 都没设过期时间，那它一个都淘汰不了，写入还是 OOM。所以纯缓存场景我一般用 `allkeys-lru` 或 `allkeys-lfu`。

### Q2\. 介绍一下Redis 内存淘汰策略

> 淘汰策略我一般按"范围 × 算法"来记，8 种就很好记了。
> 
> 首先有一个不淘汰的，叫 `noeviction`，这也是 3\.0 之后的默认值。它的行为是：内存超了不删数据，但会让**可能增加内存的写命令**直接返回 OOM，读和删除一般还能用。
> 
> 剩下 7 种都是要淘汰的。先按范围分两类：`allkeys-` 是在全库所有 key 里挑，`volatile-` 是只在**设置了过期时间**的 key 里挑。再按算法分四种：`lru` 是淘汰最久没被访问的，`lfu` 是 4\.0 加的、淘汰访问频率最低的，`random` 是随机，`ttl` 只在 volatile 里有、优先淘汰最快过期的。两两组合，就是 `allkeys-lru`、`volatile-ttl` 这些。
> 
> 选型上，纯缓存我一般用 `allkeys-lru` 或者 `allkeys-lfu`；如果这个实例里还放了分布式锁、库存这种不能丢的数据，我的建议不是换策略，而是**拆实例**，别让它们和缓存抢淘汰池。另外 `volatile-*` 有个坑：如果库里没有带 TTL 的 key，它一个都淘汰不了，写入照样 OOM。
> 
> 线上配的时候，maxmemory 我一般给物理内存的 50% 到 70%，剩下的要留给 fork 的写时复制和复制缓冲区，不能把内存吃满。
> 
> 

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NTE3NzU5YjEzZWMyNzM4ZWQ0YmNjNTE4MmUwY2M5Y2JfOGNkNmRmNmYzNTIwN2MxZGQzN2JkZDA4NjkzZWE3MTNfSUQ6NzY0NjM0MjM5MTUwMzI3NzI0MV8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

- volatile\-lru（Redis3\.0 之前，默认的内存淘汰策略）：淘汰所有设置了过期时间的键值中，最久未使用的键值；

- volatile\-lfu（Redis 4\.0 后新增的内存淘汰策略）：淘汰所有设置了过期时间的键值中，最少使用的键值；



### Q3\. LRU 和 LFU 有什么区别？Redis 是怎么实现的？

> LRU 看"**最近一次**什么时候访问"，LFU 看"**一段时间内**访问了多少次"；Redis 两者都是**近似实现**，靠采样和概率计数，不是精确链表和精确计数。
> 
> 

我先说语义上的区别，再说 Redis 怎么实现的，因为这块的实现跟教科书差别很大。

语义上，LRU 只看"最近一次访问是什么时候"，LFU 看"一段时间内访问了多少次"。举个反例最清楚：一个商品长期是爆款，但最近十分钟没人点；另一个商品一直没人看，刚刚被点了一次。LRU 会觉得后者更新鲜，可能把前者淘汰掉；LFU 会看历史频率，留下前者。所以 LRU 的问题是抗不住偶发访问，LFU 的问题是热点切换时反应慢。

实现上，Redis 的 LRU **不是**教科书那种双向链表。它只在 redisObject 里存一个 24 位的访问时钟，精度到秒。淘汰的时候随机采样 `maxmemory-samples` 个 key，默认是 5 个，从里面挑最久没访问的。3\.0 之后还加了一个淘汰候选池，16 个位置，跨多轮积累，比纯随机采样更接近真实 LRU。所以它是**近似 LRU**，采样越多越准，但 CPU 开销也越大。

LFU 更精巧一点。同样是 24 位，拆成 16 位的时间和 8 位的计数器。计数器不是访问一次加一，是按概率加，频率越高越难加，公式里有个 `lfu-log-factor` 默认 10，这样 8 位就能装下百万级访问的近似值。同时它有衰减，隔一段时间计数器会减，`lfu-decay-time` 默认 1 分钟减 1，所以以前的热点会慢慢掉下去，不会永远占着内存。

我选的时候会看热点稳不稳：商品详情、首页配置这种稳定热点用 LFU；访问模式变化快的用 LRU。不过说到底还是看监控里的命中率，不拍脑袋。

### Q4\. 介绍一下Redis过期删除策略

> Redis 的过期删除是**惰性删除加定期删除**两个配合，我觉得重点不是记住这两个词，而是说清它俩各自解决什么问题。
> 
> 惰性删除是"用到才检查"。每次访问一个 key 之前，会先走 `expireIfNeeded`，发现过期了就当成不存在，读直接返回 nil，同时在主节点上把它删掉。好处是 CPU 特别省，只对还会被访问的 key 付出代价；坏处是如果这个 key 过期之后再也没人碰，它就永远躺在那儿占内存。
> 
> 定期删除就是来兜这个底的。serverCron 每 100 毫秒触发一次，从 expires 字典里**随机抽 20 个**带过期时间的 key，把过期的删掉，如果这一批里过期比例超过 25%，就再来一轮。它不是全表扫，而且有 CPU 时间上限，大概占 25% 左右，慢循环差不多 25 毫秒，快循环 1 毫秒。所以它是"尽量清"，不是"一定清干净"。
> 
> 为什么要两个一起用？只用惰性，内存收不回来；只用定期，要么全扫会阻塞，要么采样漏删。组合起来就是热 key 靠惰性精准清、冷 key 靠定期兜底扫，本质是拿一点内存浪费换 CPU 和延迟。
> 
> 另外过期时间是单独存在 expires 字典里的，存的是绝对毫秒时间戳，不是相对时间。
> 
> 

Redis 选择「惰性删除\+定期删除」这两种策略配和使用，以求在合理使用 CPU 时间和避免内存浪费之间取得平衡。

Redis 的惰性删除策略由 db\.c 文件中的 expireIfNeeded 函数实现

Redis 在访问或者修改 key 之前，都会调用 expireIfNeeded 函数对其进行检查，检查 key 是否过期：

- 如果过期，则删除该 key，至于选择异步删除，还是选择同步删除，根据 lazyfree\_lazy\_expire 参数配置决定（Redis 4\.0版本开始提供参数），然后返回 null 客户端；

- 如果没有过期，不做任何处理，然后返回正常的键值对给客户端；

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NmEwOGRjYWFiMzcyYTY1NTcyOGIyMWRkZmFmNDFhZTVfNDA1YmNlNGNiZTViMjE4ZDYxODQ0NWQzNjUzMmQ1OWNfSUQ6NzY0NjM0NjM0MTAzNTMzMDc2NV8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

Redis 的定期删除是每隔一段时间「随机」从数据库中取出一定数量的 key 进行检查，并删除其中的过期key。

***这个间隔检查的时间是多长呢？****在 Redis 中，默认每秒进行 10 次过期检查一次数据库，特别强调下，每次检查数据库并不是遍历过期字典中的所有 key，而是从数据库中随机抽取一定数量的 key 进行过期检查。*

### Q5\. Redis的缓存失效会不会立即删除？

> 不会。`EXPIRE` 只是往 expires 字典写了一个时间戳，**没有任何定时器**；到期后要等"被访问"或"被定期任务抽到"才真正删除。
> 
> 

不会立即删除。这一点我觉得是理解这块的关键。

你执行 `EXPIRE` 的时候，Redis 只是往 expires 这个字典里写了一个**绝对的时间戳**，它不会给你注册定时器，也不会建一个按时间排序的堆。所以"到点"这个动作本身，Redis 是不知道的，它没有闹钟。

真正删除要等两件事之一发生：要么这个 key 被访问到了，走惰性删除；要么 serverCron 的定期任务正好抽样抽到它。两件都没发生，它就一直在内存里躺着——逻辑上已经死了，物理上还占着。

所以 TTL 严格说是"逻辑过期时间"，不是"物理删除时间"。这带来几个现象：`DBSIZE` 可能比真实有效的 key 多；大量冷 key 集中过期时，内存是缓慢降下去的，不是断崖式；主从架构下从节点还要更晚一点，因为它在等主节点的 DEL 同步过来。

也正因为这样，我们设过期时间一般会加随机抖动，不光是为了防雪崩，也是把删除压力摊开。

### Q6\. 那为什么不在过期时立即删除？

因为"立即删除"这个动作本身很贵，而且贵在三个地方。

第一，要有"闹钟"。要么给每个 key 挂一个定时器，百万级 key 就是百万级定时器，内存和调度都受不了；要么维护一个按过期时间排序的结构，每次改 TTL 都要维护它，而且到期还是集中在同一时刻删，没解决问题。

第二，删除不是免费的。删一个 key 要摘链表、删字典项、释放 value 的内存。如果是个大 key，比如几百万元素的 Hash，释放一次可能几十毫秒，而这几十毫秒里整个 Redis 是卡住的，所有请求都排队。我之前遇到过集中过期把 P99 打穿的情况，就是这个问题。

第三，收益不对等。绝大多数 key 是"过期即冷"，过期之后本来就不会再被访问，你立刻删它，省下的内存很有限，但付出的是主线程可能被阻塞的代价。

所以 Redis 的选择是：不追求"准时删掉"，只保证"逻辑上准时读不到"。把删除成本摊到访问时和定期采样时，这样开销可预测、可限流。如果业务真的要求到点必须失效，那正确做法不是靠 TTL，而是读取的时候判业务时间戳做逻辑过期，或者用 ZSet 做延迟队列。

### Q7\. 已经过期但还没删除的 key，能读到吗？

读不到，但要说清是"哪一层读不到"。

从客户端看，读命令执行前会先走 `expireIfNeeded` 检查，一旦发现过期，就直接当成这个 key 不存在——`GET` 返回 nil，`EXISTS` 返回 0，`TTL` 返回 \-2。所以逻辑上它已经消失了，你读不到。

但从存储上看，它还躺在主字典里，value 还占着内存，要等惰性删除或者定期删除真的把它摘掉。

这个"逻辑上不存在"其实挺重要。比如 `SET NX` 去抢锁，如果锁 key 已经过期但还没被物理删除，`SET NX` 是能成功的，因为 Redis 眼里它就不存在——分布式锁过期后能被别人重新拿到，靠的就是这个。

另外主从这块有个细节：从节点不自己删过期 key，是等主节点删完把 `DEL` 同步过来。所以那个窗口里，从节点的内存释放是滞后的。持久化倒不用担心，RDB 和 AOF 重写都会跳过已过期的 key。

### Q8\. 修改 key 的值，会不会影响过期时间？

这个要分命令看，不能一句话答。

`SET` 这一族是**覆盖整个 key**，它会把原来的过期时间清掉，等于重新创建了一个 key。这是线上特别容易踩的坑：缓存用 `SET` 刷新的时候忘了带 `EX`，这条缓存就永久驻留了，越积越多，最后内存打满，反而把热数据挤出去。Redis 6\.0 之后可以加 `KEEPTTL` 保留原来的过期时间。

另一类是"原地改值"的命令，比如 `INCR`、`APPEND`、`HSET`、`LPUSH`、`ZADD`，它们只动 value，不动 key 的元信息，所以 TTL 是保留的。

还有几个相关的：`RENAME` 之后 TTL 跟着 key 走；`PERSIST` 是主动把 TTL 去掉；`EXPIRE` 再设一次是覆盖，不是累加。

所以实际项目里我一般会封装一个统一的方法，默认带 TTL，避免有人手写 `SET` 漏掉。如果对象需要频繁改局部字段，用 Hash 会更自然，因为 `HSET` 不会影响 TTL。

## 集群

### Q1\. Redis主从同步中的增量和完全同步怎么实现？

#### 完全同步：

完全同步发生在以下几种情况：

- **初次同步**：当一个从服务器（slave）首次连接到主服务器（master）时，会进行一次完全同步。

- **从服务器数据丢失**：如果从服务器数据由于某种原因（如断电）丢失，它会请求进行完全同步。

- **主服务器数据发生变化**：如果从服务器长时间未与主服务器同步，导致数据差异太大，也可能触发完全同步。



主从服务器间的第一次同步的过程可分为三个阶段：

- 第一阶段是建立链接、协商同步；

- 第二阶段是主服务器同步数据给从服务器；

- 第三阶段是主服务器发送新写操作命令给从服务器。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODE5MjQ0N2UwNzc2YTM3Y2Q0ZTU0ZWJlNmNmZjllMzlfNmM4YTY1ZjM2ZjZjZDFlM2ZkN2E0NjYyNDlmNGJmMGZfSUQ6NzY1NTI1OTgyODg1NjA5NzcyMl8xNzkzMjU0MDQ4OjE3OTMzNDA0NDhfVjM)

实现过程：

1. 从服务器发送SYNC命令：从服务器向主服务器发送`SYNC`命令，请求开始同步。

2. 主服务器生成RDB快照：接收到`SYNC`命令后，主服务器会保存当前数据集的状态到一个临时文件，这个过程称为 RDB 快照

3. 传输RDB文件：主服务器将生成的RDB文件发送给从服务器。

4. 从服务器接收并应用RDB文件：从服务器接收RDB文件后，会清空当前的数据集，并载入RDB文件中的数据。

5. 主服务器记录写命令：在RDB文件生成和传输期间，主服务器会记录所有接收到的写命令到`replication backlog buffer`。

6. 传输写命令：一旦RDB文件传输完成，主服务器会将`replication backlog buffer`中的命令发送给从服务器，从服务器会执行这些命令，以保证数据的一致性。



#### 增量同步：

增量同步允许从服务器从断点处继续同步，而不是每次都进行完全同步。它基于`PSYNC`命令，使用了运行ID（run ID）和复制偏移量（offset）的概念。

### Q2\. 什么是RocketMQ？

RocketMQ 是一个开源的分布式消息中间件，由阿里巴巴开发并贡献给 Apache 软件基金会。它主要用于高吞吐量、低延迟的消息传递需求。

RocketMQ 的优点和功能是比较多的，以下是 一些主要特点和功能：

- 高吞吐量和低延迟：RocketMQ 设计用于处理大量的消息，并提供低延迟的消息传递服务，适合需要高性能的场景。

- 分布式架构：RocketMQ 使用分布式架构来支持大规模的消息传递。它可以水平扩展，以处理更大的数据量和更高的并发需求。

- 消息可靠性：RocketMQ 支持消息持久化和多副本机制，确保在系统故障时不会丢失消息。这使得消息的可靠性和一致性得到了保障。

- 高可用性和容错：RocketMQ 提供了高可用性的解决方案，包括多主多从等架构方案，确保系统的稳定性和连续性。

#### 削峰填谷：
