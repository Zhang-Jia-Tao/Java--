高频问题
Q1.TCP三次握手的过程以及为什么是三次?
面试官您好,TCP三次握手是为了建立可靠的端到端连接,本质是双方确认彼此的收发能力正常并协
商初始序列号。
第一次握手客戶端发送SYN报文,携带自己的初始序列号;

<!--p57-->

优化补充:ISN(InitialSequenceNumber)必须随机生成,原因有两个:1防止旧连接的数据包
被新连接误认为是合法数据(同一四元组的不同连接);2防止序列号被预测,避免伪造报文的安
全攻击(如TCP序列号预测攻击)。
第二次握手服务器回复SYN+ACK报文,携带自己的初始序列号并确认客戶端的序列号;
第三次握手客戶端再回复ACK报文确认服务器的序列号,此时双方都进入连接建立状态。
之所以是三次而不是两次,最主要的原因是防止已失效的连接请求报文导致服务器错误建立连接,浪
费资源。同时三次也是确认双方收发能力正常的最小次数,而四次则没有必要,因为服务器可以将
SYN和ACK合并在一个报文中发送
优化补充:
•
握手前:客戶端 CLOSED →发SYN→ SYN_SENT 
•
服务端收到SYN: LISTEN →发SYN+ACK→ SYN_RCVD 
•
客戶端收到SYN+ACK:发ACK→ ESTABLISHED 
•
服务端收到ACK: ESTABLISHED 
Q2.TCP四次挥手的过程以及为什么是四次?
TCP四次挥手是为了安全地终止全双工连接,本质是双方各自关闭自己的发送通道。
第一次挥手主动关闭方发送FIN报文,表示自己没有数据要发送了;
第二次挥手被动关闭方回复ACK确认,此时主动方向的连接关闭,但被动方向还可以继续传输数据;
第三次挥手被动关闭方发送完所有数据后,也发送FIN报文表示自己也没有数据要发送了;
第四次挥手主动关闭方回复ACK确认,双方最终关闭连接。
之所以是四次而不是三次,最核心的原因是TCP是全双工协议,被动关闭方收到FIN时可能还有数据
要发送,所以不能立即发送FIN,必须先回复ACK,等数据发送完再发送FIN,这两个步骤无法合并。
另外,主动关闭方最后会进入TIME_WAIT状态等待2MSL时间,这是为了确保最后一个ACK能到达
对方,同时防止旧连接的报文干扰新连接。
优化补充:MSL(MaximumSegmentLifetime)是报文的最大存活时间,Linux默认是60秒,所
以TIME_WAIT持续120秒。选择2MSL的原因是:如果最后一个ACK丢失,被动方会重发FIN,主
动方需要能在这段时间内收到并重新回复ACK,一来一回最坏情况就是2MSL。
Q3.TCP和UDP的区别?
TCP和UDP是传输层的两个核心协议,它们的本质区别在于设计目标不同。TCP是面向连接的可靠传
输协议,提供确认应答超时重传、序列号、拥塞控制和流量控制机制,保证数据可靠有序地到达,但
传输速度较慢,开销较大。UDP是无连接的不可靠传输协议,不提供可靠性保证,但传输速度极快,
开销极小,实时性好。
•
可靠性:TCP通过序列号+确认应答+超时重传保证数据不丢失不乱序;UDP不保证,可能丢
包、重复、乱序

<!--p58-->

•
传输方式:TCP是字节流,无消息边界(需要处理粘包);UDP是数据报,保留消息边界
TCP适用于对数据完整性要求高的场景,比如文件传输、网叶浏览和电子邮件;UDP适用于对实时性
要求高的场景,比如视频通话、直播和在线游戏。另外,现在很多新的协议比如QUIC是基于UDP实
现的,它在应用层增加了可靠性机制,结合了两者的优点。
Q4.TCP的流量控制和拥塞控制
TCP流量控制和拥塞控制是TCP可靠传输的两大核心机制。流量控制解决的是端到端的速度匹配问
题,通过滑动窗口协议防止发送方发送过快导致接收方缓冲区溢出;拥塞控制解决的是全局网络的拥
塞问题,通过慢启动、拥塞避免、快速重传和快速恢复四个算法,动态调整发送方的发送速率,防止
过多数据注入网络导致网络性能下降。
优化补充:
•
慢启动:连接建立初始cwnd=1MSS,每收到一个ACK,cwnd加1,呈指数增长,直到达到慢
启动阈值(ssthresh)
•
拥塞避免:cwnd超过ssthresh后,每个RTT只加1MSS,线性增长,探测网络上限
•
快重传:收到3个重复ACK时立即重传丢失报文,不必等待超时(超时重传代价极大,cwnd会
归1)
•
快恢复:快重传后将ssthresh设为当前cwnd的一半,cwnd从新ssthresh开始线性增长,避免
从头慢启动
流量控制的核心是接收窗口rwnd,拥塞控制的核心是拥塞窗口cwnd,发送方的实际发送窗口大小是
两者的最小值。现在主流的拥塞控制算法是CUBIC和BBR,其中BBR基于带宽和延迟来判断拥塞,
在高速网络中性能更好。
"为什么慢启动初始cwnd是1,现在实际上是多少?"

<!--p59-->

RFC6928(2013年)将初始cwnd从1提升到10MSS,主要是因为现代网络带宽已经大幅提升,
初始cwnd=1在高延迟高带宽链路上启动太慢(每次RTT才翻倍),10MSS是经过大量真实网络数
据统计得出的更合适的初始值。
"HTTP/1.1keep-alive和拥塞控制有什么关系?"
TCP连接复用(keep-alive)能让连接保持在拥塞避免的线性增长阶段,避免每次新建连接都要重新
经历慢启动。这也是HTTP/1.1相比HTTP/1.0性能大幅提升的原因之一。
Q5.token,session,cookie的区别?
Cookie是客戶端存储的小文本,每次请求自动带,但有4KB限制和CSRF风险;Session是服务端存
储、有状态,安全但分布式要Redis共享;Token是无状态的JWT签名令牌,天然支持分布式跨域,
但签发了就不能主动失效、Payload不加密。
1)Cookie:服务器通过响应头下发给浏览器、由浏览器保存的一小段文本数据。
原理(四步工作流):
1 用戶首次访问 → 服务器在响应头 Set-Cookie: user=zhang; Max-Age=86400 
2 浏览器收到 → 保存到本地(按域名存) 
3 后续每次请求 → 浏览器自动在请求头 Cookie: user=zhang 带上 
4 服务器读取 Cookie → 识别用戶 
大小限制:约4KB;数量有限;同源限制(不能跨域携带)。
本质定位:Cookie只是一个存储载体,它本身不含"你是谁"的判断逻辑——它存的可能是
SessionID,也可能是Token。
2)Session:服务端存储的会话档案(接待员的台账)
服务器端保存的用戶会话信息。服务器创建Session对象,生成唯一SessionID作为"钥匙",通过
Cookie发给客戶端。
原理(四步工作流):
1 用戶登录成功 → 服务器创建 Session 对象(存内存 /DB ),生成唯一 Session ID 
2 服务器通过 Set-Cookie: JSESSIONID=xxx 把 Session ID 发给浏览器 
3 浏览器自动带 Cookie → 服务器拿 Session ID 查 Session 
4 查得到 → 已登录;查不到 → 未登录 
核心特点:
•
有状态:身份信息在服务端,客戶端只拿一把"钥匙"(SessionID);
•
更安全:敏感信息不暴露给客戶端,SessionID泄露也只是钥匙(配合过期);
•
占用服务端内存:Session多了要清理(内存泄漏问题,后面GC讲过);

•

(约50个);4容易被CSRF攻击利用(浏览器自动携带)
它们最核心的区别在于状态性:Session是有状态的,服务器需要维护会话信息,适合传统单体应用;

Q7.HTTP和HTTPS的区别?
关于HTTP和HTTPS的区别,我从核心本质、七大核心维度对比、HTTPS完整握手流程、核心安全
机制、常见误区和实际开发应用六个方面来回答:
首先,两者的核心本质和设计目标完全不同。HTTP是明文传输的超文本传输协议,诞生于1991年,
设计目标是快速、简单地传输超文本数据,没有任何安全机制;HTTPS是HTTP+SSL/TLS的安全超文

本传输协议,在HTTP和TCP之间增加了一层SSL/TLS加密层,设计目标是解决HTTP明文传输的安
全问题,保证数据传输的机密性、完整性和身份认证。简单来说:HTTPS就是穿了"安全外套"的
HTTP。
接下来是两者最核心的七大维度对比,这也是面试必背内容:
然后是HTTPS的完整握手流程,这是面试的核心考点。HTTPS的安全建立在SSL/TLS握手之上,以
TLS1.2为例,完整握手分为四个步骤:
1. 客戶端发送ClientHello:客戶端向服务器发送支持的TLS版本、加密套件列表和一个随机数
ClientRandom
2. 服务器返回ServerHello:服务器选择双方都支持的TLS版本和加密套件,返回服务器随机数
ServerRandom和数字证书
3. 客戶端验证证书并生成预主密钥:客戶端验证证书的合法性,验证通过后生成一个随机的预主密钥
Pre-MasterSecret,用服务器公钥加密后发送给服务器
4. 双方协商生成会话密钥:客戶端和服务器分别用ClientRandom、ServerRandom和Pre-Master
Secret生成相同的会话密钥,之后所有通信都使用这个对称会话密钥加密
整个握手过程只需要两次往返,完成后就进入加密通信阶段。
接下来是HTTPS的三大核心安全机制,这也是它能够保证安全的根本原因:
1. 机密性:通过对称加密算法(AES)加密传输的数据,即使被截获也无法解密
2. 完整性:通过哈希算法(SHA-256)生成消息摘要,防止数据在传输过程中被篡改
3. 身份认证:通过数字证书(含公钥、域名、有效期、CA签名)和非对称加密算法(RSA)验证服务
器的身份,防止中间人攻击
加密防"看"(窃听)、摘要防"改"(篡改)、证书防"假"(冒充)。
这里我想重点讲一下对称加密和非对称加密的配合使用:非对称加密速度慢,只用来加密传输预主密
钥;对称加密速度快,用来加密实际的业务数据。两者结合,既保证了安全性,又兼顾了性能。

然后是常见误区部分,我想澄清三个非常常见的错误认知:第一,很多人以为HTTPS会严重影响性

假证书,仍然会有安全风险;第三,很多人以为只要用了HTTPS就不需要其他安全措施了,其实
HTTPS只能保证传输层的安全,应用层的安全问题(比如SQL注入、XSS)仍然需要单独处理。
Q8.HTTPS握手过程说一下
关于HTTPS握手过程,我从核心本质、TLS版本演进、TLS1.2完整握手流程、TLS1.3重大改进、核
心安全机制、常见误区和实际开发应用七个方面来回答:
首先,HTTPS握手的核心本质是SSL/TLS协议的安全通道建立过程。它的核心目标是在不安全的公共
网络上,通过非对称加密、对称加密和数字证书技术,协商出双方都认可的加密算法和唯一的会话密
钥,同时验证服务器的真实身份,最终建立一个机密、完整、可认证的加密通信通道。所有HTTPS通
信都必须先完成TLS握手,才能传输业务数据。
接下来是TLS协议的版本演进,这是面试必考点。TLS是SSL的继任者,目前主流使用的是两个版
本:
•
TLS1.2:2008年发布,是目前兼容性最好的版本,绝大多数网站和浏览器都支持,也是过去十年
的工业标准
•
TLS1.3:2018年发布,是最新的稳定版本,握手延迟降低了50%,安全性大幅提升,移除了所有
不安全的加密算法,现在已经成为主流浏览器和服务器的默认版本

<!--p65-->

•
更早的SSL3.0、TLS1.0、TLS1.1都存在严重的安全漏洞,已经被所有主流浏览器废弃,生产环
境必须禁用
然后是面试必考的TLS1.2完整握手流程,整个过程需要2次RTT(往返时间),分为四个清晰的阶
段:
第一阶段:客戶端发起握手请求(ClientHello)
客戶端向服务器发送握手请求,包含以下核心信息:
1. 客戶端支持的最高TLS版本号
2. 客戶端支持的加密套件列表(按优先级排序)
3. 客戶端生成的第一个随机数: Client Random 
第二阶段:服务器响应握手(ServerHello)
服务器收到请求后,返回响应信息,包含以下核心内容:
1. 双方协商确定的TLS版本号(取双方都支持的最高版本)
2. 从客戶端列表中选择的加密套件
3. 服务器生成的第二个随机数: Server Random 
4. 服务器的数字证书(包含服务器公钥、域名、有效期、CA签名等信息)
5. 服务器HelloDone消息,表示服务器端的Hello阶段结束
第三阶段:客戶端验证证书并发送密钥材料
客戶端收到证书后,首先进行严格的证书验证:
1. 验证证书是否由可信的CA机构签发
2. 验证证书的域名是否与当前访问的域名一致
3. 验证证书是否在有效期内
4. 验证证书是否被吊销
验证通过后,客戶端生成第三个随机数: Pre-Master Secret (预主密钥),用服务器公钥加密
后发送给服务器。
Pre-MasterSecret是整个密钥体系的"核心秘密"
1 Client Random :客戶端发 Client Hello 时明文带上 → 服务器看到了 ✓ 
2 Server Random :服务器回 Server Hello 时明文带上 → 客戶端看到了 ✓ 
3 Pre-Master Secret:客戶端生成后,用【服务器公钥】加密发出 
 → 只有服务器用【私钥】能解开 → 服务器拿到 ✓(中间人拿到也解不开)

接下来是TLS1.3的重大改进,这是现在面试的热点问题。TLS1.3对握手流程进行了革命性的优化:
1. 握手延迟减半:从TLS1.2的2次RTT减少到1次RTT,大幅提升了叶面加载速度
2. 0-RTT握手:对于已经建立过连接的客戶端,可以直接发送加密的业务数据,不需要等待握手完成
3. 安全性大幅提升:移除了所有不安全的加密算法和密钥交换方式,只保留了5个安全的加密套件
4. 简化握手流程:合并了多个握手消息,减少了网络传输量
这里我想重点讲一下三个随机数的作用:为什么需要三个随机数而不是一个?因为如果只用一个随机
数,一旦这个随机数被破解,整个会话的密钥就会被破解。使用三个独立的随机数,分别由客戶端和
服务器生成,即使其中一个被破解,也不会影响整个会话的安全性,极大地提高了密钥的随机性和不
可预测性。
然后是常见误区部分,我想澄清三个非常常见的错误认知:第一,很多人以为握手过程中会传输会话

的双向认证第三,很多人以为TLS1.3的0-RTT握手是绝对安全的,其实0-RTT存在重放攻击的风
险,不能用于传输敏感数据
最后是实际开发中的应用。在项目中,我会严格遵循HTTPS的最佳实践:

3. 配置证书自动续期,避免证书过期导致服务不可用
4. 开启会话复用(SessionTicket),减少重复握手的开销

Q9.RPC和HTTP有什么区别?
RPC是设计思想、HTTP是协议
HTTP更像是对外暴露接口的通用方式,RPC更像是服务内部互相调用的方法调用方式。先说HTTP,
HTTP本质上是一种应用层通信协议,平时写的接口,例如用戶登录、查询订单、提交订单等都是通过
HTTP完成的,它的特点是通用性强,跨语言、跨平台、跨系统都很方便,比如前端调用后端,浏览器
访问服务器,等都会使用HTTP,因为接入成本低,易于调试;再说RPC,全称远程核心调用,它的核
心目标是:让你调用远程服务,就像调用本地方法一样,无需关心底层怎么建立连接、怎么序列化、
怎么传输、怎么拿返回值,这些事情RPC框架会帮我们进行封装。
那他们最大的区别是什么?
"最核心的区别是使用场景——对外用HTTP,对内用RPC。对外看重通用性和兼容性,HTTP用
JSON可读性好、跨语言;对内看重性能和治理,RPC用高效序列化体积小,框架自带负载均衡、熔
断、服务发现。一句话:对外用HTTP接口,对内用RPC调用,本质是通用性vs性能治理的取
舍。"
1. 使用场景不同,HTTP更适合对外接口,比如开放平台、前后端交互、第三方系统对接;RPC更适
合内部服务调用,比如微服务之间的调用;对外接口更看重通用性和兼容性,内部调用更看重性
能、治理能力和开发体验
2. 调用方式不同,HTTP通常是面向资源的,比如查询用戶,就是访问用戶相关接口,它强调的是我
对某个资源做什么操作;而RPC,更像是面向方法的,比如查询库存方法,它强调的是,我调用远
程服务里的某个函数,所以RPC写起来更像是本地方法调用
3. 数据传输方式不同,HTTP的数据传输方式常见是JSON,JSON的优点是可读性好,调试方便,缺
点是体积相对大,解析成本高;而RPC框架通常会使用更高效的序列化方式,优点是传输体积小,
解析速度快,缺点就是可读性没那么强,在内部调用场景下,RPC往往性能更好
4. 服务治理能力不同,普通HTTP调用,本身只是一次请求和响应,如果想做负载均衡、熔断、限
流、重试、服务发现、链路追踪通常要额外接入网关、注册中心或者中间件,而成熟的RPC框架往
往就会集成这些能力,这也是微服务内部选择RPC的原因
