## fw-01 · 雪花算法与分布式 ID 生成

### 一句话

分片之后自增主键不再全局唯一，分片表主键必须在应用层生成；雪花把 64 位切成「1 符号 + 41 时间戳 + 10 机器 + 12 序列」，靠时间戳单调加机器号隔离来保证不撞；时钟回拨是它唯一的硬伤。

### 展开

64 位布局：
```text
| 0 | 41 位时间戳(ms) | 10 位 workerId | 12 位 sequence |
```
仓库里的三处用法：
```java
// 分片表主键：应用层生成，避免各分表自增撞号
UserCouponDO userCouponDO = UserCouponDO.builder()
        .id(IdUtil.getSnowflakeNextId())
        ...
// 批次号：要跨表、跨服务唯一
couponTaskDO.setBatchId(IdUtil.getSnowflakeNextId());
```
DDL 里的兜底声明（实际被应用层覆盖）：
```sql
`id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
```
一句话总结：分片表用雪花保全局唯一，单库单表继续用自增，别把两者混成一句「主键是雪花」。

### 源码依据

- `distribution/src/main/java/com/nageoffer/onecoupon/distribution/mq/consumer/CouponExecuteDistributionConsumer.java` · 分片表主键用雪花（L241）—— 用户券要落到 2 库 32 表，自增主键必然撞号，所以在应用层生成

- `merchant-admin/src/main/java/com/nageoffer/onecoupon/merchant/admin/service/impl/CouponTaskServiceImpl.java` · 批次号用雪花（L119）—— batch_id 要跨表、跨服务唯一（失败记录也按它关联），不能靠单表自增



### 要点

1. 分片后各分表自增 ID 会冲突，主键要在应用层生成
2. 64 位切分：1 + 41 + 10 + 12
3. 容量推导：4096/ms × 1000 ≈ 409 万/秒/节点，41 位约 69 年
4. 趋势递增对 B+ 树友好（不是随机 ID）
5. 时钟回拨的三种处理策略
6. 本仓库用 Hutool，没有自研雪花实现
7. 三种 ID 策略并存：自增主键 / 雪花主键 / 雪花批次号
8. workerId 怎么分配（代码里由 Hutool 默认推导，仓库未显式配置）

### 坑与边界

- 把「主键都是雪花」当事实——t_coupon_task 的主键是数据库自增，只有分片表主键和 batch_id 用雪花。
- 说雪花绝对不重复——时钟回拨会重复，必须显式处理。
- 只背 41/10/12 三个数字，说不清为什么这样切（时间粒度、节点规模、单机 QPS）。
- 不知道 10 位机器号常再拆成 5 位数据中心 + 5 位机器，也不提 workerId 冲突检测。
- 把 DDL 里的 AUTO_INCREMENT 当成实际策略，从而和代码里的雪花赋值自相矛盾。

### 关键数字

- 时间戳位数：41 位（约 69 年）
- 机器号位数：10 位（1024 节点）
- 序列位数：12 位（4096/毫秒）
- 单节点理论上限：≈409 万/秒
- 仓库取值方式：Hutool IdUtil.getSnowflakeNextId()

### 追问

**为什么不用 UUID？**

UUID 是随机无序的，作为聚簇索引主键会让 B+ 树频繁页分裂，插入变慢且索引碎片多；另外 32 字符占空间、可读性差。雪花是长整型且趋势递增，正好对症。

**workerId 冲突会怎样？**

同一毫秒、同一机器号、同一序列就会生成完全相同的 ID。所以机器号必须全局唯一，生产上通常由配置中心或启动时抢占注册来分配，Hutool 默认按 MAC/进程推导，多实例部署要显式指定。

**时钟回拨你会怎么处理？**

小幅回拨自旋等待追平；大幅回拨直接抛异常拒绝服务，绝不出重复 ID；同时把上次生成的时间和机器号持久化，重启时先校验。业务侧可以配合重试或降级到号段模式。

**号段模式和雪花怎么选？**

号段（Leaf/数据库批量取号）不依赖时钟，没有回拨问题，但依赖发号服务且 ID 不连续递增；雪花无中心、趋势递增，但要处理时钟与机器号。量大且能接受中心化发号时号段更稳。


## fw-02 · 两个线程池的参数差异：一个能丢，一个不能丢

### 一句话

两个池都用 SynchronousQueue 不排队，差别在饱和策略：行数统计可补算所以直接丢；提醒发送丢了用户就收不到通知，所以回退到调用线程同步执行，把压力反压回上游。

### 展开

后管：统计行数，丢了可补算
```java
private final ExecutorService executorService = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().availableProcessors() << 1,
        60, TimeUnit.SECONDS,
        new SynchronousQueue<>(),
        new ThreadPoolExecutor.DiscardPolicy()
);
```
engine：发提醒，丢了用户就收不到
```java
private final ExecutorService executorService = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors() << 1,
        Runtime.getRuntime().availableProcessors() << 2,
        60, TimeUnit.SECONDS,
        new SynchronousQueue<>(),
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```
对照：
```text
            核心 / 最大          队列               饱和策略      丢了会怎样
行数统计    核数 / 2×核数        SynchronousQueue   Discard       下次发送时重算
提醒发送    2×核数 / 4×核数      SynchronousQueue   CallerRuns    用户收不到提醒
```

### 要点

1. 两池参数对比：核心/最大/存活时间/队列/拒绝策略
2. 都用 SynchronousQueue，等于不排队
3. 无界队列（Executors 默认）会在堆里堆积直到 OOM
4. 线程数差异来自 IO 等待比例，不是随手写的
5. DiscardPolicy 的前提是任务可补算（代码注释写明）
6. CallerRunsPolicy 是反压上游，会拖慢提交线程
7. 为什么倍数选 2 而不是更激进（等待时间占比的量化）

### 坑与边界

- 说 CallerRunsPolicy「性能更好」——它会让调用线程被占用，是牺牲吞吐换不丢。
- 把 DiscardPolicy 说成 bug 或失误——它是基于「可补算」做的有意选择。
- 只对比拒绝策略，不看队列类型；其实 SynchronousQueue 才是两池共同的防 OOM 设计。
- 不知道行数统计可补算这条代码注释，导致理由只能靠猜。

### 关键数字

- 行数统计池核心线程：availableProcessors()
- 行数统计池最大线程：availableProcessors() << 1
- 提醒池核心线程：availableProcessors() << 1
- 提醒池最大线程：availableProcessors() << 2
- 空闲存活：60 秒（两池一致）

### 追问

**为什么不用 Executors 工厂方法？**

工厂方法的队列和拒绝策略是写死的：newFixedThreadPool 和 newSingleThreadExecutor 都是无界 LinkedBlockingQueue，任务堆积时会一直涨到 OOM；也拿不到有意义的线程名。手写 ThreadPoolExecutor 才能把队列、策略、线程名都定下来。

**CallerRunsPolicy 在 MQ 消费线程里会不会出问题？**

会有影响：消费线程被拿去执行任务，消费速度下降，Broker 侧堆积甚至触发消费超时重投。所以一般要么在独立的线程池里提交，要么配合限流，避免把消费线程全部占满。

**IO 密集型为什么是 2N 而不是更大？**

线程数上限取决于「等待时间 / 计算时间」的比值：纯 IO 可以到 2N 甚至更高，但线程越多上下文切换和栈内存占用越大，而且下游（数据库、邮箱服务）本身有承载上限，堆线程数只是把压力挤到下游。

**既然可补算，为什么还留线程池，不直接同步算？**

同步算会把创建任务的接口拖到 4~5 秒，用户体验差；异步算即使丢一次，也只是晚一点有数，不阻塞主流程。这是「把非关键路径挪出去」的标准做法。


## fw-03 · 注解 + AOP 的两个真实切面：防重锁与 MQ 幂等

### 一句话

注解只声明意图（message、key 表达式、超时），切面负责把声明变成动作：SpEL 把方法参数拼成唯一 key，再用 Redis 做「第一次进入」的判定，最后按业务成功或异常决定保留、改写还是删除这个标记。

### 展开

Lua 原子占位（GET 后 SET NX PX）：
```java
private static final String LUA_SCRIPT = """
        local key = KEYS[1]
        local value = ARGV[1]
        local expire_time_ms = ARGV[2]
        local old = redis.call('GET', key)
        if old then
            return old
        end
        redis.call('SET', key, value, 'NX', 'PX', expire_time_ms)
        return nil
        """;
```
key 由前缀加 SpEL 拼成，三态分支决定放行 / 重投 / 空跑：
```java
String uniqueKey = noMQDuplicateConsume.keyPrefix() + SpELUtil.parseKey(
        noMQDuplicateConsume.key(), method, joinPoint.getArgs());

if (Objects.nonNull(absentAndGet)) {
    if (IdempotentMQConsumeStatusEnum.isError(absentAndGet)) {
        throw new ServiceException(...);   // 消费中 → MQ 重投
    }
    return null;                            // 已消费 → 空跑
}
result = joinPoint.proceed();
stringRedisTemplate.opsForValue().set(uniqueKey, CONSUMED.getCode(), keyTimeout, TimeUnit.SECONDS);
// catch 分支：delete(uniqueKey); throw ex;
```


### 要点

1. 注解声明 + 切面增强 + SpEL 拼 key 的三层结构
2. 防重切面：path + userId + 参数 MD5，tryLock 非阻塞
3. MQ 幂等切面：Lua 原子 GET / SET NX PX
4. 三态分支：空放行、消费中重投、已消费空跑
5. 成功后改已消费、异常删 key（幂等闭环）
6. SpEL 只在含 # 或 T( 时解析，否则当字面量
7. Lua 传毫秒、成功写状态用秒，单位不一致
8. Redis 不可用时切面的降级语义（放行还是拒绝）

### 坑与边界

- 把 MQ 幂等说成「key 存在就丢弃」——存在还要看状态，消费中要抛异常让 MQ 重投，只有已消费才空跑。
- 讲防重只说加锁不说 key 怎么拼，被问「两个用户同时提交会互相挡吗」会哑。
- 忘了异常删 key，等于一次失败就把消息永久锁死。
- 把 tryLock 说成性能优化——真正理由是 Web 请求要快速失败、不能排队。
- 宣称 Redis 挂了也不影响——切面里 Redis 报错就是直接抛异常，业务得自己有兜底。

### 关键数字

- 防重 key 组成：path + currentUserId + 参数 MD5
- MQ 幂等状态值：CONSUMING(0) / CONSUMED(1)
- Lua 占位命令：GET → SET NX PX（毫秒）
- 成功状态写入：SET key CONSUMED，过期时间按秒

### 追问

**为什么要用 Lua，不能 GET 之后再 SET NX 吗？**

两条命令之间有窗口：两个消费者可能同时 GET 到空，然后都去 SET NX，其中一个成功、另一个被 NX 挡住——虽然 SET NX 本身能兜住，但「读到的旧状态」和「写入的判定」不在一个原子操作里，语义容易说不清。放一段脚本里，判定和写入就不可分割了。

**返回「消费中」为什么要抛异常而不是直接丢弃？**

丢弃等于这条消息永远不处理了；抛异常会让 MQ 按重试策略延迟重投，等上一条处理完、key 过期或改成已消费之后，重投就能正常进入。这是「宁可慢一点，不能漏」。

**key 的过期时间怎么定？**

要覆盖「消息重投的最长间隔」：太短会在重投窗口内失效、失去幂等；太长占内存。一般取业务重试窗口的上限，比如 10 分钟到 1 小时。代码里是通过注解的 keyTimeout 配的。

**SpEL 直接解析用户输入会不会有安全问题？**

有风险。这里的表达式来自代码里的注解常量，不是用户输入，所以可控；如果表达式来自外部配置，就要限制可用的类和方法（T() 能调静态方法），否则等于远程代码执行。


## fw-04 · 缓存一致性：删缓存、延迟双删与 binlog 订阅

### 一句话

双写必然有窗口，区别只在窗口里读到什么、能不能自愈；通用答案是「先更新库再删缓存」，但本项目更彻底——写库为准、binlog 驱动重建缓存，再加写后复核兜住 Redis 丢写。

### 展开

四种策略的窗口与代价：
```text
策略          窗口期问题                        代价
更新缓存      并发写顺序颠倒，旧值覆盖新值       很难判断谁更新
先删后更      删完未更时读请求回填旧值           旧值可能被固化
先更后删      删除失败时缓存短暂脏               最常用，窗口最小
延迟双删      覆盖主从延迟期间的旧值回填         多一次删除，要估延迟
binlog 重建   有同步延迟                         最彻底，天然可重放
```
binlog 驱动写缓存 + 写后复核：
```java
stringRedisTemplate.opsForZSet().add(userCouponListCacheKey, userCouponItemCacheKey, receiveTime.getTime());
Double scored = stringRedisTemplate.opsForZSet().score(userCouponListCacheKey, userCouponItemCacheKey);
if (scored == null) {
    // Redis 主从同步或持久化丢写，补写一次
    stringRedisTemplate.opsForZSet().add(userCouponListCacheKey, userCouponItemCacheKey, receiveTime.getTime());
}
```
写入路径可切换（binlog 与非 binlog 二选一）：
```java
if (ObjectUtil.notEqual(userCouponListSaveCacheType, "binlog")) {
    return;
}
```

### 要点

2. 删缓存 vs 更新缓存：删除避免并发覆盖
3. 先更后删优于先删后更（后者会固化旧值）
4. 延迟双删解决主从延迟期间的旧值回填
5. 本项目以库为准 + binlog 驱动重建 + 写后复核
6. 缓存写入路径可切换（binlog / 应用内主动写）
7. 为什么能接受最终一致（错误方向可选 + 唯一索引兜底）
8. 仓库里没有延迟双删的实现，属于通用方案讨论

### 坑与边界

- 把延迟双删说成「我们项目实现了」——仓库里只有 binlog 同步加写后复核，没有双删代码。
- 只讲「先删缓存再更新库」的流程，不讲它会固化旧值这个致命窗口。
- 忽略「更新缓存」的问题：并发写时无法判断谁的值更新，容易留下旧值。
- 宣称缓存和数据库强一致——这套方案本质是最终一致，要敢说取舍。
- 不提缓存穿透/击穿是另一套防护（布隆 + 空值 + 锁），混在一起讲会显得乱。

### 关键数字

- 缓存结构：ZSet（score = 领取时间戳）
- 复核方式：写后 score 查一次，为空补写
- 延迟双删的延迟量：按主从延迟估（通常几百毫秒）

### 追问

**先更后删，删除失败怎么办？**

靠 TTL 兜底：缓存最终会过期，过期后回源重建；同时可以把删除做成重试消息，失败进重试队列。强一致的场景光靠这套不够，得上订阅 binlog 或分布式事务。

**为什么不用更新缓存而用删除？**

更新缓存要解决「用谁的值更新」：两个并发写，后到的可能基于旧读算出新值，缓存里留下的是旧结果；而且很多写场景缓存里根本没有这个 key，更新等于白做。删除把重建时机交给读路径，逻辑单一。

**Canal 同步有延迟，用户领完券立刻查不到怎么办？**

这就是两条写入路径并存的原因：主链路落库后自己写一次缓存（快），binlog 路径负责补偿和重建（准）。追求「写完立刻可查」时用前者，追求「最终一定对」时靠后者。

**延迟双删的第二次删除延迟多久合适？**

要覆盖「主从延迟 + 那次读请求的回填耗时」，通常几百毫秒到一秒；准确的量级要靠监控主从延迟（Seconds_Behind_Master）来定，拍一个固定值在高负载时会失效。

### 追问

**EasyExcel 为什么比 POI 省内存？**

POI 的 XSSF 会把整个工作簿解析成对象树放在内存里，百万行必然 OOM；EasyExcel 基于 SAX 逐行解析 XML，只在内存里保留当前行的模型对象，配合监听器就能做到常数级内存。

**无界队列除了 OOM 还有什么问题？**

延迟不可控：任务排在队尾，用户等很久才执行；也拿不到「被拒绝」的信号，无法反压上游。有界队列加合理拒绝策略至少能把压力显式暴露出来。

**堆 dump 怎么定位这三类？**

看 dominator tree 里占比最高的对象：如果是某个 ArrayList 里几百万个实体，就是全量读/大结果集；如果是大量 FutureTask/Runnable，就是队列堆积；再配合 GC 日志看 Full GC 后是否回收，能区分泄漏与瞬时峰值。

**游标分批时数据被并发修改会不会漏？**

会。游标依赖字段单调且不被回改，如果这期间有记录被改小 id 或删插，可能漏或重。导出这类场景通常接受「近似快照」，要么加时间上界过滤，要么在低峰执行。


## fw-07 · 幂等的三种实现：锁、MQ 状态机、唯一索引

### 一句话

三种幂等解决三个层面的重复：注解加锁挡「短窗口内重复请求」，MQ 状态机挡「消息重投」，数据库唯一索引兜「业务上只能发生一次」；前两层是优化，最后一层才是正确性保证。

```text
消息层      注解 + Lua 消费状态机          MQ 重投 / 并发消费      key 过期或 Redis 故障
存储层      联合唯一索引                   业务上只能一次         违反即异常，需业务处理
```


### 坑与边界

- 把三种幂等当成「任选其一」——它们覆盖的重复窗口完全不同。
- 说唯一索引冲突「先查再插更稳妥」——那是在代码里制造竞态，索引本身就是原子判定。
- 忽略分库分表后唯一约束只在单分片内生效，索引里不带分片键就不是全局唯一。
- MQ 幂等只讲「key 存在就跳过」，不讲消费中要抛异常重投。
- 宣称加了锁就一定幂等——锁释放后的重复提交挡不住。

### 关键数字

- 请求层 key：path + currentUserId + 参数 MD5
- 消息层状态：CONSUMING(0) / CONSUMED(1)
- 唯一索引列：user_id + coupon_template_id + receive_count

### 追问

**为什么唯一索引比「先查再插」可靠？**

先查再插是 check-then-act，两个并发都能查到「不存在」然后都去插；唯一索引把判定放进存储引擎的一次写入里，第二个必然失败。代价是要处理异常，而不是拿到一个干净的 false。

**分库分表后唯一索引还有效吗？**

只在单分片内有效。本项目按 user_id 分片，索引里也包含 user_id，同一用户的记录必然落在同一分片，所以约束仍然是全局的——这是「分片键进唯一索引」的经典用法。

**三种都上会不会过度设计？**

看重复的代价。券这种真金白银的业务，重复发券的损失远大于三层判断的成本；如果只是普通写操作，加个唯一索引或乐观锁就够了。原则是「按错误的代价选防护层数」。

**Redis 挂了，防重和 MQ 幂等会怎样？**

切面里会抛异常，等于拒绝服务——对券业务这是安全侧失败（宁可不发也不错发）。要提升可用性就得降级到「唯一索引兜底 + 限流」，接受更强的数据库压力。


## fw-10 · 分布式锁：Redisson 到底怎么实现的

### 一句话

锁本体是一个 Hash：field 是「客户端 UUID:线程 ID」、value 是重入次数；拿锁用 Lua 保证判断与写入原子，不传租期时看门狗每 10 秒续一次 30 秒租期，所以 lock 会一直等、tryLock 立刻失败。

### 展开

锁的数据结构（Redisson 源码语义）：
```text
KEY   coupon_template_lock:{templateId}
      ├─ field = 8f3a...uuid:98   value = 2   ← 该线程重入 2 次
      └─ field = 8f3a...uuid:104  value = 1
      TTL   = 30s（未指定 leaseTime 时由看门狗每 10s 续期）
```
加锁 Lua 的逻辑骨架（原子判断 + 重入 + TTL）：
```lua
if (redis.call("exists", KEYS[1]) == 0) then
    redis.call("hincrby", KEYS[1], ARGV[2], 1)
    redis.call("pexpire", KEYS[1], ARGV[1])
    return nil
end
if (redis.call("hexists", KEYS[1], ARGV[2]) == 1) then
    redis.call("hincrby", KEYS[1], ARGV[2], 1)   -- 本线程重入
    return nil
end
return redis.call("pttl", KEYS[1])               -- 别人的锁，返回剩余时间
```
本项目两种用法对照（同一个 RLock API，语义完全不同）：

```java
lock.lock();
try {
    // 双重判定 + 查库 + 回填缓存
} finally {
    lock.unlock();
}

// ② 快速失败：创建结算单 / 防重复提交
RLock lock = redissonClient.getLock(String.format(EngineRedisConstant.LOCK_COUPON_SETTLEMENT_KEY, couponId));

    throw new ClientException("正在创建优惠券结算单，请稍候再试");
}
```

1. 锁本体是 Hash：field=UUID:threadId，value=重入次数
2. 加锁是 Lua 脚本，判断与写入原子
3. 可重入靠 field 里的线程标识 + 计数加减
4. 看门狗：默认 30 秒租期、每 10 秒续期，仅无参 lock 生效
5. lock 阻塞无限等 / tryLock 立即失败，选择看业务语义
6. 红锁：多独立 master 过半成功，代价大且有争议
7. 锁分片对单 key 唯一资源无效（等于放弃互斥）
8. 显式传 leaseTime 会关闭看门狗，可能业务未完成锁先释放

10. 单实例主从切换可能丢锁，为何可接受

### 坑与边界

- 把 Redisson 锁说成 SETNX——它是 Hash + Lua，否则没法做可重入。
- 说看门狗「永远续期」——它只在持有者活着时续，进程挂了 30 秒后释放；而线程卡死时确实会一直续。
- 以为 lock() 可以设超时——无参 lock 是无限等，要超时必须显式传 leaseTime（但会关掉看门狗）。
- 把锁分片当成万能优化：单 key 唯一资源场景拆锁等于没有互斥。
- 声称用了红锁——本项目是单实例，没有 RedLock 实现。

### 关键数字

- 看门狗默认租期：30 秒（lockWatchdogTimeout）
- 续期周期：租期的 1/3 ≈ 10 秒
- Redisson 版本：3.27.2
- 本项目传 leaseTime 处：0 处（全走看门狗）
- 本项目 isHeldByCurrentThread 守卫：0 处

### 追问

**看门狗续期是怎么实现的？**

加锁成功后注册一个 Netty 时间轮任务，每 1/3 租期执行一次：判断当前线程是否仍持有锁，是就 pexpire 重置为 30 秒；unlock 时取消该任务。所以它续的是「租期」不是「永久」。

**业务线程死循环了，锁会一直不释放吗？**

会。看门狗只判断持有关系，不判断业务是否卡住，线程活着就一直续期。所以无参 lock 适合短临界区，长任务应该显式传 leaseTime 并自己做幂等保护。

**主从切换会丢锁吗？**

会。主节点加锁成功还没同步到从节点就宕机，从节点升主后其他人可以再拿到锁。RedLock 试图解决这个问题但代价大且有争议；对可重试的业务（缓存重建、防重）通常接受这个风险。

**为什么 unlock 要判断 isHeldByCurrentThread？**

如果锁因为超时/被删已经不是自己的，直接 unlock 会抛 IllegalMonitorStateException，也可能误删别人的锁。本项目没用这个守卫，属于可改进点。

**Redisson 锁和 SETNX + 过期时间比，强在哪？**

三处：可重入（Hash 计数）、安全释放（按 UUID:threadId 判断归属，不会删别人的锁）、自动续期（看门狗解决「业务没跑完锁过期」）。自己用 SETNX 这三样都要手写。

### 追问

**异步刷盘和同步刷盘怎么选？**

看能接受丢多少。异步刷盘（默认）性能高，宕机可能丢最后几百毫秒；同步刷盘每条都落盘才返回，吞吐下降明显但更稳。金融类通常同步刷盘 + 同步复制。

**消费失败重试 16 次后怎么办？**

进死信队列（%DLQ%topic），需要人工处理或补偿任务重放。生产上要监控死信堆积量，否则消息悄悄死在队列里没人知道。

**为什么消费端一定要幂等？可靠性不是保证不丢吗？**

保证不丢的代价就是「至少一次」，失败重投、超时重投都会让同一条消息被消费多次。所以可靠性和幂等是配套的：不丢靠重试，不重靠幂等。

**生产端为什么不加重试？**

盲目重试可能放大问题（Broker 抖动时重试加剧拥塞），而且重试失败仍需兜底。本项目选择快速失败 + 日志告警 + 人工/补偿重投，牺牲自动化换取链路简单，这条取舍要能讲出来。

**延时消息和普通消息在可靠性上有区别吗？**

都走同步发送、都返回 SendResult，可靠性机制一致；区别在 Broker 侧延时消息需要定时投递，时间精度和堆积策略不同，但同样遵循至少一次投递，所以消费端幂等一样要做。

**为什么不做本地消息表？**

**唯一索引为什么带 receive_count？**

业务允许同一张券领多次（不同轮次），所以不能只对 user_id + template_id 唯一；把领取次数纳入，等于约束「第 N 次只有一条」。这也是限领规则的落点。

**Redis 预扣成功但落库失败，账怎么平？**

会少卖（Redis 少一张、库里还有）。可以靠定时校准把库存补回，或下次活动前重置；相比超卖，少卖是可接受方向——这条取舍要主动讲。

**TCC 的三个坑是什么？**

空回滚（try 没到就来了 cancel）、幂等（confirm/cancel 可能重复）、悬挂（cancel 先于 try 到达）。要引入事务控制表记录状态才能防住，所以TCC 的成本主要在业务改造和异常分支。

**Canal 方案的一致性怎么保证？**

它保证最终一致而不保证实时：binlog 解析 + MQ + 消费有秒级延迟。要有位点管理和顺序消息，读侧再做一层兜底（如写后复核），否则会出现用户刚领完查不到券的窗口。


## fw-13 · 限流与降级：算法、Sentinel、以及本项目的空白

### 一句话

四种算法解决不同问题：固定窗口有临界突刺、滑动窗口更平滑、漏桶恒定速率削峰、令牌桶允许突发；熔断是保护依赖、降级是兜底业务，而本仓库只有网关日志 Filter，Sentinel 未落地。

### 展开

四种算法的核心差异（背这张表就够）：
```text
固定窗口   : 按自然窗口计数，实现最简单，边界可放 2 倍流量
滑动窗口   : 细分时间格 / ZSet 存时间戳，平滑，内存与计算↑
漏桶       : 恒定速率流出，超量排队/丢弃，削峰但引入延迟
令牌桶     : 按速率放令牌 + 桶容量，允许突发，限平均速率
```
Sentinel 流控 vs 熔断（两条正交的能力）：
```text
流控 rule : 阈值类型 QPS / 线程数
```

- 把熔断和降级当同一件事：熔断是自动触发的保护，降级是业务给的兜底。
- 只知道令牌桶，讲不出固定窗口的临界突刺问题。

### 追问

**为什么单机限流不够，还要网关限流？**

单机阈值乘以实例数会被扩容放大，而且挡不住针对整个集群的攻击流量；网关层可以按 IP/用户做统一配额，代价是多一跳网络和状态存储（通常用 Redis）。

**QPS 阈值和线程数阈值怎么选？**

下游是快接口用 QPS 更直观；下游变慢时 QPS 不变但线程被占满，此时线程数阈值能更早保护自己。生产上常见组合：QPS 做常态限流，线程数做兜底。

**预热（Warm Up）解决什么？**

应用刚启动时缓存冷、连接池空、JIT 未优化，直接放满流量容易雪崩。预热让阈值从低到高爬升，给系统升温时间，大促前滚动发布尤其需要。

**半开状态为什么必要？**

熔断打开后如果一直不探测，依赖恢复了也不知道。半开就是放少量请求试探：成功则关闭恢复流量，失败则继续打开。没有半开，熔断就变成永久下线。

**本项目要补限流，最小改动是什么？**

网关引入 Sentinel 适配做接口级 QPS 限流 + Redis 令牌桶做用户维度配额；应用内给核心接口加 @SentinelResource 并用统一 blockHandler 做降级返回。先量测再定阈值，别拍脑袋。

### 追问

**为什么审计日志不复用技术日志？**

技术日志会采样、会按容量滚动删除，而且内容是非结构化的；审计要求字段固定（操作人、业务主键、改前改后）、可 SQL 查询、保留期长。同一条链路里两者的生命周期完全不同，混在一起两头都不满足。

**@LogRecord 的 SpEL 拿不到运行时生成的 ID 怎么办？**

在方法体里 LogRecordContext.putVariable 手动塞，比如 bizNo。这是 bizlog 的标准用法，因为注解在方法执行前就要生成日志模板。

**审计落库失败要不要影响业务？**

不该影响。项目里 catch 后只 log.error。理由是把审计做成强依赖等于让「记日志」反过来拖垮下单，可用异步写或本地消息补偿提高可靠性，但不能阻塞主流程。

**错误码为什么用字符串 A000001 而不是数字？**

前缀能表达归属，前端按 A/B/C 分类处理（提示用户、提示重试、提示稍后）；纯数字没有语义，只能靠范围约定，扩展时容易冲突。

**traceId 怎么做全链路透传？**

网关生成放 MDC 并写进请求头，下游用 Filter/拦截器读头再放 MDC，日志格式里带上 %X{traceId}；异步线程和线程池要显式传递，否则会丢。用完必须 remove，否则线程复用会串号。
