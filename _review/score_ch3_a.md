## ② 逐题点评

### 3-0 JVM 内存模型(JMM) 和运行时内存结构有什么区别 —— 72 分（及格）

- **得分**：A36 / B16 / C10 / D8 / E2
- **必答点核对**：
  - 两个维度区分（"内存存在哪里" vs "多线程如何安全访问内存"）✅ 这是本题最该先说的一句话，说对了
  - 主内存 / 工作内存抽象、读写必须经过工作内存、线程间不能互访 ✅
  - 三性（原子 / 可见 / 有序）✅，且各自给了保证手段 ✅
  - volatile 内存屏障四类 ❌ 只报了名字（StoreStore/StoreLoad/LoadLoad/LoadStore），**没有一条解释"禁止哪种重排"**，也没说屏障插入的完整链条
  - happens-before 八条 ⚠️ 只说"最常用的有"，实际只点到 6 条（程序次序、锁定、volatile、线程启动、线程终止、传递性），**缺线程中断规则、对象终结规则**，**final 字段规则完全没提**
  - final 内存语义 ❌ 只在"可见性"里塞了 `final` 一个字，没有"构造器内写 final 字段 HB 于引用赋值"这层
  - 运行时内存结构这一侧 ❌ 只有"堆、栈、方法区"三个词，**五区划分、线程私有/共享、元空间替代永久代**一个都没展开 —— "区别题"只答对了一半
  - 对比维度 ❌ 少了"是否 JMM 规范强制 / 是否线程私有 / 是否有 OOM / 是抽象还是物理"这几栏

- **硬伤**：**严格意义上无硬伤**（结论层没有说反、没有编造）。但有 1 处**位置表述不严谨，必被追问**，单独标注：
  - 原文："在 volatile **读操作前后**会插入 LoadLoad 和 LoadStore 屏障" → 正确说法：**读侧两个屏障都在 volatile 读之后**（LoadLoad 禁止"后面的普通读"越过 volatile 读，LoadStore 禁止"后面的写"越过 volatile 读），**读之前不插任何屏障**；写侧才是"写前 StoreStore、写后 StoreLoad"（原文写侧顺序是对的）。另需补一句：**x86 是 TSO 模型，实际只落地 StoreLoad（`lock addl $0x0,(%rsp)` / `mfence`），另外三种由编译器屏障消除**。
  - 似是而非："可见性通过 volatile、synchronized 和 **final** 保证" → 更准确：final 给的是**构造完成后的正确发布（初始化安全）**，属 HB 的 final 字段规则，不是通用可见性开关；说成三件套并列会让面试官顺着问"final 保证什么可见性"。

- **扣分点**：
  - A-4：上述屏障插入位置含糊 + final 语义被降级成"可见性关键字"。
  - B-9：happens-before 八条只到 6 条且自称"最常用"（这是回避，不是省略）；运行时数据区五区完全没答；无对比表格（rubric 三.5 按内容缺失处理）。
  - C-10：全篇无一处触及硬件根源（CPU 缓存 / store buffer / 编译器重排三源）、无 as-if-serial、无 JSR-133 的"旧内存模型为什么失败（允许 final 字段值改变）"、无 DCL 单例这个最经典落地。**"为什么需要 JMM"只说了"保证跨平台一致"，没说清"不保证会怎样"**。
  - D-2：四个方面结构清晰、可直接说出口，但结尾戛然而止，没有一句话收束；且缺表格，面试里这种题**表格比段落有效**。
  - E-3：零项目锚点，只有一个"volatile 不保证原子性"的误区澄清在撑亮点。

- **可加分但没说的**：
  1. 一句话点透：**"JMM 是规范，运行时数据区是实现"**；工作内存不是栈、主内存不是堆，前者覆盖寄存器/L1-L2/写缓冲，后者对应物理内存。
  2. `count++` 的坑补一句"用 `AtomicInteger` 或 `LongAdder`（分段 CAS，高并发下更优）"，立刻显得不是背的。
  3. DCL 单例：`instance = new Singleton()` 的三步（分配 → 初始化 → 赋值）重排 → 必须 `volatile`，这是 volatile 有序性唯一的"现场证据"。
  4. `synchronized` 一次性给全三性（原子 + 可见 + 有序），比"原子性靠它、可见性靠它、有序性靠它"分三处复读更有说服力。
  5. "主内存/工作内存"是 JMM 的**抽象模型**——把它当成真实分层（有人答"主内存是堆、工作内存是栈"）是本章最高频的错误答案，主动说破即加分。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **"工作内存就是虚拟机栈、主内存就是堆吗？"** → 不是：主内存/工作内存是 JMM 的**抽象概念**，工作内存覆盖 CPU 寄存器、L1/L2 缓存和写缓冲（store buffer），主内存对应物理内存，堆栈只是运行时数据区在这块物理内存上的分配，二者不是一一映射。
  2. **"HB 除了你列的还有哪几条？final 字段的 HB 规则怎么表述？"** → 还缺**线程中断规则**（`interrupt()` 先于被中断线程检测到中断）和**对象终结规则**（`finalize()` 先于对象回收）；final 字段规则是"构造器内对 final 字段的写入 HB 于把该对象引用赋给其他变量"，所以**构造器里 `this` 逃逸**会破坏初始化安全。
  3. **"x86 上 volatile 到底编译成什么？四种屏障真的都插了吗？"** → 只有 **StoreLoad** 是真指令（`lock` 前缀 / `mfence`），代价最大；LoadLoad/LoadStore/StoreStore 在 x86 的 TSO 下天然成立，JIT 直接省略；所以"volatile 慢"主要慢在这条全屏障上。

- **改法（可直接替换进稿子的段落）**：
  > "两者是**规范 vs 实现**的关系，不能混为一谈。运行时数据区是 JVM 规范对内存的物理划分：线程私有的程序计数器、虚拟机栈、本地方法栈，线程共享的堆和方法区（JDK8 起由元空间实现，用本地内存）；它回答'对象和栈帧放在哪'。JMM 则是一套**抽象的并发访问规范**，回答'多线程读写共享变量时，什么结果是被允许的'——为此它定义了主内存/工作内存的抽象（工作内存并不是栈，而是寄存器、CPU 缓存和写缓冲的统称，主内存也不是堆，而是物理内存），并用 synchronized 保证原子性、volatile/synchronized/final 保证可见性、volatile/synchronized 加 HB 规则保证有序性。需要注意的是运行在 x86 上时，四种屏障里只有 StoreLoad 真正落地，其余三种靠编译器屏障消除。"

### 3-2 CMS 和 G1 垃圾回收器的区别 —— 62 分（不合格）

- **得分**：A30 / B14 / C8 / D8 / E2
- **必答点核对**：
  - CMS 四阶段（初始标记 / 并发标记 / 重新标记 / 并发清除）✅，且点明**只有初始标记、重新标记两处 STW** ✅
  - CMS 三缺点（CPU 敏感 / 浮动垃圾 / 标记清除碎片）✅
  - CMS 是**老年代收集器、必须与 ParNew/Serial 这类新生代收集器组合**（"分代组合式"）❌ 完全没提，这是 CMS 最基础的定位
  - **Concurrent Mode Failure** + `CMSInitiatingOccupancyFraction`（默认约 68%，未显式设置时 JVM 自适应）❌ 缺失，而"碎片 + 浮动垃圾"在面试里必须由 CMF 收口
  - **三色标记 + 增量更新（incremental update）** ❌ 缺失，CMS 全部原理都挂在这上面
  - G1 Region 化、Humongous ✅（但 Humongous 判定口径不精确，见硬伤 3）
  - G1 四阶段（初始标记 / 并发标记 / 最终标记 / 筛选回收）✅，但**G1 的 STW 点（初始标记、最终标记、筛选回收的疏散）没标清**
  - **SATB**（G1 的并发标记漏标处理）❌ 缺失
  - **Young GC / Mixed GC 两种回收模式、`-XX:InitiatingHeapOccupancyPercent`（默认 45%）触发并发周期** ❌ 缺失
  - "可预测停顿" ⚠️ 说成"通过参数指定最大停顿时间"（详见硬伤 1）
  - "G1 整体标记-整理、局部（Region 间）复制" ✅ **这个口径是对的，是本篇最值钱的一句**
  - "G1 自 JDK9 起为默认" ✅
  - CMS JDK9 废弃（JEP 291）/ JDK14 移除（JEP 363）❌ 缺失（详见硬伤 2）
  - 记忆集 / RSet / 卡表 / 写屏障（G1 跨 Region 引用的开销来源）❌ 缺失
  - "G1 适合 >8GB 属经验值" ✅ **没有编数字，这点没踩坑**，值得肯定

- **硬伤**（2 处，故本题封死 90+，A 项扣到底）：
  1. **原文**："G1 可以通过 `-XX:MaxGCPauseMillis` 参数**指定最大停顿时间**，实现可预测的停顿。"
     **正确说法**：`MaxGCPauseMillis`（默认 200ms）是**期望目标（soft goal），不是硬上限、不保证**。G1 用"衰减均值 + 各 Region 回收收益/成本"的停顿预测模型，在这个预算内**尽量多选** Region；设得过小会导致每次只能回收极少 Region，回收速度追不上分配速度 → 并发周期频繁甚至退化为 Full GC，**实际停顿反而更长**。正确表述是"G1 提供**可预期的**停顿模型（pause prediction），目标是让停顿可控，而不是承诺上限"。
  2. **原文**：全篇用现在时给 CMS 推荐适用场景（"CMS 适合堆内存适中、对延迟要求极高的应用，比如 Web 服务器和电商系统"），只字不提 CMS 的命运。
     **正确说法**：**CMS 在 JDK9 被废弃（JEP 291），JDK14 被移除（JEP 363）**，JDK14+ 已无法启用（`-XX:+UseConcMarkSweepGC` 直接报错）。现代面试的正确开场是"先说结论：CMS 已死，今天讨论它只有两个意义——理解并发标记的演进、以及在老 JDK8 系统上维护/迁移"。
  3. **（不计硬伤，标注为"似是而非"）原文**："每个 Region 可以是 Eden、Survivor、Old 或者专门存储大对象的 Humongous Region。"
     **正确说法**：Region 的**角色只有 Eden / Survivor / Old 三种**；Humongous 不是第四种角色，而是"用途"——**单个对象 ≥ Region 大小的一半（50%）时**，会占用**连续的一个或多个 Region**以 Humongous 方式分配，逻辑上归属老年代；找不到连续 Region 时会直接触发 Full GC。
  4. **（不计硬伤，标注为"似是而非"）原文**："G1 会计算各个 Region 的**回收价值**。"
     **正确说法**：价值 = **可回收空间 ÷ 预计回收耗时**（garbage collection efficiency），不是单纯的空间大小；这就是"Garbage First"的字面含义，也是它能在停顿预算内挑 Region 的依据。

- **扣分点**：
  - A-10：1 处机制性硬伤（停顿目标当上限）+ 1 处版本过时（CMS 生命周期），按 rubric 各扣 ≥8 的部分合并计。
  - B-11：缺 CMS 的老年代定位与组合方式、CMF、三色标记+增量更新、SATB、Mixed GC、CMS 废弃/移除，共 6 个"考官必问"级别的点。**这 6 个里任意被抽中一个，答案就断在这里。**
  - C-12：全篇没有一行触及底层——无三色标记（黑/灰/白、漏标的两个条件、读写屏障）、无 SATB vs 增量更新的取舍（SATB 保守不漏但多浮动垃圾，增量更新精确但要重扫 dirty card）、无 RSet/卡表（G1 每次 YGC 都要扫 RSet，这是 G1 的固定开销，也是堆小时不如 Parallel 的原因）、无 Region 大小（1~32MB、2 的幂、目标约 2048 个 Region）、无 TAMS 指针。属于典型"只背结论"。
  - D-2：四个方面框架清楚、有对比，但"关键差异"只给内存模型/算法/停顿三条，**缺并发标记算法（增量更新 vs SATB）、记忆集、回收粒度（整代 vs Region）、Full GC 行为（单线程 Serial Old 退化 vs 并行 Full GC）、触发条件（占用率 68% vs IHOP 45%）**这几个真正的对比维度；结尾"我主要使用 G1，通过调整最大停顿时间参数来平衡延迟和吞吐量"是空话，而且踩在自己的硬伤上。
  - E-3：项目锚点只有一句"我主要使用 G1"，无堆大小、无版本、无 GC 日志指标、无切换前后对比，等于没有。

- **可加分但没说的**：
  1. 一句话记忆锚："**CMS 是'老年代 + 标记清除 + 增量更新'，G1 是'整堆 Region + 标记整理 + SATB + 停顿模型'"**——四个词把两道题串起来。
  2. G1 的退路：JDK10 之前 Full GC 会退化成**单线程 Serial Old**（大堆上是灾难），JDK10+（JEP 307）改为并行 Full GC —— 这是"G1 到底能不能上生产"的关键判断点。
  3. 选型结论："堆 < 4~6GB、追求吞吐用 Parallel；6GB 以上、要控延迟用 G1（经验值，看的是停顿目标和对象晋升速率，不是堆大小本身）；极致低延迟（<10ms）才轮到 ZGC/Shenandoah"——把"8GB"说成经验值而不是规范。
  4. CMS 的可调参数三件套：`CMSInitiatingOccupancyFraction` + `UseCMSCompactAtFullCollection` + `CMSFullGCsBeforeCompaction`，一个参数对应一个缺点，结构极漂亮。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **"CMS 为什么会 Concurrent Mode Failure？"** → 并发清理速度跟不上分配速度（老年代占用越过 `CMSInitiatingOccupancyFraction`，默认约 68%）或碎片导致晋升失败时，CMS 来不及并发收集，只能**退化为单线程 Serial Old 做整堆 Full GC**，停顿直接上一个数量级。
  2. **"CMS 和 G1 分别怎么解决并发标记的漏标？为什么选择不同？"** → 漏标有两个条件（黑→白引用被断开、白对象又被黑对象重新引用）；**CMS 用增量更新**（写屏障记录被改写的引用，重新标记时以这些引用为根重扫，精确但重扫成本高），**G1 用 SATB**（写屏障把**旧值**压进队列，按标记开始时的快照标记，不漏标但保守、多浮动垃圾）——G1 选 SATB 是因为它要在并发标记后靠 Mixed GC 精挑 Region，宁可多点垃圾也要让标记更快结束。
  3. **"把 MaxGCPauseMillis 设成 5ms 会怎样？"** → 不会真的 5ms：G1 只能少选 Region，回收跟不上分配，并发周期频繁甚至 Full GC，停顿反而更长；正确做法是设一个**可接受的**值（默认 200ms），然后看 GC 日志里 actual pause、humongous allocation failure、evacuation failure 来调。

- **改法（可直接替换进稿子的段落）**：
  > "先给版本结论：**CMS 在 JDK9 被废弃（JEP 291）、JDK14 被移除（JEP 363）**，G1 自 **JDK9** 起成为默认收集器。两者的本质差异是四条：一是**内存布局**，CMS 是严格连续分代、且只负责老年代（必须配 ParNew），G1 是整堆切成约 2048 个 1~32MB 的 Region，Eden/Survivor/Old 在物理上不连续；二是**并发标记的漏标处理**，CMS 用**增量更新**、G1 用 **SATB**（写前快照，靠写屏障记旧值，宁可多浮动垃圾也不漏标）；三是**处理方式**，CMS 标记-清除，不移动对象所以有碎片，最终靠 CMF 退化 Full GC，G1 整体标记-整理、Region 间复制，碎片问题基本消失但要多付 RSet/写屏障的开销；四是**停顿可控性**，CMS 完全不可预测，G1 用 `-XX:MaxGCPauseMillis`（默认 200ms）作为**期望目标**，靠停顿预测模型在预算内挑'回收收益 ÷ 回收耗时'最高的 Region——注意它是 soft goal，不是保证，设得过小反而会退化成 Full GC。"

### 3-3 双亲委派是什么、有啥用 —— 68 分（不合格）

- **得分**：A31 / B17 / C9 / D8 / E3
- **必答点核对**：
  - 核心思想（向上委托、向下加载；父加载不了才自己加载）✅
  - 三层结构 + 各自加载范围 ✅（但版本口径错误，见硬伤 1）
  - Bootstrap 由 C++ 实现、`getClassLoader()` 返回 null ✅
  - 自定义类加载器继承 `ClassLoader`、重写加载逻辑 ✅
  - 三大作用（安全防篡改 / 避免重复加载 / 类隔离）✅ 三条都在，且 `java.lang.String` 的例子举得对
  - 破坏场景：SPI + **线程上下文类加载器 TCCL**（JDBC）✅、Tomcat（Webapp 优先本地）✅、OSGi（网状）✅、**热部署** ⚠️ 只在最后"实际应用"里提了自定义类加载器，没有归入"破坏场景"清单
  - "双亲是组合不是继承，内部持有 parent 引用" ✅ 这是本篇最好的一句
  - **loadClass 三步**（`findLoadedClass` → parent → `findClass`）❌ 只有行为叙述，没有方法级流程，也没提"父加载器找不到是返回 null，不是抛异常"
  - **ClassNotFoundException vs NoClassDefFoundError** ❌ 只提了前者，后者一个字没有
  - 重写 `findClass`（保留双亲委派）vs 重写 `loadClass`（才破坏委派）的区别 ❌ 缺失，这是自定义类加载器唯一的正确姿势
  - JDK9 模块化对委派的影响 ⚠️ 无（模块化后 Boot 加载 java.base 等、Platform 加载平台模块）

- **硬伤**（1 处，版本精度问题，恰好是面试官最爱问的那一句）：
  1. **原文**："第二层是扩展类加载器 Extension ClassLoader，负责加载 JRE 扩展目录下的类库。"
     **正确说法**：**JDK9 起（JEP 261 模块化），ExtClassLoader 已被 PlatformClassLoader（平台类加载器）取代**，`jre/lib/ext` 扩展目录被取消，平台类加载器负责加载 `java.sql`、`java.xml` 等**平台模块**；委派链变成 **Bootstrap → Platform → App**。原文按 JDK8 口径陈述且未标注版本，在今天（主流程 JDK17/21）是错误信息。若目标 JDK 明确是 8，可保留 Ext 的说法，但**必须点明"JDK8 及以前"**。
  2. **（不计硬伤，标注为"似是而非"）原文**："同一个类只会被同一个类加载器加载一次，**保证了 JVM 中类的唯一性**。"
     **正确说法**：类的运行时唯一性 = **加载它的 ClassLoader 实例 + 全限定名**（命名空间）；双亲委派只保证"同一个类名在委派链上由最先找到它的那个加载器加载一次"，不同加载器可以各自持有一份同名类——所以才有紧接着的第 3 点"类隔离"，说成"JVM 中唯一"与第 3 点自相矛盾。
  3. **（不计硬伤）原文**："如果所有父类加载器都加载不了，就会抛出 ClassNotFoundException。"
     方向对，但应补一句**由最初的调用者（App）在自己 `findClass` 也失败后才抛**，中间层 `parent.loadClass` 失败是返回 `null`/抛异常被捕获后继续；同时应点出另一条路径：**NoClassDefFoundError**。

- **扣分点**：
  - A-9：Ext → Platform 版本硬伤（且这是"JDK9 之后双亲委派还是三层吗"的必答位）。
  - B-8：缺 loadClass 三步、`NoClassDefFoundError` 对比、`findClass` vs `loadClass` 的姿势差异、热部署未归入破坏场景、JDK9 模块化影响。
  - C-11：全篇停在"规则 + 三个作用"的八股层。无 `ClassLoader.loadClass(String, boolean)` 源码链路（`getClassLoadingLock` / `findLoadedClass` / `parent.loadClass` / `findClass`）、无 `defineClass` 与 `CodeSource`/保护域、无 `java.*` 包名的禁止定义检查、无类命名空间的形式化、无 Tomcat `WebappClassLoaderBase` 为什么"先自己后父"、无 JDK9 `BuiltinClassLoader`。**"是什么 + 有啥用"两问，第一问的机制骨架是空的。**
  - D-2：开头摆"七个方面"略显模板化，可接受；真正的问题是有三处在**重复论证"破坏委派是好事"**（作用第 3 点、误区第 2 点、结尾又来一遍），信息密度被稀释；缺一句收束。
  - E-2：热部署、依赖隔离两个场景是"我们用了"，没有具体症状（`LinkageError`、`NoSuchMethodError`、两个版本 Jackson 打架）、没有工具（Arthas `sc -d` 看 loaderHash）、没有代价（Metaspace 泄漏、需要卸载旧加载器）。

- **可加分但没说的**：
  1. **"双亲"其实是误译**：`parent` 只有一个，本质是**单亲委派**；说清这一点比说"组合不是继承"更能证明真读过代码。
  2. **判断类是否相等的三元组**：`(ClassLoader 实例, 全限定名, 是否同一份字节码)`，这直接解释了"为什么热部署必须换新的 ClassLoader 实例"和"为什么 Arthas 里同一个类有两个 loaderHash"。
  3. **自定义类加载器只用重写 `findClass`**，绝不轻易重写 `loadClass`——一句话给出工程纪律，是本题最漂亮的收尾。
  4. 破坏场景补第四类：**JNDI/Spring Boot 的 `LaunchedURLClassLoader`（fat jar）**、以及"同一台 JVM 里跑两个版本同一中间件"的隔离需求。

- **面试官追问（3 个，附一句话标准答法）**：
  1. **"loadClass 的三步是什么？重写 loadClass 和重写 findClass 有什么区别？"** → `findLoadedClass`（缓存命中就返回）→ `parent.loadClass`（委派，父返回 null 不算失败）→ `findClass`（自己找，URLClassLoader 走 URLClassPath）；重写 `findClass` 只换"自己怎么找"，仍受双亲委派约束，重写 `loadClass` 才能改委派**顺序**——Tomcat 的 `WebappClassLoader` 就是重写 `loadClass` 实现"先本地后父"。
  2. **"什么时候抛 ClassNotFoundException，什么时候是 NoClassDefFoundError？"** → 前者是**显式加载**（`loadClass`/`Class.forName`/反射）走完委派链都没找到 → **受检异常**；后者发生在**链接/初始化**阶段，编译期存在、运行期 classpath 缺失，或静态初始化抛异常（先 `ExceptionInInitializerError`，再次访问变 `NoClassDefFoundError`）→ **Error**，通常不可恢复。
  3. **"Tomcat 为什么必须破坏双亲委派？JDK9 之后委派还在吗？"** → 一个 Tomcat 里多个 webapp 可能依赖同一框架的不同版本，若按双亲委派先问父加载器，公共路径上的 jar 会互相顶掉，所以 Webapp 加载器**先查 `WEB-INF/classes` 和 `WEB-INF/lib`**，但对 `java.*` 仍强制走父（JVM 层面也禁止用户定义 `java.*`）；JDK9 之后委派模型没变，只是实现换成 `BuiltinClassLoader`（Boot/Platform/App），并在委派之上叠加了**模块可读性（readability）**这一层约束。

- **改法（可直接替换进稿子的段落）**：
  > "先把版本钉死：**JDK8 及以前是 Bootstrap（C++，返回 null）→ ExtClassLoader → AppClassLoader；JDK9 起 ExtClassLoader 被 PlatformClassLoader 取代**，`ext` 目录取消，平台类加载器加载 `java.sql` 这类平台模块，委派链变成 Bootstrap → Platform → App。委派的实现只有三步：`findLoadedClass` 查缓存、`parent.loadClass` 委托父加载器（父返回 null 不算失败）、最后 `findClass` 自己找；因此**自定义类加载器应只重写 `findClass`**，重写 `loadClass` 才会改变委派顺序——Tomcat 正是这么做的。它的两个直接价值：一是安全（`java.lang.String` 永远先由 Bootstrap 命中，恶意同名类不可能被加载），二是**类的唯一性只由"ClassLoader 实例 + 全限定名"决定**，于是不同加载器能各持一份同名类、实现隔离与热部署——代价是两者类型不兼容，强转会抛 `ClassCastException`，而找不到类的两种表现要分清：显式加载失败是 `ClassNotFoundException`，链接/初始化阶段失败是 `NoClassDefFoundError`。"

## ③ 小结

### 分数统计

- **平均分：67.3**（72 + 62 + 68 = 202，÷3 ≈ 67.3）
- **最高分：72 —— 3-0（JMM vs 运行时内存结构）**
- **最低分：62 —— 3-2（CMS vs G1）**

三题全部落在"及格 / 不合格"，没有一题进入 80+ 良好档。**不是表达问题，是"版本 + 底层"两层同时失守**：三题的开场都能拿 D 项的 8 分，但 A 项各自被硬伤扣到 30 上下，B/C 又只拿到 52%~68%，总分自然封顶。按 rubric 纪律：**1 处硬伤 A 项至少扣 8，2 处及以上本题不得 90+**——3-2 有两处，3-3 有一处。

### 最容易被面试官击穿的点（按严重度排序）

1. **3-2 把 `MaxGCPauseMillis` 当硬上限**（"指定最大停顿时间，实现可预测的停顿"）——面试官只需追问"那我设 5ms 呢"，答案立刻崩；这是把"目标"说成"保证"的典型硬伤。
2. **3-2 通篇不提 CMS 已废弃/移除**，还在现在时推荐 CMS 适用场景——2026 年面 JDK17/21 岗位，这一句直接暴露知识停在 JDK8 教材。
3. **3-3 的 ExtClassLoader**——"JDK9 之后第二层还是扩展类加载器吗？"一问就穿，而且它是"双亲委派"题的标准起手式。
4. **3-0 的 happens-before 只到 6 条**且自称"最常用"——"另外几条是什么"是标准追命问，缺中断规则、对象终结规则、final 字段规则三块。
5. **三题都没有三色标记 / SATB / 增量更新 / 内存屏障语义**这一层"真正的底层"——3-2 最严重（CMS 与 G1 的差异本质就在并发标记算法上），3-0 次之（屏障只报名字不报语义）。
6. **"区别题"只答半边**（3-0 的运行时数据区五区几乎空白；3-2 的对比维度缺并发标记/记忆集/回收粒度/Full GC 行为）——这是 rubric 三.5 明确要求按"内容缺失"处理的地方。
7. **E 项全军覆没（2/2/3）**：三题的项目锚点都是"我主要使用 XX"级别的空话，没有任何堆大小、JDK 版本、GC 日志指标、故障现象、切换前后对比。这是最容易低成本补齐的 3-5 分。

### 最值得保留的亮点（3 条）

1. **3-0 的 30 秒破题**："JVM 内存结构解决'内存存在哪里'，JMM 解决'多线程如何安全访问内存'"——结论先行、一句话把两个维度劈开，这是三道题里最标准的一句开场白，值得原样保留并推广到其他"区别题"。
2. **3-3 的主动纠偏**："双亲是组合关系不是继承，每个加载器内部持有 parent 引用" + "破坏双亲委派不是坏事，是灵活性的体现"——面试官最吃"主动澄清常见误区"这一套，而且这两句都是事实正确的高含金量表述。
3. **3-2 的口径精度**："G1 整体使用标记-整理、局部使用复制" + "Garbage First 的名字来自优先回收价值最高的 Region"——口径是对的，且没有编造"G1 适合 >8GB"这类伪规范，说明作者对"经验值 vs 规范"有基本分寸感，这一点在补内容时千万别丢。
