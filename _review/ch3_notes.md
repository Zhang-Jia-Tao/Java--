线程私有区域(3个)
3.1.1 程序计数器(ProgramCounterRegister)
•
作用:记录当前线程执行到哪一行字节码,线程切换后能恢复继续执行;
•

•

•

•
栈帧里存:局部变量、方法参数、返回地址、操作数等;
•
生命周期:随线程而生,随线程而灭;
•
异常:
◦
栈深度超过限制:StackOverflowError栈溢出;
◦
栈内存不够:OOM内存溢出。

垃圾回收GC
什么是GC?

<!--p18-->

GC=GarbageCollection垃圾回收通俗说:JVM自动帮我们清理堆内存中没人使用的对象,释放内
存,不用程序员手动删对象。
哪些区域会垃圾回收?
只有堆、元空间会GC;虚拟机栈、本地方法栈、程序计数器完全不用GC,线程结束自动释放。
什么是垃圾对象?
没有任何引用指向的对象,就是垃圾,等着被回收。或者说是
JVM用「可达性分析」判定垃圾:从GCRoots出发遍历对象图,遍历不到的对象就是垃圾。
为什么不用引用计数法?引用计数法无法解决循环引用——A引用B、B引用A,两者计数都为1,
永远不为0,永远收不掉。可达性分析天然免疫这个问题:从根出发,环上的对象连不上根就是垃
圾,整环一起回收。
例:
代码块
User user = new User(); 
user = null; // 原来 new 的 User 对象没有引用了,变成垃圾

四大引用类型(由强到弱)
1. 强引用:普通new,只要有引用,永远不会被回收;
2. 软引用:内存不够时才回收,适合做缓存;
3. 弱引用:只要触发GC就一定回收,适合临时缓存;
4. 虚引用:形同虚设,不能获取对象,仅用于监控对象回收。
垃圾对象怎么判定?两种算法
引用计数法
给对象加计数器,有引用+1,引用失效-1,计数器为0就是垃圾。缺点:无法解决循环引用(A引
用B,B引用A,计数器都不为0,永远回收不了),JVM不用。
可达性分析算法(JVM正在用)
核心:从GCRoots(根对象)开始往下遍历,能遍历到的就是存活对象,遍历不到的就是垃圾。
哪些是GCRoots?
•
虚拟机栈中引用的对象;
•
静态变量引用的对象;
•
常量引用的对象;
•
本地方法栈引用的对象。
一句话:GCRoots就是程序当前正在用、必须保留的核心对象,从它们找不到的对象,全是垃圾。
三大垃圾回收算法
3.1.1 标记-清除
•
步骤:标记垃圾→直接清除;
•
优点:简单;
•
缺点:产生内存碎片,大对象分配容易OOM。
3.1.2 标记-复制
•
步骤:标记存活对象→复制到新内存区域→清空原区域;
•
优点:无内存碎片,效率高;
•
缺点:需要双倍内存空间;
•
适用:新生代。
3.1.3 标记-整理

<!--p20-->

•
步骤:标记存活对象→向一端整理压缩→清理末端垃圾;
•
优点:无内存碎片;
•
缺点:整理移动对象,效率低;
•
适用:老年代。
分代回收(JVM默认策略)
为什么分代?
对象生命周期不一样:大部分对象朝生夕灭,少数长期存活,分开回收效率更高。
堆内存分代结构
堆=新生代+老年代
1. 新生代(占堆1/3)分为:Eden区+Survivor0(S0)+Survivor1(S1)默认比例:8:1:1
◦
新建对象优先放Eden;
◦
Eden满了触发MinorGC,存活对象复制到S0/S1;
◦
S区来回复制15次(默认)还存活,晋升到老年代。
2. 老年代(占堆2/3)存放长期存活的对象、大对象;回收频率低,回收慢。
GC分类
1. MinorGC:只回收新生代,频率高、速度快;
2. MajorGC:只回收老年代;
3. FullGC:回收整个堆+元空间,StopTheWorld(STW)暂停所有用戶线程,卡顿严重,生产环
境要尽量避免。
GC完整工作流程
我们跟着一个 new User() 对象,看GC全程怎么干活:
1. 新对象出生对象优先放入Eden区,此时S0、S1都是空的。
2. 第一次MinorGC(Eden满了)

<!--p21-->

◦
Eden区放不下新对象→触发MinorGC;
◦
标记存活对象,全部复制到S0区;
◦
直接清空整个Eden区;
◦
存活对象年龄+1。
3. 第二次MinorGC
◦
Eden又满了→再次GC;
◦
把Eden+S0的存活对象,全部复制到S1区;
◦
清空Eden+S0;
◦
存活对象年龄+1。
4. 对象轮换存活S0↔S1来回复制,每熬过一次MinorGC,年龄+1。
5. 对象晋升老年代默认年龄达到15岁,还存活→直接送入老年代。
6. FullGC触发老年代也被长寿对象占满→触发FullGC,清理整个堆内存。
垃圾收集器

<!--p22-->

收集器就是把理论做成能跑的、有参数的、能调优的引擎。同一套算法可以做出多个收集器,区别
在于执行细节:谁来做(单线程还是多线程)、何时停用戶线程(STW还是并发)、怎么组织内存
(连续分代还是Region)。
任何GC都在这三个目标里取舍,三者不可兼得:
无论哪个收集器,一次回收都走这六步(差异在"每一步谁来做、做的时候用戶线程停不停"):
代码块
1 触发 → 2 判定(可达性分析) → 3 标记 → 4 处理(复制 / 清除 / 整理) → 5 
更新引用 / 指针 → 6 恢复 
收集器之间的全部差异,可以压缩成四个维度(这是理解所有收集器的钥匙):
1. 线程模型:串行(1个GC线程)/并行(多GC线程但用戶线程全停)/并发(GC与用戶线程同时
跑);
2. 内存布局:连续分代(新生代+老年代连续内存)/Region化(不连续小块);
3. 标记机制:STW全量标记/并发标记(三色标记+增量更新或SATB)/染色指针标记;
4. 处理方式:复制/清除(不移动,可并发)/整理(移动,STW)/并发整理(移动但用戶线程不停
——ZGC/Shenandoah的独门绝技)。
STW=StopTheWorld(世界停顿),指的是:GC执行某些阶段时,JVM把所有应用线程(业务
线程)全部暂停,只让GC线程干活。暂停的这段时间就叫"STW停顿"。
