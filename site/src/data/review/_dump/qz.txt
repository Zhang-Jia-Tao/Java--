===== qz-01 =====
TITLE: Integer 的 == 为什么时真时假
ONE: 自动装箱走 valueOf，负一百二十八到一百二十七之间复用同一个缓存对象，所以 == 为真；区间外每次新建为假，比数值请用 equals。
S60: 结论先说：两个 Integer 用 == 比的是对象引用，自动装箱走的是 Integer.valueOf，它会复用负一百二十八到一百二十七这三百五十六个预先造好的对象，所以在这个区间里两次装箱拿到的是同一个对象，== 为真；一旦出了区间，valueOf 每次都新建对象，引用不同，== 就为假。为什么要有这个缓存：循环计数、状态码、小下标这类小整数出现频率极高，固定缓存一小段就能省下大量短命装箱对象，直接减轻 GC 压力。落地只有一条：比数值一律用 equals，或者先把两边拆成 int 再比。
S180: 自动装箱是编译期的语法糖，javac 会把 Integer a 等于字面量一百这类写法替换成 Integer.valueOf(一百)，所以决定结果的是 valueOf 而不是 new。Integer 内部有一个静态的 IntegerCache，默认把负一百二十八到一百二十七的对象提前造好放进数组，valueOf 先看入参是否落在区间内，落在里面直接返回数组元素，落在外面才真正 new 一个。这个区间不是随意的：小整数在业务里最常见，固定三百五十六个对象几乎不占内存，却能省掉海量短命对象，属于典型的时间换空间。注意下界是写死的负一百二十八，上界默认一百二十七，可以靠虚拟机参数 AutoBoxCacheMax 调大，而且只影响 Integer 自己。所以两个一千的 Integer 用 == 比是假，换成一百就是真。真正比较业务数值时不要依赖缓存，用 equals 比数值和类型，或者直接拆成 int 比。
S600LEN: 651
S600: 先把三种写法的对象归属理清。第一，直接写 Integer a 等于一百二十七，编译器插入 valueOf，拿到的是缓存数组里的共享对象，两个这样的变量 == 为真。第二，写 new Integer(一百二十七)，构造器一定在堆上新建，哪怕数值落在缓存区间，== 也是假，所以 new 包装类是明确的错误用法，从高版本开始构造器也被标记为废弃。第三，一边是 Integer 一边是 int，比较时 Integer 被拆箱，语义退化成数值比较，此时一百和一千都返回真，但一旦这个 Integer 是 null，拆箱直接抛空指针，这是线上最常见的坑。相等的判断标准也要分清：equals 先比运行时类型再比值，所以 Integer 的一和 Long 的一用 equals 互比是假，而 == 在两者都是对象时根本编译不过，因为类型不可比。缓存覆盖范围也要记准：Short、Byte、Character 有固定缓存，Boolean 只有两个常量，Long 和 Integer 一样缓存负一百二十八到一百二十七但上界不能被参数调大，Float 和 Double 完全没有缓存。实践建议是：实体和返回值统一用包装类型表达可空语义，比较用 equals 或者工具类的空安全比较，往里传参时能拆箱就拆箱，但拆之前先判空。还要区分解析与创建：把字符串转成数字时用的解析方法返回的是基本类型，不经过缓存，只有装箱才走 valueOf。把包装类当 map 的键没有额外问题，因为相等基于值；换成按对象身份比较的容器才会踩坑。
POINTS:
 - [done] 自动装箱调用的是 Integer.valueOf，不是构造器，缓存区间内返回的是同一个共享对象。
 - [done] 缓存默认区间是负一百二十八到一百二十七，下界固定，上界可用虚拟机参数调大且只对 Integer 生效。
 - [done] == 比引用、equals 比类型加数值，所以 Integer 和 Long 的同值用 equals 互比也是假。
 - [done] 一边是基本类型时会触发拆箱，比较退化为数值比较，但值为 null 时会抛空指针。
 - [done] new Integer 永远在堆上新建对象，绕过缓存，属于应被淘汰的写法。
PITFALLS:
 - 以为缓存适用于所有包装类且区间都能调，实际上 Double 和 Float 根本没有缓存，Long 的上界也调不了。
 - 在条件或三目表达式里混用 Integer 和 int，触发隐式拆箱，遇到 null 直接空指针，而且报错位置常常离真正的原因很远。
FOLLOWUPS:
 Q: 为什么缓存只到一百二十七，不能做得更大？
 A: 核心是性价比。缓存的作用是命中高频小值，循环下标、状态码、标志位基本都落在很小的范围里，三百五十六个对象的总开销可以忽略；如果把上界放到几千甚至几万，缓存数组本身就要占可观内存，还都是长寿对象，等于把短命对象换成了常驻对象，命中率却提升有限。所以设计上给了一个固定小区间加一个可调上界，需要的人自己调大，不需要的人不付代价。反过来也要注意，调大上界只是让缓存数组变大，不会改变 == 的比较语义，业务代码仍然不该依赖它。
 Q: Integer 和 int 混用具体会出什么问题？
 A: 三类。第一类是空指针：集合里取出的 Integer 是 null，直接参与算术或比较就炸。第二类是语义不一致：两个 Integer 用 == 比是比引用，一旦其中一边被拆成 int，又变成比数值，同一段代码换个上下文结论就变了。第三类是隐蔽的拆箱点：三目表达式两边分别是 Integer 和 int，整个表达式会被提升成 int，null 分支就会抛异常；方法重载也可能因为拆箱选到另一个签名。规避办法是接口边界统一用包装类型、内部计算统一用基本类型，在入口处显式判空。

===== qz-02 =====
TITLE: try 里 return 之后 finally 还执行吗
ONE: 会执行，但顺序是先算返回值、再跑 finally、最后才返回；finally 改基本类型局部变量不影响结果，自己 return 或抛异常才会覆盖。
S60: 结论是 finally 一定执行。顺序拆三步：先算 return 后面的表达式并暂存，再执行 finally，最后才返回给调用方。值已经存下来了，所以 finally 里再改那个基本类型局部变量，返回值也不会变。为什么这么设计：编译器把 finally 的代码复制到了 try 的正常出口和每个异常出口，异常表里也登记了跳转，正常返回、抛异常、break 跳出都会经过它。工程上记住两条：别指望 finally 修正返回值，资源释放交给 try-with-resources，并避免在这里写 return。
S180: 先讲机制。javac 编译时不会生成一个真正的 finally 子过程调用，而是把 finally 的语句块复制到所有正常和异常的出口路径上，同时用异常表把 try 块覆盖的字节码关联到一个处理入口，这个入口先执行 finally 再重新抛出。所以只要控制流离开 try，finally 就会被走到，包括 return、break、continue 和抛出异常。再看返回值：return 后面的表达式在进入 finally 之前就已经求值完成，结果被压到操作数栈或存进局部变量槽，finally 执行完之后才做真正的返回指令。因此如果返回的是基本类型，finally 里怎么改都不影响；如果返回的是引用，finally 里通过这个引用改对象内部状态，调用方是看得到的，因为改的是同一个对象。第三点讲风险：finally 里如果自己 return，会丢弃 try 里已经算好的返回值和正在抛出的异常；finally 里如果抛出新异常，同样会覆盖原异常，堆栈上只剩最后那个，排查时会丢掉真正的根因。这也是很多规范禁止在 finally 里写 return 的原因。实际写代码时，资源关闭用 try-with-resources，需要兜底清理时 finally 里只做不会抛异常的收尾。
S600LEN: 707
S600: 把几种典型写法逐个过一遍。第一种，try 里写 return x，finally 里写 x 加加，返回的是自增前的值，因为返回值早已入栈。第二种，try 里写 return 一个引用，finally 里往这个引用指向的集合里塞元素，调用方能看到元素，因为引用没变、对象被改了。第三种，try 里写 return，finally 里也写 return，最终返回 finally 的值，中间那个被静默丢弃，而且编译器不报警，只有靠代码规范去禁。第四种，try 里抛异常，finally 里正常执行完，异常继续往外抛；finally 里抛了新异常，原异常被完全吞掉，日志里只能看到新异常。第五种，try 里抛异常，finally 里 return，方法会正常返回，异常消失。还有一个容易被忽略的边界：System.exit 会直接终止虚拟机，不进入 finally；线程被强制杀死或进程被杀也不会；守护线程在主线程结束后被回收，同样可能来不及执行。另外嵌套 try 时，内层 finally 先于外层 finally 执行，顺序是从里到外。字节码层面还有一个细节：老版本编译器曾用 jsr 和 ret 指令实现 finally，后来改为内联复制，异常处理表里能看到编译器自动生成的 any 型 catch 块，它捕获 Throwable 执行 finally 后再原样抛出，理解这一点就能解释为什么 finally 对 Error 也生效。工程结论是，finally 只用来做确定不会抛异常的收尾，关闭资源优先用 try-with-resources，它能把关闭异常作为抑制异常保留下来，比手写 finally 更安全。
POINTS:
 - [done] 执行顺序是先求值并暂存返回值，再执行 finally，最后返回，所以 finally 改基本类型局部变量不影响结果。
 - [done] finally 对正常返回、抛异常、break 和 continue 都会执行，因为编译器把代码复制到了所有出口。
 - [done] finally 里写 return 会覆盖 try 的返回值并吞掉正在抛出的异常。
 - [done] 返回引用时，finally 里修改该引用指向的对象内容，调用方可以看到，因为对象是同一个。
PITFALLS:
 - 以为 finally 里给局部变量自增能改变返回值，实际返回的是自增前已经暂存的值。
 - 在 finally 里写 return 或让 close 抛异常，把真正的业务异常吞掉，线上只能看到不相干的报错。
FOLLOWUPS:
 Q: finally 里 return 会发生什么，为什么规范要禁止？
 A: 会发生两件坏事。一是返回值被替换，try 里算好的结果被静默丢弃，调用方拿到的是 finally 的值，代码读起来完全看不出这个覆盖关系。二是异常被吞，try 块里抛出的异常还没有传播出去就被 finally 的 return 截断，方法正常返回，上层完全感知不到失败，日志里也没有记录。更麻烦的是编译器不会给任何提示，这类问题只能通过代码评审和静态检查拦住。正确做法是 finally 里只做清理，需要转换异常就在 catch 里显式包装并抛出。
 Q: 如果 finally 里也抛异常，最终抛出去的是哪个？
 A: 抛的是 finally 里的那个，原来 try 里的异常被彻底丢弃，而且是丢失而不是挂成抑制异常，堆栈上只有新异常。这个语义和 try-with-resources 正好相反：try-with-resources 会把 close 抛出的异常作为抑制异常附加到主异常上，用 getSuppressed 还能取到，打印堆栈时也会带上。所以资源关闭一律优先用 try-with-resources，不要手写 finally 里调用 close，尤其不要在手写 close 里再抛业务异常。
 Q: finally 一定执行吗，有没有例外？
 A: 有例外，但不是语法层面的。正常返回、抛异常、break、continue、goto 标签跳转都会经过 finally，因为这些都属于控制流正常离开 try 块，编译器已经把所有出口都接上了。真正不执行的情况是虚拟机直接终止：调用 System.exit、进程被信号杀掉、机器断电；守护线程在主线程结束后被回收也可能来不及。另外如果把清理逻辑放在 finally 里但虚拟机已经进入关闭钩子阶段，行为也不可控，所以关键资源要在钩子里单独处理。

===== qz-03 =====
TITLE: 两个 List 参数的重载为什么编译不过
ONE: 泛型只在编译期，两个 List 参数的方法擦除后签名都是 List，编译器直接报名字冲突；只能换方法名、加类型令牌或改参数个数。
S60: 结论是编译不过，报的是名字冲突。原因在于泛型实参不参与方法签名，编译器在做重载决议时看的是擦除后的描述符，List 加 String 和 List 加 Integer 擦除后都变成 List，两个方法就成了同一个签名。为什么这么设计：泛型是编译期的类型检查工具，运行时为了兼容老版本字节码，类型参数被擦成原始类型或它的上界，虚拟机里根本没有这两种 List 的区别。所以想按元素类型分流，只能换方法名、加一个 Class 参数做类型令牌，或者干脆收一个 Collection 在方法内部判断。
S180: 先讲擦除规则。类型参数如果没有边界就擦成 Object，有上界就擦成上界，比如 T extends Number 擦成 Number；参数化类型擦成原始类型，List 加 String 擦成 List；方法上的泛型参数本身也会被擦掉，必要时编译器插入桥方法保证多态正确。于是两个方法一个收 List 加 String 一个收 List 加 Integer，擦除后描述符完全一样，虚拟机无法区分，编译器在编译期就会拒绝，报错信息通常是两个方法具有相同的擦除。再看重载决议：它发生在编译期，依据是实参的静态类型，和运行时对象的真实类型无关；既然签名冲突，决议根本没机会做。桥方法是另一个话题，它解决的是子类覆写时泛型协变的问题，编译器会生成一个收 Object 的合成方法转调真正的实现，和重载冲突没有关系。需要按元素类型分流时的可行做法有三种：改方法名让语义显式；增加一个 Class 参数作为类型令牌，用 class 字面量区分；或者接收原始集合，在方法内部靠 instanceof 逐元素判断。
S600LEN: 634
S600: 把边界讲清楚。第一条，擦除导致的不只是重载冲突，还有一串附加限制：不能对参数化类型做 instanceof，因为运行时没有这个类型；不能直接 new 泛型数组，必须先造 Object 数组再强转，而且这种强转是不安全的；静态成员不能引用类的类型参数；泛型异常类型不能被 catch，因为异常处理器在运行时要靠类型匹配；基本类型不能作为类型实参，只能用包装类。第二条，重载决议还有几个容易踩的点：收 Object 和收 String 的两个重载传 null 时选更具体的 String；收 String 和收 Integer 的两个重载传 null 会歧义报错；泛型方法加一个具体类型的重载是允许的，因为擦除后分别是 Object 和具体类型，描述符不同，但调用时具体类型那个优先。第三条，运行期真想拿到泛型实参，只能从带类型信息的地方取：字段的泛型签名、方法参数和返回值的泛型签名、父类或接口的泛型实参，通过反射的 ParameterizedType 解析；直接对一个实例调 getClass 拿到的永远只是原始类型。第四条是取舍：擦除是为了二进制兼容，代价是运行期类型信息缺失和一堆语法限制，所以框架层普遍用类型令牌把类型信息显式传下去，比如反序列化时传 Class 或 TypeReference，本质都是把编译器才知道的信息在运行期补回来。还有一点容易忽略：重载决议取自实参的静态类型，传字面量或装箱表达式时编译器早已定好调哪个方法，运行时对象再变也不会换分支。
POINTS:
 - [done] 泛型在编译后被擦除成原始类型或上界，运行时 List 加 String 和 List 加 Integer 是同一个类。
 - [done] 方法签名不包含泛型实参，两个方法擦除后描述符相同，编译器报名字冲突而不是等到运行期。
 - [done] 桥方法是编译器为覆写和协变生成的合成方法，用来保证多态调用正确，和重载冲突无关。
 - [done] 需要按元素类型分流时，可以改方法名、增加 Class 类型令牌，或收集合后在内部逐元素判断。
PITFALLS:
 - 以为给两个方法配上不同泛型实参就算不同签名，实际上擦除后完全一样，编译期直接失败。
 - 以为运行期还能从对象上拿到 List 加 String 这个类型，实际只有从字段、方法签名、父类签名这些带泛型信息的位置反射才取得到。
FOLLOWUPS:
 Q: 什么是桥方法，它解决什么问题？
 A: 桥方法是编译器自动生成的合成方法。典型场景是子类实现泛型接口或覆写泛型父类方法，比如父类声明收 T 的方法、子类实现成收 String，擦除后父类方法的描述符是收 Object，子类方法是收 String，两者描述符不同，多态调用就会落到父类那个空实现上。编译器于是在子类里生成一个收 Object 的桥方法，内部强转成 String 再调用真正的实现，这样按父类签名调用也能正确分派。它和重载冲突无关，因为桥方法是在擦除之后补的，不参与源码层面的重载决议。
 Q: 擦除除了重载冲突还带来哪些坑？
 A: 主要有五类。不能对参数化类型做 instanceof，运行时没有这个类型。不能直接创建泛型数组，只能建 Object 数组再强转，而且这个强转不安全，可能引发堆污染。静态成员不能使用类的类型参数。泛型异常类型不能被 catch。基本类型不能作为类型实参，必须用包装类。另外可变参数加泛型会生成泛型数组，需要用注解压制警告并保证只读，否则同样有堆污染风险。
 Q: 怎么在运行时拿到泛型实参？
 A: 只能从保留了泛型签名的地方取。第一是字段，通过字段对象取泛型类型，能拿到 ParameterizedType，再看实参。第二是方法参数和返回值，同样走方法的泛型签名。第三是父类和接口，通过取带泛型签名的父类型来拿实参，很多通用基类就是靠这一步知道自己被哪个具体类型继承的。第四是显式传类型令牌，构造函数里传一个 Class 或者带泛型的引用对象，框架层普遍用这个办法。直接对一个实例调 getClass 拿到的永远是擦除后的原始类型，里面没有实参信息。

===== qz-04 =====
TITLE: new String 和字面量的 == 为什么不同
ONE: 字面量在类加载时进字符串常量池并被复用，new String 每次在堆上新建，所以 == 为假；intern 返回池中同值字符串的引用。
S60: 结论：字面量走常量池，new String 一定在堆上新建。编译期出现的字符串字面量被写进 class 文件的常量池，类加载解析时到字符串池里找同值对象，有就复用，没有就造一个放进去，所以两个相同的字面量其实是同一个对象，== 为真。new String 是把内容拷进一个全新的堆对象，内容相同但引用不同，== 为假。为什么要有池：字符串是使用频率最高的对象，去重能省内存也能让比较变快。常量表达式还会在编译期折叠，字面量直接相加的结果也是池里的对象。

 Q: JDK6 和 JDK7 之后 intern 的行为有什么区别？
 A: 区别在池的位置和未命中时的动作。JDK6 里字符串池在永久代，intern 未命中时会把当前字符串的内容复制一份放进池，返回的是池里那个复制品，所以对 new 出来的对象调 intern，结果和原对象引用不同。JDK7 起池移到堆里，未命中时直接把当前对象的引用登记进池，不再复制内容，于是 intern 的返回值和原对象是同一个引用。这个变化导致很多老面试题的答案在新版本上不成立，回答时要说清版本前提，否则容易被追问打穿。
 Q: 字符串常量池在内存的哪个区域？
 A: 现在在堆里。早期它在永久代，和类元数据放在一起，容量受限、回收条件苛刻；JDK7 把它移到了堆中，从此受堆大小约束，也由普通垃圾回收管理，只有没有任何引用的池内字符串才可能被回收。要注意它和运行时常量池不是一回事：class 文件里的常量池是每个类自己的数据结构，加载后其中的字符串字面量会被解析到全局的字符串池，两者层级不同，很多回答把这两个概念混着说。
 Q: 大量使用 intern 为什么可能有害？
 A: 因为池是长期存活的共享结构。第一，池里的字符串一旦被登记就常驻，除非引用全断且被回收，动态生成的大量业务字符串塞进去，等于把短命对象变成长寿对象，压力从新生代转移到老年代。第二，每次 intern 都要做一次池查找，重复调用是纯开销。第三，池的桶数有限，大量不同值会加剧哈希冲突，查找退化成链式比较，反而更慢。合理的用法是只对有限枚举集合的字符串做池化，用引用比较替代 equals 来提速，而不是把所有外部输入都过一遍 intern。

S60: 结论是逆序关闭，最后声明的资源最先关。为什么：资源之间常有依赖，后声明的往往建立在先声明的基础之上，先关外层再关内层才安全，所以语法规定按声明的相反顺序释放。机制上编译器把这段展开成嵌套的 try 加 finally，每层负责关闭一个资源并判空，关闭抛出的异常不会直接往外扔，而是用抑制异常挂到主异常上，主异常的堆栈和原因都保留，排查时用 getSuppressed 就能看到全部。所以凡是实现 AutoCloseable 的资源都优先用它。

 Q: 如果第二个资源初始化就抛异常，第一个会被关闭吗？
 A: 会。资源是按声明顺序从左到右初始化的，第二个构造器抛出异常时，控制流已经离开了初始化序列，编译器生成的嵌套结构会从内向外退出，只对已经成功初始化的资源执行关闭，也就是第一个会按正常路径被关闭。未初始化成功的那个没有对象，自然不需要关。此时主异常是初始化失败那个，如果第一个资源关闭也失败，关闭异常作为抑制异常挂在主异常上，两者都能看到。这一点和普通 finally 手写时容易漏判空的情况相比更稳妥。
 Q: 抑制异常怎么打印才不会丢？
 A: 关键是用标准方式输出。调用打印堆栈的方法时，虚拟机实现会自动把抑制异常链一起打出来，格式上会标记为 suppressed，所以直接打堆栈就够。真正会丢的是这几种写法：只打异常的 message、把异常包成自定义异常但只拷 message、或者日志框架把异常对象转成字符串再输出。如果确实需要包装，应该把原异常作为 cause 传进新异常，并且把 getSuppressed 的内容也带过去，或者在日志里额外遍历一次抑制列表。线上排查时，看到主异常是个无关的关闭失败，就要警惕主异常是否被丢掉，去查抑制链。
 Q: 为什么资源的声明顺序要考虑依赖关系？
 A: 因为释放是逆序的，后声明的先关，所以谁依赖谁决定了谁该写在后面。典型是连接、语句、结果集，语句依赖连接，结果集依赖语句，按连接、语句、结果集的顺序声明，释放时就是结果集、语句、连接，正好自内向外。如果把连接写在最后一个声明，释放时先关连接，语句和结果集的关闭就会失败，或者在不支持的情况下静默失效。顺序写错通常不报编译错误，只在关闭阶段抛异常或者造成连接泄漏，属于必须靠规范约束的地方。

TITLE: HashMap 并发扩容为什么会死循环
ONE: 老版本头插式迁移在并发扩容时会把链表接成环，查找就死循环打满 CPU；新版本改尾插不再成环，但并发写仍会丢数据，需 ConcurrentHashMap。
S60: 结论分两段。老版本是数组加链表，扩容迁移用头插，两个线程同时迁移同一个桶时，节点顺序被反复反转，指针最终指回自己形成环，之后任何一次查找落到这个桶就转不出来，CPU 直接跑满。新版本改成尾插，并且扩容时按哈希的高位把一条链拆成低位和高位两条，各自保持原有相对顺序，所以不会再成环。但新版本依然不是线程安全的，并发写会互相覆盖、计数不准、扩容时读到中间状态，所以并发场景只能用 ConcurrentHashMap，HashMap 只用于单线程或外部加锁。
S180: 先看结构。HashMap 底层是数组，默认初始容量十六，负载因子零点七五，元素数超过容量乘负载因子就扩容为原来的两倍；每个桶里挂链表，链表过长且表容量足够时转成红黑树，索引位置由哈希值与容量减一做与运算得到，这也是容量必须是二的幂的原因。再说老版本的死循环。迁移时把旧桶里的节点逐个搬到新桶，采用头插，也就是每搬一个就插到链头，这样链表顺序被反转。假设两个线程同时扩容，一个线程刚把 A 指向 B，另一个线程又按它读到的旧链表头继续插，指针就可能出现 A 指向 B、B 又指向 A 的环。环一旦形成，后续查找走到这个桶就沿着 next 无限转，表现为某几个请求卡死、单核 CPU 打满、线程栈一直停在查找方法里。新版本的改动是把头插改成尾插，保留相对顺序，并且迁移时不再逐个重算索引，而是用哈希值与旧容量做与判断，把一条链拆成留在原位的低位链和整体后移的高位链，两条链内部顺序不变，因此并发下最多是数据错乱，不会成环。但要注意，这个改动解决的是死循环，没有解决线程安全：并发 put 可能互相覆盖、size 统计错、resize 期间读到不完整数据。

S600: 把权衡讲透。为什么当初用头插：早期实现里迁移时只需要改头指针，插入是常数操作，写法简短，而且当时认为反正扩容是单线程环境，没有考虑并发。代价是顺序反转，也埋下了环的隐患。新版本改成尾插并做高低位拆分，好处有三个：保持顺序，避免环；不用重新计算哈希，因为容量翻倍后新索引只可能是原索引或原索引加旧容量，判断一位就够；迁移后节点分组更连续，缓存友好。代价是迁移代码更复杂，需要维护两条链表的头尾。红黑树是另一个优化：单个桶冲突太多时，链表查找是线性，转成树后退化成对数；但树化有前提，链表长度到八且表容量至少六十四，容量不够时优先扩容而不是树化，因为小表上树化收益低还增加维护成本；删除后节点减少到六再退化成链表，用两个阈值留出缓冲，避免在边界反复转换。并发问题则交给 ConcurrentHashMap：早期用分段锁把表切成若干段各自加锁，新版本改成对桶头节点加锁配合无锁读和 CAS 初始化，粒度更细，扩容还支持多线程协助迁移。最后是使用边界：HashMap 允许一个空键和多个空值，不保证顺序，迭代器是快速失败的，结构被修改会抛并发修改异常，但这只是尽力检测，不能当线程安全保证用；多线程读多写少可以用不可变快照或只读发布，只要有写就必须换并发容器或者外部加锁。另外要记住容量是二的幂这条前提贯穿全文：手动给的初始容量不是二的幂时会被向上取整到最近的二的幂，所以别指望精确控制数组长度；遍历时尽量用迭代器，不要在循环里做结构性修改。

 Q: 负载因子为什么取零点七五？
 A: 是空间和时间的折中。负载因子越小，冲突越少、查找越快，但数组空洞多、内存浪费大、扩容更频繁；越大越省内存，但链表变长、查找退化，还可能更早触发树化。零点七五是实测的经验值，在这个点上冲突概率和空间利用率比较平衡；同时它让容量乘负载因子的阈值在常用容量下都是比较整的数。真正的调优不是改这个值，而是预估数据量后直接给初始容量，避免反复扩容，因为扩容要迁移全部元素，代价远大于一开始就分配够。
 Q: 为什么容量必须是二的幂？
 A: 为了把取模换成位运算。索引位置本来应该是哈希值对容量取模，但取模是除法，开销大；当容量是二的幂时，哈希值与容量减一做按位与，结果和取模完全一致，而且快得多，这也是实现里到处可以看到的写法。代价是低位信息决定一切，如果哈希的低位分布不好，冲突会集中，所以实现里对哈希值做了一次扰动，把高位异或到低位，让高位也参与定位。容量翻倍后索引的变化也因此很简洁：只看哈希那一位，是零就留在原位，是一就后移旧容量个位置，扩容拆分就是靠这个判断。
 Q: 为什么树化阈值是八，退化阈值是六？
 A: 八来自冲突概率的统计：在哈希分布均匀的理想情况下，一个桶里节点数达到八的概率极低，所以真到了八，说明要么哈希被恶意构造，要么分布很差，此时链表查找会明显拖慢，转成红黑树把最坏情况压到对数级。之所以不更早转，是因为树节点比链表节点占内存更多，小规模冲突用链表更快。退化阈值取六而不是八，是为了留出缓冲带，如果两个阈值相同，元素在七和八之间反复增删就会在链表和树之间来回转换，白白消耗性能。另外树化还要求表容量至少六十四，容量太小时优先扩容，因为扩容本身就能把冲突打散。

FOLLOWUPS:
 Q: 为什么移三十二位的结果和没移一样？
 A: 因为语言规定移位次数只有低位参与运算：int 只看低五位，相当于对三十二取模，long 只看低六位，对六十四取模。这是为了和硬件移位指令的行为保持一致，也避免超出位宽时出现未定义结果。所以移三十二位等价于移零位，移三十三位等价于移一位，移位数为负数时同样先取模。实践含义是，写循环移位或者想用移位做除法时，必须自己保证次数合法，不能依赖语言去报错，因为编译器通常不会提示。
 Q: 怎么用位运算判断一个数是二的幂？
 A: 思路是利用二的幂在二进制里只有一个一。把这个数减一，原来那个一会变成零，它右边全变成一，两者按位与结果为零，所以条件是这个数大于零并且它和它减一的与为零。必须加大于零，因为零减一之后全是一，零与全一还是零，会误判零；负数因为符号位是一，也不满足只有一个一。同类技巧还有取最低位的一，用这个数和它的相反数做与；以及统计二进制中一的个数，用与上减一逐次消掉最低位的一，循环次数就是一的个数。
 Q: 负数取模和按位与为什么在哈希里可以互换？
 A: 因为哈希索引只需要低位，而且实现里保证容量是二的幂，此时对一个非负整数取模和与容量减一做按位与完全等价。但要注意前提：按位与不受符号影响，负数上两者结果不同，比如负五对二取模是负一，负五与一是正一，所以不能无条件互换。哈希表里之所以能用，是因为索引只取哈希的低若干位，结果天然落在容量范围内，而容量是二的幂保证了位掩码就是取余；再加上哈希值经过扰动，低位分布已经被打散。换成非二的幂的容量，就必须老老实实取模。

 Q: 用 G1 时还需要显式指定年轻代大小吗？
 A: 一般不要。G1 会按暂停目标动态调整年轻代占用的区域数量，显式指定年轻代大小等于把这个决策钉死，自适应失效，停顿目标也就形同虚设。同理，老年代相关的比例参数也和 G1 的回收模型冲突，混着设容易互相覆盖。真要调，优先调最大停顿目标和堆大小，再看是否需要调整区域大小，而且每次只动一个参数并用日志验证。只有在明确知道业务分配模式、并且实测证明自适应策略不适用时，才考虑限制年轻代范围，并承担相应的停顿波动风险。
 Q: GC 日志里的回收前降到回收后括号里大小分别代表什么？
 A: 三个数依次是这次回收开始时的堆占用、回收结束后的堆占用，以及括号里的当前堆提交大小或容量。看回收前可以判断这次回收是被分配压力逼出来的，还是例行执行；看回收后能算出回收释放了多少，以及还剩多少存活对象。如果回收后占用仍然接近容量，说明存活率很高，年轻代回收腾不出太多空间，接下来很可能出现混合回收甚至完整回收。这三个数配合停顿时间一起看，就能判断是分配太快、存活太多，还是堆本身给得不够。
 Q: 为什么同样的参数在容器里可能不生效？
 A: 通常是三个原因。第一是内存识别，早期版本按宿主机内存计算默认堆，容器限额小的时候会被杀死，后来才有容器感知和按比例设置的方式。第二是版本差异，同一语义的参数在不同版本里名字或默认值不同，统一日志语法就是新版本才有，老版本要用另一套打印开关。第三是回收器差异，某些参数只在特定回收器下有意义，换一个回收器就被忽略或者被覆盖。可靠做法是在容器里显式给出堆和堆外预留，启动时用打印最终标志的方式核对生效值，并定期看日志确认行为符合预期。
