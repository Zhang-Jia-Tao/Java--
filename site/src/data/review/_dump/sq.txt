===== sq-01 =====
TITLE: 订单、用户、商品三表 join 统计每个用户消费额
ONE: 以订单为主表 join 用户和明细，按用户分组，金额用 SUM(数量乘单价)，订单数必须 COUNT(DISTINCT 订单id)，否则明细行放大会重复计数。
S60: 先定粒度：要每个用户一行，主表 orders，join users 拿名字，join order_items 拿明细金额，按 user_id 和 name 分组。金额写 SUM(oi.qty * oi.price)，订单数一定写 COUNT(DISTINCT o.id)，因为一张订单有多条明细，join 后订单 id 被复制成多行，COUNT(*) 数的是明细条数。状态和时间这类订单表过滤放 WHERE 先缩小行数，要保留零消费用户就改 left join 并把条件写进 ON。
S180: 完整写法是 SELECT u.id, u.name, COUNT(DISTINCT o.id) AS order_cnt, SUM(oi.qty * oi.price) AS total_amount FROM users u JOIN orders o ON o.user_id = u.id AND o.status = 'PAID' JOIN order_items oi ON oi.order_id = o.id WHERE o.created_at >= '2025-01-01' AND o.created_at < '2025-02-01' GROUP BY u.id, u.name HAVING SUM(oi.qty * oi.price) >= 1000 ORDER BY total_amount DESC LIMIT 20。三步讲清：第一定输出粒度，一个用户一行，分组键就是 u.id 加 u.name；第二定连接路径，join users 一对多查一不放大，join order_items 一对多会放大行数，聚合只能放最外层；第三定过滤位置，订单状态和时间放 WHERE 能用索引先减行，HAVING 只留给聚合条件。数据量大时先按订单粒度聚合明细再汇总，比先 join 再聚合省一次关联。
S600LEN: 860
S600: 深挖先讲行放大：join 的中间结果是各表匹配行的乘积，orders 一条对 order_items 五条，订单层面的运费、优惠金额就被复制五份，SUM 出来直接翻五倍。判断标准是看被聚合的字段属于哪张表的粒度，明细金额在明细粒度求和没问题，订单运费属于订单粒度，就必须先按订单粒度聚合再往上汇总。Distinct 不能救这种情况，DISTINCT 去重的是值不是重复加总，金额永远算不对。稳妥做法是两步聚合：内层写 SELECT o.user_id, o.id, SUM(oi.qty * oi.price) AS amt FROM orders o JOIN order_items oi ON oi.order_id = o.id GROUP BY o.user_id, o.id，外层再 SELECT user_id, SUM(amt) FROM 这段 GROUP BY user_id。第二讲 COUNT(DISTINCT) 的代价，它要为每组维护去重集合，容易落到临时表和磁盘，如果分组基数大要警惕。第三讲 WHERE 和 HAVING 的分工，WHERE 在分组前过滤行且能走索引，HAVING 在分组后过滤组，只有聚合条件必须用 HAVING，把用户城市这种普通条件写进 HAVING 会白扫一遍数据。第四讲 NULL，left join 之后没下单的用户 SUM 返回的是 NULL 不是零，展示层要用 COALESCE(total_amount, 0)，COUNT 列则天然是零。第五讲更复杂的口径：如果一张订单还要关联支付流水和优惠券，两个一对多同时 join 会让行数变成两边的乘积，金额会成倍虚高，这种必须分别按订单聚合再 join 回订单粒度。最后落执行计划，Explain 里看 type 是不是 ref 或 range，Extra 出现 Using temporary 或 Using filesort 基本说明分组键没走索引或中间结果太大，可以先把过滤和聚合压到子查询里缩小数据再关联。
POINTS:
 - [done] 先定输出粒度再定分组键，一个用户一行就按 user_id 和 name 分组，非聚合列必须出现在 group by 里。
 - [done] 订单数必须 COUNT(DISTINCT o.id)，因为 order_items 是一对多，join 后订单 id 被复制成多行，COUNT(*) 数的是明细条数。
 - [done] 对事实表的过滤放 WHERE 能先缩小行数并走索引，HAVING 只留给聚合条件。
 - [done] 要保留零消费用户必须用 left join 并把右表条件写进 ON，写进 WHERE 会退化成 inner join。
 - [done] 订单级字段和明细级字段不能混在一起 SUM，先按订单粒度聚合再汇总到用户才不会重复加总。
PITFALLS:
 - 一条订单多条明细时用 COUNT(*) 当订单数，结果偏大，或者用 SUM(DISTINCT 金额) 去重，把真实的两笔同额订单也合成一笔。
 - 写了 left join 却把右表状态条件放在 WHERE，等于把左连接变回内连接，零消费用户直接消失。
FOLLOWUPS:
 Q: 为什么订单数要用 COUNT(DISTINCT o.id)，用 COUNT(*) 会怎样？
 A: 结论是 COUNT(*) 数的是连接后的行数，不是订单数。orders 和 order_items 是一对多，一张订单有三条明细就会展开成三行，COUNT(*) 得到的是明细条数，金额合计也跟着翻。纠正方式有两种，要么 COUNT(DISTINCT o.id) 把重复 id 折叠，要么先按订单粒度聚合明细、再关联聚合结果，后一种在大数据量下更稳，因为去重集合的维护成本比多一次分组高。同理 SUM 也要检查是否被放大，金额字段如果来自订单表而不是明细表，必须换成两步聚合。
 Q: left join 之后在 WHERE 里过滤右表字段会发生什么？
 A: 结论是 left join 退化成 inner join。执行顺序是先连接再过滤，右表没匹配上的行补 NULL，WHERE 里对右表字段做等于判断时 NULL 参与比较得到 unknown，整行被过滤掉，本该保留的零消费用户就丢了。正确写法是把条件放进 ON，让它在匹配阶段生效，右表不满足条件就仍保留左行并补 NULL。如果条件里有零值语义，再在外面用 COALESCE 兜底。要验证很简单，看 EXPLAIN 或者对比加条件前后左表行数是否一致。
 Q: 如果一张订单还关联支付流水和优惠券，金额怎么算才不出错？
 A: 结论是分别聚合、再回到订单粒度 join，绝不能让两个一对多在一条语句里同时展开。支付流水两条、优惠券三条同时 join 会得到六行，订单金额被乘了六倍。做法是各写一个按 order_id 分组的子查询，一个算实付合计，一个算优惠合计，得到每个订单一行，再和 orders 关联，这样每个子查询的粒度都是订单，不会互相放大。如果一定要在一条 SQL 里完成，就用 CTE 把两步分开写清楚，可读性和正确性都更好。

===== sq-02 =====
TITLE: 每个部门工资前三，分组 TopN 怎么写
ONE: 内层 ROW_NUMBER 按部门分区、工资倒序编号，外层筛 rn 小于等于 3，窗口函数在 WHERE 之后才计算，不能直接过滤。
S60: 思路是窗口函数套一层子查询。内层 SELECT 里写 ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn，给每个部门内部按工资倒序编号，外层再 WHERE rn <= 3。不能直接在内层 WHERE 里筛 rn，因为窗口函数在 SELECT 阶段才算，执行顺序在 WHERE 之后，字段还不存在。并列要不要都取决定用哪个函数，取三个人用 ROW_NUMBER，取前三档工资用 DENSE_RANK。
S180: 完整写法是 WITH t AS (SELECT e.id, e.name, e.dept_id, e.salary, ROW_NUMBER() OVER (PARTITION BY e.dept_id ORDER BY e.salary DESC, e.id) AS rn FROM emp e) SELECT t.dept_id, d.name AS dept_name, t.name, t.salary, t.rn FROM t JOIN dept d ON d.id = t.dept_id WHERE t.rn <= 3 ORDER BY t.dept_id, t.rn。执行顺序是 FROM 和 JOIN 拼数据，WHERE 过滤行，GROUP BY 和 HAVING 聚合，然后才计算窗口函数，接着 SELECT 投影，最后 ORDER BY 和 LIMIT，所以窗口结果只能在外层过滤。并列处理是考点：工资 100、100、90 时 ROW_NUMBER 给出 1、2、3，两个 100 可能被丢掉一个；RANK 给出 1、1、3，第三名空缺；DENSE_RANK 给出 1、1、2，两档都保留。窗口 ORDER BY 要补唯一键比如 id 做 tie-break，否则并列行顺序会漂。
S600LEN: 842
S600: 深挖先讲窗口函数的实现代价：PARTITION BY 加 ORDER BY 需要对数据按分区键排序，内存里放不下就落临时文件，所以分区数多、数据量大时要先把无关列和无关行过滤掉，别拿全表直接开窗。第二讲 TOP N 的几种等价写法及取舍：UNION ALL 把每个部门一条 SQL 拼起来，部门少时最快，部门多就不可维护；相关子查询写法直观但平方级，只适合小表；窗口函数是通用解，一次扫描加一次排序，还能顺便算占比、排名。第三讲 rank 系列的边界：RANK 并列后跳号，DENSE_RANK 不跳，ROW_NUMBER 强制唯一，取前三名员工用 ROW_NUMBER，取工资前三档用 DENSE_RANK，口径要和业务对齐，否则 HR 会质疑为什么部门只有两个人上榜。第四讲 NULL 和排序：MySQL 升序时 NULL 排最前，倒序时排最后，如果 salary 允许为空，NULL 会被排到最后不占名额，想要参与排序就写 ORDER BY salary DESC NULLS LAST，MySQL 用 ORDER BY salary IS NULL, salary DESC 模拟。第五讲窗口帧：不写 ROWS/RANGE 时默认是从分区第一行到当前行的 RANGE 帧，对 ROW_NUMBER 无影响，但如果你在同一个窗口里既排名又累计求和，RANGE 会把 peer 行一起算进去，累计值会跳，要显式写 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。第六讲性能优化：在 dept_id 和 salary 上建联合索引能让排序走索引顺序，减少 filesort；如果只要第一页的少量部门，可以用 LATERAL 或者先取部门列表再逐个 topN。最后提醒，部门表 left join 员工表时，空部门 rn 是 NULL，条件 rn <= 3 会把它过滤掉，想展示空部门要写 rn IS NULL OR rn <= 3。
POINTS:
 - [done] 标准写法是内层窗口函数打行号、外层派生表筛 rn，因为窗口函数在 WHERE 之后才计算，不能直接过滤。
 - [done] ROW_NUMBER 严格编号、RANK 并列跳号、DENSE_RANK 并列不跳号，取人或取档决定选哪个。
 - [done] 窗口 ORDER BY 要补唯一键做 tie-break，否则并列行的编号不稳定，分页会重复或漏数据。
 - [done] 没有窗口函数时用相关子查询数比自己工资高的人数，复杂度平方级，只适合小表。
 - [done] 在 dept_id 和 salary 上建联合索引可以减少排序开销，先过滤无关行再开窗能降低临时表压力。
PITFALLS:
 - 直接把窗口函数结果写进 WHERE 或者 HAVING，报字段不存在或逻辑不对，因为窗口计算发生在 WHERE 之后。
 - 窗口 ORDER BY 只写 salary 不写唯一键，工资并列时每次执行编号可能不同，取出来的前三名会抖动。
FOLLOWUPS:
 Q: RANK、DENSE_RANK、ROW_NUMBER 在这题里分别会取出几行？
 A: 结论取决于并列。假设某部门工资 100、100、90，ROW_NUMBER 得到 1、2、3 取前三行，两个 100 里可能只留一个；RANK 得到 1、1、3，前三名会把两个 100 和 90 都留下，实际三行但名次跳号；DENSE_RANK 得到 1、1、2，前两档共三行全留。如果业务说取工资最高的三个人，用 ROW_NUMBER 并按 id 兜底保证稳定；如果说取工资最高前三个档次，用 DENSE_RANK，行数可能超过三行。选之前先和业务确认口径，别默认。
 Q: MySQL 5.7 没有窗口函数，这题怎么写？
 A: 结论是用相关子查询或者自连接计数。写法是 SELECT * FROM emp e WHERE (SELECT COUNT(*) FROM emp x WHERE x.dept_id = e.dept_id AND x.salary > e.salary) < 3，含义是比自己工资高的人少于三个就算进前三。缺点是外层每行都要扫一遍同部门数据，复杂度是部门人数平方，几十万行就基本跑不动。优化思路是只对候选部门算，或者用变量模拟行号，但变量写法依赖执行顺序、不可靠。生产中更推荐升级到 8.0 或者用应用层按部门分批查询。
 Q: 分组 TopN 在数据量很大时怎么优化？
 A: 结论是减少参与排序的行数、让排序走索引、能用 LIMIT 就别全量开窗。具体做法：先用 WHERE 把时间范围、状态过滤掉；在 dept_id 和排序字段上建联合索引，让每个分区内部天然有序，减少 filesort；如果只要每部门第一名，可以先按 dept_id 分组的聚合拿到最大工资，再回表匹配，避免全量开窗。部门特别多而每部门数据少时，用 UNION ALL 或 LATERAL 逐个部门取 LIMIT 3 反而更快。最后一定要看执行计划里有没有 Using temporary。

===== sq-03 =====
TITLE: row_number、rank、dense_rank 的区别
ONE: 三者都按窗口内排序编号，row_number 严格递增不并列，rank 并列同名次且后续跳号，dense_rank 并列同名次但后续不跳号。
S60: 记一组数据就够：工资 100、100、90、80。ROW_NUMBER 给 1、2、3、4，两行 100 谁先谁后由排序键决定；RANK 给 1、1、3、4，并列占掉两个名次所以第三名直接跳过；DENSE_RANK 给 1、1、2、3，并列只占一个名次，名次连续。所以取固定条数用 ROW_NUMBER，奥运会那种并列金牌下一名是铜牌用 RANK，取前三档用 DENSE_RANK。三者都不影响聚合，只是编号规则不同。
S180: 验证 SQL 是 SELECT name, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn, RANK() OVER (ORDER BY salary DESC) AS rk, DENSE_RANK() OVER (ORDER BY salary DESC) AS drk FROM emp ORDER BY salary DESC。三个函数签名一样，都要求 OVER 里带 ORDER BY，不带 ORDER BY 时全部返回 1，因为没有排序就没有名次概念，这点常被拿来当陷阱题。区别只在并列处理：ROW_NUMBER 是无状态的递增计数器，遇到并列也强行给不同编号，具体谁在前取决于排序是否稳定，所以必须补唯一键 tie-break；RANK 是当前名次等于比自己大的行数加一，并列后下一名跳号；DENSE_RANK 是不同取值的个数，并列只算一档。再补充两个同族函数：NTILE(n) 把分区平均切成 n 桶，适合分位数分群；PERCENT_RANK 和 CUME_DIST 返回相对位置，做分位报表用。PARTITION BY 决定在哪个范围内编号，去掉 PARTITION BY 就是全表排名，加上就是组内排名。
S600LEN: 654
S600: 深挖先讲实现：RANK 和 DENSE_RANK 在排序键相同的行之间共享排名，本质是排序后对 peers 分组计数，ROW_NUMBER 则完全依赖物理输出顺序，所以同一个窗口里 ROW_NUMBER 的结果可以随索引、并行度、执行计划变化，而 RANK 只依赖值本身。这条差异决定了工程用法：要稳定分页、要导出对账，必须给 ROW_NUMBER 补唯一键；要对外展示名次，用 RANK 或 DENSE_RANK 更符合直觉。第二讲 NULL 的位置，MySQL 降序时 NULL 排最后、升序排最前，而 PostgreSQL 默认降序 NULL 在最前，跨库迁移时排名会整体错位，要显式写 NULLS LAST 或加 IS NULL 排序键。第三讲窗口 ORDER BY 和语句末尾 ORDER BY 是两回事，前者只决定编号顺序，不保证结果集输出顺序，很多线上问题就是只看编号顺序没加外层排序导致展示乱序。第四讲性能，三个函数共用一次排序，写了三个也只是一次 sort，代价主要来自排序本身，所以能用分区键走索引排序就别让优化器 filesort；同时不要为了排名 SELECT *，只取需要的列能减少临时表宽度。第五讲组合用法，常见的是 ROW_NUMBER 取最新一条、RANK 做并列榜单、DENSE_RANK 配合 COUNT(DISTINCT) 校验去重结果，还有用 RANK 差值识别连续区间。最后是口径沟通，面试官问取前三名时要主动问一句并列算不算都取，这比背定义更能体现你做过真实需求。
POINTS:
 - [done] ROW_NUMBER 严格 1 到 n 不并列，RANK 并列同名次并跳号，DENSE_RANK 并列同名次不跳号。
 - [done] 三者签名一致，都必须带 OVER 和 ORDER BY，不带 ORDER BY 时全部返回 1。
 - [done] PARTITION BY 决定编号范围，去掉就是全局排名，加上就是组内排名。
 - [done] ROW_NUMBER 的结果依赖排序稳定性，必须补唯一键做 tie-break，否则分页会重复或漏行。
PITFALLS:
 - 以为 ROW_NUMBER 在并列时按插入顺序给号，实际上只由窗口 ORDER BY 决定，键相同则顺序不确定。
 - 把窗口里的 ORDER BY 当成结果集输出顺序，忘了最外层再写一次 ORDER BY，展示名次是乱的。
FOLLOWUPS:
 Q: 数据是 100、100、90，三个函数的结果分别是什么？
 A: 结论是 ROW_NUMBER 给 1、2、3，RANK 给 1、1、3，DENSE_RANK 给 1、1、2。ROW_NUMBER 把两行 100 当成两个独立个体，谁排第一取决于有没有补唯一键；RANK 把并列看成并列第一，占掉第一和第二两个位置，下一个 90 就是第三；DENSE_RANK 也认并列，但只消耗一个档位，90 是第二档。所以取最高工资的三个人用 ROW_NUMBER 结果三行，取前三档工资用 DENSE_RANK 结果两行，业务口径不一样。
 Q: 为什么说用 ROW_NUMBER 做分页可能不稳定？
 A: 结论是排序键不唯一时，同一批数据多次执行得到的编号可能不同。窗口函数只保证按 ORDER BY 的键排序，键值相同的行之间没有约定顺序，可能受索引、并行扫描、数据页位置影响。如果按 rn 分段取页，第二页可能出现第一页已经出现过的行。解决办法是在 ORDER BY 里补一个唯一且稳定的键，比如主键 id，写成 ORDER BY create_time DESC, id DESC，这样排序是全序，编号就固定了，分页也不会重。
 Q: NTILE 和这几个函数有什么不同？
 A: 结论是 NTILE 分桶而不是排名。NTILE(n) 按窗口顺序把数据尽量平均切成 n 桶并返回桶号，行数不能被 n 整除时前面的桶会多一行，适合做四分位、十分位分群，比如按消费额把用户分成十档。它不关心具体名次，也不处理并列，两行相同值可能落在不同桶里。PERCENT_RANK 和 CUME_DIST 更接近排名，返回的是相对位置百分比，做分布报表时比 NTILE 更精确，代价是浮点比较要注意精度。

===== sq-04 =====
TITLE: 统计连续登录超过三天的用户，思路是什么
ONE: 登录日期减去按用户分区的行号，连续日期的差值恒定，相同差值就是同一段连续登录，再按用户加差值分组计数筛出大于等于三天的段。
S60: 核心是一个减法的技巧。先把登录日志按 user_id、login_date 去重，因为一天可能登多次；然后按 user_id 分区、login_date 升序用 ROW_NUMBER 打号，得到每天的行号；再用 login_date 减去行号天数的日期，连续登录的这些日期差值完全一样，断一天差值就变，所以这个差值就是连续段的标识；最后按 user_id 和这个标识分组，COUNT 大于等于 3 的用户就是连续三天以上登录的人。
S180: 完整写法分三层。第一层去重 WITH t AS (SELECT DISTINCT user_id, login_date FROM login_log)，一天多条记录必须先折叠，否则行号连加会让日期差乱跳。第二层打号 WITH r AS (SELECT user_id, login_date, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn FROM t)，行号在连续日期上顺序递增。第三层求标识 SELECT user_id, login_date, DATE_SUB(login_date, INTERVAL rn DAY) AS grp FROM r，连续段内日期和行号同增，差值恒定；断一天后日期跳、行号只加一，差值立刻变化，自然分出新段。最后 SELECT user_id, MIN(login_date) AS start_date, MAX(login_date) AS end_date, COUNT(*) AS days FROM 上面结果 GROUP BY user_id, grp HAVING COUNT(*) >= 3。日期字段必须是 date 类型，datetime 要先转 DATE，减的是天不是秒。

 Q: 为什么日期减行号的差值能标识连续段？
 A: 结论是连续日期和递增行号的差值恒定。设首日 d 对应行号 1，差值是 d 减 1 天；第二天是 d 加 1 天对应行号 2，差值还是 d 减 1 天；一直连续下去差值不变。一旦中间断了一天，日期变成 d 加 2 天而行号只到 2，差值变成 d，比原来大一天，于是自然分到新的一组。所以 grp 相同的行一定属于同一段连续登录，按它分组计数就是段长。这个技巧是 gaps and islands 的最简形式，要求数据先按日期去重且日期类型是 date。
 Q: 如果要找最长连续登录天数，SQL 怎么改？
 A: 结论是在分组结果外面再取一次最大值。内层还是按 user_id 和 grp 分组得到每段长度 COUNT(*)，外层写 SELECT user_id, MAX(days) FROM 这段 GROUP BY user_id，得到每个用户历史上最长的连续天数。如果要连区间一起给，就在内层保留 MIN 和 MAX 日期，外层按 days 倒序取第一条，可以用 ROW_NUMBER 再排一次。注意没有登录记录的用户不会出现，需要配合用户表 left join 补零。
 Q: 一天内登录多次，你想算连续活跃小时，思路要变吗？
 A: 结论是思路一样但要换成时间戳加 LAG 的通用海岛解法。因为小时级别不是等差的一行一天，行号乘法就不成立。做法是先按用户和时间排序，用 LAG 取上一行时间，算差值，差值超过一个小时的标记为新段起点，再用 SUM 累计标记得到段号，最后按段分组。检查点落到分钟级也一样。这类问题在日志分析里很常见，核心是把连续判定从日期运算转成相邻差值的阈值比较。

===== sq-05 =====
TITLE: 行转列和列转行分别怎么写
ONE: 行转列用 CASE WHEN 包聚合函数再按主体分组，列转行用 UNION ALL 把多列拼成多行，列动态时只能应用层拼 SQL 或用 JSON 聚合。
S60: 行转列是把维度取值变成列，本质是条件聚合，写法是 SELECT sid, SUM(CASE WHEN subject = '语文' THEN score END) AS chinese FROM score GROUP BY sid。列转行把多列拼成多行，用 SELECT sid, '语文' AS subject, chinese FROM t UNION ALL SELECT sid, '数学', math FROM t 上下拼，列多时用 CROSS JOIN 配合 CASE 只扫一次表。
S180: 行转列完整写法：SELECT student_id, MAX(CASE WHEN subject = '语文' THEN score END) AS chinese, MAX(CASE WHEN subject = '数学' THEN score END) AS math, SUM(CASE WHEN subject = '英语' THEN score END) AS english FROM score GROUP BY student_id。用 MAX 还是 SUM 取决于一个学生一门课是否只有一条记录，唯一就用 MAX 更安全，可能多条用 SUM 累加。CASE 不写 ELSE 时返回 NULL，正好让没考这门课的学生显示空而不是零，写 ELSE 0 会把缺考和零分混在一起。列转行列多时可以用 CROSS JOIN (SELECT '语文' AS subject UNION ALL SELECT '数学') k，再在外层用 CASE k.subject WHEN '语文' THEN chinese WHEN '数学' THEN math END，只扫一次表。更现代的做法是用 JSON：MySQL 的 JSON_OBJECT 配合 JSON_ARRAYAGG，PostgreSQL 的 jsonb_agg 和 jsonb_each，把动态列交给应用层展开。
S600LEN: 796
S600: 深挖先讲为什么 SQL 写不出真正的动态行转列。SQL 是静态编译的语言，列必须在写语句时就确定，而科目、月份这些维度取值来自数据，只有执行时才知道，所以纯 SQL 无法根据数据自动增加列。工程上三条路：一是列固定就用 CASE WHEN 写死，简单可控；二是在应用层先 SELECT DISTINCT subject 拿到列名，再拼接 SQL 字符串执行，要注意 SQL 注入和预编译缓存失效，拼接的列名必须来自白名单或者做转义，而且列一多语句长度和执行计划都会劣化；三是用 JSON 或数组类型把结果聚成一个字段，让前端或下游展开，MySQL 8 可以 JSON_OBJECTAGG 按课程聚成对象，PostgreSQL 用 jsonb_object_agg，这种写法列数不受限，但牺牲了 SQL 层的可筛选性。第二讲聚合函数的选择陷阱：CASE 加 MAX 适合一对一，CASE 加 SUM 适合多对一累加，用 SUM 且写了 ELSE 0 时缺考和零分不可区分；如果某学生一门课有多条成绩但业务只想取最新一条，要先按学生和课程用 ROW_NUMBER 取最新再转列，否则会累加错误。第三讲性能，行转列本质是一次分组扫描，GROUP BY 的键要建索引；列转行用 UNION ALL 会多次扫表，而 CROSS JOIN 展开只扫一遍，数据量大时差别明显，但 CROSS JOIN 版本可读性差。第四讲类型和顺序，列转行后行顺序由 UNION ALL 各分支决定，要稳定输出得在外层加排序键，常见做法是给每个分支加一个序号列再 ORDER BY。第五讲 Oracle 和 SQL Server 有原生 PIVOT 和 UNPIVOT 语法，PIVOT 里 FOR subject IN 后面同样要枚举值，所以也解决不了动态列，只是语法糖。面试时先问清列是固定还是动态，这是这题的分水岭。
POINTS:
 - [done] 行转列本质是条件聚合，用 SUM 或 MAX 包 CASE WHEN，再按主体分组，SELECT 里的列要写死。
 - [done] CASE 不写 ELSE 返回 NULL 可以区分缺考，写 ELSE 0 会把没考和考零分混在一起。
 - [done] 列转行用 UNION ALL 每列一条 SELECT 上下拼接，或者 CROSS JOIN 维度表配 CASE 只扫一次表。
 - [done] 维度取值是动态的时纯 SQL 做不到，要在应用层先查 DISTINCT 再拼 SQL，或者用 JSON 聚合交给下游展开。
PITFALLS:
 - 行转列用 SUM CASE 又写了 ELSE 0，缺考的学生显示 0 分，报表口径直接错，应该用 MAX 或让 ELSE 为 NULL。
 - 拼动态列名时直接字符串拼接用户可控的值，既不安全也无法命中预编译缓存，必须走白名单。
FOLLOWUPS:
 Q: 科目数量不固定，行转列还能用纯 SQL 写吗？
 A: 结论是不能。SQL 的列在编译期就固定，而科目要到执行时才知道，所以没法用一条静态语句自动产出动态列。三种替代：应用层先查比较 distinct 的科目列表，白名单校验后拼成 CASE WHEN 语句，这是最常见的做法，缺点是列一多语句膨胀、执行计划不稳定；用 JSON_OBJECTAGG 聚成一个 JSON 字段，列数不受限但下游要解析；或者在报表层用透视组件处理，SQL 只负责输出明细。面试时说清取舍比硬写一条错语句更加分。
 Q: 行转列时一个学生一门课有多条成绩，用 MAX 会丢数据吗？
 A: 结论是 MAX 只保留最大那条，如果多条都是有效成绩就会丢。要先明确业务口径：取最新一次考试就用 ROW_NUMBER 按考试时间倒序取 rn 等于 1 再转列；求和总分就用 SUM；取最高分才用 MAX。直接写 MAX 而不加说明会被追问。稳妥语句是先内层去重到学生加课程唯一，再用条件聚合，这样聚合函数选什么都没歧义。
 Q: 列转行后行数不对或者顺序乱，怎么排查？
 A: 结论先看 UNION 和 UNION ALL 的区别，再看维度表有没有重复。UNION 会去重并排序，导致本该保留的重复行被合并，行数变少；维度表如果有重复值，CROSS JOIN 会按笛卡尔积放大行数。顺序乱是因为 UNION ALL 不保证输出顺序，需要在外层显式 ORDER BY 一个稳定键，比如学生 id 加列序号。再加一个自检：比较转换前后的列数乘行数是否等于转换后的行数，不等就是维度有重复。

===== sq-06 =====
TITLE: 同一用户多条记录只保留最新一条，怎么删
ONE: 两种写法：自连接按业务键相等且更新时间更旧把自己连出来删掉，或者窗口函数按业务键分区、更新时间倒序编号，删编号大于 1 的行。
S60: 两条路。自连接把表当两张别名，条件是 a.user_id = b.user_id 并且 a.updated_at 小于 b.updated_at，时间相等时用 a.id 小于 b.id 兜底，旧记录都能连到更新的记录，删 a 即删非最新。窗口函数是先 SELECT id, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC, id DESC) AS rn，外层删 rn 大于 1。MySQL 不允许边查边删同一张表，子查询要包一层派生表。
S180: 自连接写法：DELETE a FROM user_log a JOIN user_log b ON a.user_id = b.user_id AND (a.updated_at < b.updated_at OR (a.updated_at = b.updated_at AND a.id < b.id))。含义是只要存在同用户且更新的记录，a 就该删；时间相同时用主键兜底保证每组只留一行。窗口函数写法：DELETE FROM user_log WHERE id IN (SELECT id FROM (SELECT id, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC, id DESC) AS rn FROM user_log) t WHERE t.rn > 1)。外面那层派生表 t 是为了绕开 MySQL 的 You can not specify target table for update in FROM clause 报错，PostgreSQL 和 Oracle 不需要。取舍是自连接兼容 5.7 但时间相等时容易留下多行；窗口函数可读性好、一次排序解决、并列处理直观，是首选。生产上先跑 SELECT 确认要删的行再在事务里删。

 Q: 为什么自连接写法要加 a.id < b.id 这个条件？
 A: 结论是处理时间戳相同的情况。如果两条记录 updated_at 完全一样，只写小于号时它们互相不满足 a 更旧，谁也连不到谁，结果一条都不删，重复数据保留下来。加上主键比较后，较小 id 的那条能连到较大 id 的那条并被删除，最终每组恰好留一行。这个兜底条件还保证了删除是确定性的，多次执行结果一致。窗口函数写法里同样要写 ORDER BY updated_at DESC, id DESC，道理一样。
 Q: 两种写法在数据量很大时谁更快？
 A: 结论是通常窗口函数更快，但不是绝对。自连接是 N 次探测的嵌套循环或哈希连接，重复用户越多中间结果越大，而且删除要回表定位每一行；窗口函数只排一次序，代价集中在排序和临时表上，分区基数小的时候优势明显。但如果表非常大且只有极少数用户重复，窗口函数会全表排序反而浪费，这时先 GROUP BY 找出重复用户再只处理这些用户更快。无论哪种，都要按 user_id 建索引，并用 EXPLAIN 看是否走索引。
 Q: 线上误删了怎么补救？
 A: 结论是先停写、再恢复、最后复盘。如果开了事务且未提交就回滚；如果已提交，用备份加 binlog 做时间点恢复，把误删区间的事务反向执行，或者从备份表按主键回插。预防上做三件事：删除语句先用 SELECT 同样条件核对行数；用 limit 分批删并观察影响行数是否符合预期；对重要表加逻辑删除列而不是物理删。另外 MySQL 的 safe update 模式能挡住不带主键或 LIMIT 的更新删除，应该打开。

===== sq-07 =====
TITLE: 怎么查找并删除表里的重复数据
ONE: 先按业务唯一键 GROUP BY 加 HAVING COUNT 大于 1 查出重复组，再保留每组最小或最大主键删其余，MySQL 要套派生表绕开边查边删限制。
S60: 分两步。查重是 SELECT email, COUNT(*) AS cnt FROM t_user GROUP BY email HAVING COUNT(*) > 1。删重可以直接自连接，DELETE t1 FROM t_user t1 JOIN t_user t2 ON t1.email = t2.email AND t1.id > t2.id，每组留最小那条。子查询版本要写成 NOT EXISTS 而不是 NOT IN，因为 NOT IN 的子查询里一旦有 NULL，条件恒为 unknown，一行都删不掉。
S180: 查重按业务键分组计数：SELECT email, COUNT(*) AS cnt, MIN(id) AS keep_id FROM t_user GROUP BY email HAVING COUNT(*) > 1 ORDER BY cnt DESC。删重三种写法：第一种保留最小 id，DELETE FROM t_user WHERE id NOT IN (SELECT keep_id FROM (SELECT MIN(id) AS keep_id FROM t_user GROUP BY email) t)，派生表是为了绕开 MySQL 1093；第二种自连接，DELETE a FROM t_user a JOIN t_user b ON a.email = b.email AND a.id > b.id，只删较大 id，每组自然留最小；第三种窗口函数，先给每组按 id 排序编号再删 rn 大于 1。坑在 NULL：NOT IN 子查询里只要出现 NULL，整体结果就是 unknown，一行都删不掉，所以业务键可能为空时改用 NOT EXISTS，写成 DELETE FROM t_user a WHERE EXISTS (SELECT 1 FROM t_user b WHERE b.email = a.email AND b.id < a.id)，NULL 比较不成立反而安全。

 Q: 为什么 NOT IN 遇到 NULL 会出问题？
 A: 结论是三值逻辑。NOT IN 等价于对列表里每个值做不等于并且用 AND 连起来，只要列表里有 NULL，与 NULL 比较得到 unknown，整个 AND 结果就可能是 unknown 而不是 true，WHERE 只保留 true 的行，所以一条都删不掉。而且这个行为是静默的，语句执行成功、影响行数为零。解决方式是改用 NOT EXISTS，或者在内层加 WHERE 键 IS NOT NULL，或者先过滤空值再删。
 Q: 保留最新一条而不是最小 id，语句怎么改？
 A: 结论是把排序依据换掉。子查询版本改成 SELECT MAX(id) 作为保留 id，但最大 id 不一定是最新业务时间，更准确是按更新时间取：先用 ROW_NUMBER 按业务键分区、更新时间倒序编号，保留 rn 等于 1 的 id，再删不在这些 id 里的行。自连接版本改成 a.updated_at < b.updated_at OR 时间相等且 a.id < b.id。关键是时间相同必须有主键兜底，否则同组会留多条。
 Q: 删完之后怎么防止再次产生重复数据？
 A: 结论是入口约束加幂等写入。数据库层给业务唯一键建唯一索引，写入用 INSERT 加 ON DUPLICATE KEY UPDATE 或者 INSERT IGNORE，避免并发插入两条相同记录；应用层做参数校验和幂等键，比如用请求 id 去重。如果业务键由多个字段组成，就建联合唯一索引，注意长度限制可以先算哈希列。加索引前要清理存量重复，否则建索引会失败。最后加一个定时巡检 SQL，每天跑一次查重并在有结果时告警。

===== sq-08 =====
TITLE: 累计求和、环比同比用 SQL 怎么写
ONE: 累计用 SUM OVER 带 ORDER BY 和 ROWS 帧，环比用 LAG 取上一期，同比用 LAG 偏移十二或按年自连接，除法用 NULLIF 防零。
S60: 都是窗口函数。累计写 SUM(amount) OVER (PARTITION BY user_id ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)。环比写 amount - LAG(amount, 1) OVER (PARTITION BY user_id ORDER BY dt)。同比把偏移改成十二，LAG(amount, 12) 取去年同月，或自连接年月减一。除法用 NULLIF 把零变 NULL 防除零，再用 ROUND 保留两位。
S180: 完整例子：SELECT dt, amount, SUM(amount) OVER (PARTITION BY user_id ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS acc, amount - LAG(amount, 1) OVER (PARTITION BY user_id ORDER BY dt) AS mom_diff, ROUND((amount - LAG(amount, 12) OVER (PARTITION BY user_id ORDER BY dt)) / NULLIF(LAG(amount, 12) OVER (PARTITION BY user_id ORDER BY dt), 0) * 100, 2) AS yoy_pct FROM daily_amount。要点一，累计必须显式写 ROWS 帧，不写时默认是 RANGE 帧，同一天有多行会被一起算进累计，出现同日两行累计值相同。要点二，LAG 的第二个参数是偏移行数不是天数，日期有缺口时上一条可能不是昨天，要严格按日算得先补全日期或者用自连接按日期减一匹配。要点三，比例计算分母用 NULLIF 处理零，分子分母都要防 NULL，展示层再套 COALESCE。
S600LEN: 896
S600: 深挖先说窗口帧。SUM 的默认帧是 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，RANGE 会把排序键相同的行视为 peers 一起纳入，所以同一天有两笔记录时，两行的累计值都会包含当天全部金额，看起来像重复加了。要严格逐行累加必须写 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，这也解释了为什么生产报表经常出现同日累计相等的怪异数据。第二讲缺口日期。LAG 按行偏移，如果某天没有数据，上一行是前天，环比就变成隔天对比而报表看不出来。严谨做法是先生成日期序列左连接数据把缺失日期补零，MySQL 8 用递归 CTE WITH RECURSIVE 生成日期，或者维护一张日历表，这是数仓最常见的做法。第三讲同比的两种写法：LAG 偏移十二适用于数据按月且月份连续；如果不连续或者要按自然年对比，用自连接 a.year = b.year - 1 AND a.month = b.month，或者把日期截断到月再按月份序号偏移。第四讲除零和 NULL，NULLIF(x, 0) 把零变 NULL 避免报错，但反过来 null 参与算术仍然得 null，展示层要 COALESCE；如果分子分母都为空，业务上可能想显示横杠而不是零，要在应用层处理。第五讲口径问题，累计求和的分区键决定业务含义，按用户分区是该用户生命周期累计，不分区是全站累计，混用会导致金额对不上；同比环比是看增长率还是看绝对差，要跟业务确认，增长率还要说明是百分比还是小数。第六讲性能，多个窗口函数只要分区和排序相同，优化器通常只排一次序，所以尽量复用同一个窗口定义；如果表很大，先聚合到天或月再做窗口，不要拿明细直接开窗，否则临时表会爆。最后提一句有专门的窗口函数可以替代自连接：NTILE 做分位，CUME_DIST 做累计占比，SUM OVER 做累计占比时分子用累计值分母用总和，分母可以写 SUM(amount) OVER (PARTITION BY user_id)，不带 ORDER BY 就是分区总和。

 - [done] 累计求和用 SUM OVER 加 ORDER BY，并显式写 ROWS 帧，否则默认 RANGE 帧会把同日数据一起累计。
 - [done] 环比用 LAG(值, 1) 取上一期做差，同比用 LAG(值, 12) 或按年份减一自连接。
 - [done] LAG 偏移的是行数不是天数，日期有缺口时要先补日历表，否则比较的不是上一期。
 - [done] 比例计算分母用 NULLIF 防除零，结果用 COALESCE 和 ROUND 处理显示。
PITFALLS:
 - 累计求和只写 ORDER BY 不写 ROWS 帧，同一天多条记录时每行累计值相同，看起来像重复加总。

FOLLOWUPS:
 Q: 默认窗口帧为什么会把同一天的数据算重复？
 A: 结论是 RANGE 帧按排序键的值而不是行号划定范围。默认帧是 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，其中 CURRENT ROW 在 RANGE 模式下代表当前行所在的那一组 peers，也就是排序键相同的所有行。所以同一天有两笔金额时，两行的累计都包含当天全部数据，数值相同。改成 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW 后按物理行逐行累加，第一行只到第一行，第二行才加上去。
 Q: 日期不连续时环比怎么保证比的是上一期？
 A: 结论是先把日期补全再算。做法是用日历表或者递归 CTE 生成完整日期序列，左连接业务数据把缺失日补零，这样每行都有一天间隔，LAG 就是严格前一天。如果不想补全，也可以不用 LAG 而用自连接 on 日期等于本期日期减一天，没有对应行时结果为 NULL，语义上表示昨天没有数据，比错位比较更诚实。月份同理，要注意月末和闰年。
 Q: 同比用 LAG 偏移十二和自连接各有什么适用场景？
 A: 结论是数据按月连续时用 LAG 简单，数据有缺口或跨自然年时用自连接稳妥。LAG 按行偏移，如果某个月整月没数据，偏移十二行其实是十三个月前，同比就错了；自连接用年份减一加月份相等做匹配，缺月就是 NULL，不会错位。代价是自连接要多一次扫描，而且需要年份月份能单独取出来，用日期函数截断即可。数仓里通常先补全月份维度再用 LAG，兼顾性能和正确性。

===== sq-09 =====
TITLE: 一条慢 SQL 你会怎么改写
ONE: 先看 EXPLAIN 判断全表扫描还是回表太多，再把子查询改 JOIN 或 EXISTS、把函数从条件左侧挪走改范围查询，让条件能走索引。
S60: 先别改，先看执行计划。用 EXPLAIN 看 type 是不是 ALL、rows 有多少、Extra 有没有 Using filesort 或 Using temporary，再看有没有用上索引。常见三类病：一是条件左侧套函数，比如 DATE(create_time) 等于某天，索引直接失效，改成大于等于当天零点且小于次日零点；二是子查询写成 IN，旧版 MySQL 会物化或者走半连接，改成 JOIN 或 EXISTS；三是隐式类型转换，varchar 字段拿数字比较，索引失效。改完再对比执行计划确认。
S180: 举个例子，改写前是 SELECT * FROM orders WHERE DATE(create_time) = '2025-01-01' AND user_id IN (SELECT id FROM users WHERE city = '杭州')。改写后是 SELECT o.id, o.user_id, o.amount, o.create_time FROM orders o JOIN users u ON u.id = o.user_id WHERE o.create_time >= '2025-01-01' AND o.create_time < '2025-01-02' AND u.city = '杭州'。三处变化：第一，DATE(create_time) 改成范围条件，对索引列套函数无法用 B+ 树有序性定位，改开区间就能走 create_time 索引做范围扫描；第二，IN 子查询改成 JOIN，避免物化临时表，也让优化器有更多连接顺序可选，但 users 到 orders 是一对多，只需要订单时加 DISTINCT 或改 EXISTS；第三，SELECT 把星号换成明确列，这些列都在索引里就是覆盖索引，省掉回表。其他失效场景要能背：左模糊、OR 连未建索引的列、NOT IN、字符串字段传数字、复合索引不满足最左前缀、索引列上做运算。

S600: 深挖方法论。第一步永远是拿证据，用 EXPLAIN 看访问类型和预估行数，用 EXPLAIN ANALYZE 看实际耗时分布，再结合慢查询日志确认是偶发还是常态，别凭感觉上手改。第二步判断是扫描多还是回表多：type 是 ALL 且 rows 很大说明扫描问题，type 是 ref 但 rows 只有几千却慢，多半是回表随机 IO，这时要建覆盖索引。第三步才是改 SQL，常见套路有四类。子查询改连接：IN 子查询在 MySQL 5.6 之后有半连接优化，但遇到含聚合、含 LIMIT 或者相关子查询时还是可能物化，改 EXISTS 通常更稳，语义上 EXISTS 碰到第一条就短路，适合判断存在性，JOIN 适合要取子表字段。函数导致失效：条件左侧套 DATE、YEAR、SUBSTR、CAST 都会让索引失去有序性，统一改成对常量做运算而不是对列做运算，比如把 2025-01-01 转成区间。隐式转换：字符串列和数字比较时 MySQL 会把列转成数字再比，索引直接废掉，这个坑在手机号、订单号字段上特别常见。OR 改写：OR 两侧字段不同时优化器可能走不了索引，可以拆成 UNION ALL 两个能走索引的查询。第四步要考虑改写是否改变语义，JOIN 一对多会让行数放大，原来 IN 是去重的，改 JOIN 往往要加 DISTINCT，DISTINCT 又可能触发临时表，未必更快，要用数据实测。第五步看索引设计，联合索引要按等值在前、范围在后的顺序，覆盖索引把 SELECT 需要的列都放进去，注意索引列太多会拖慢写入，还要避免在区分度低的列上建单列索引。最后要有兜底手段：读写分离、缓存热点结果、把大查询拆成预聚合的统计表，或者把报表查询挪到从库和离线数仓，不是所有慢 SQL 都该在 OLTP 主库上硬优化。

 - [done] 条件左侧套函数会让索引失效，改写成对常量运算的范围查询，比如日期改成大于等于当天小于次日。

 - [done] 隐式类型转换、左模糊、OR 跨列、复合索引不满足最左前缀都会让索引失效，要逐条排查。
 - [done] 改写要验证语义不变，并用实测执行时间和扫描行数对比，覆盖索引能显著减少回表。

FOLLOWUPS:
 Q: 为什么在索引列上套函数会导致索引失效？
 A: 结论是 B 加树索引存的是列的原始值，按原始值有序排列。条件写成 DATE(create_time) 等于某天时，数据库必须对每一行先算函数再比较，无法利用索引的有序性做二分定位，只能全表扫描。同理在列上做加减乘除、类型转换、字符串拼接都会失效。正确做法是把运算挪到常量侧，写成 create_time 大于等于起始时间且小于结束时间，这样索引列保持裸值，优化器能做范围扫描。MySQL 8 支持函数索引，可以给 DATE(create_time) 建索引，但会额外占空间，优先改写法。
 Q: IN 子查询和 EXISTS 在这题里怎么选？
 A: 结论是看语义和优化器。EXISTS 只判断是否存在，找到第一条就短路，适合过滤型条件，而且它是相关子查询，外层每行执行一次，子表有索引时很快。IN 子查询可能被优化器改写成半连接，也可能物化成临时表，含聚合或 LIMIT 时基本无法优化。要取子表字段就只能 JOIN。JOIN 的问题是一对多会放大行数，需要 DISTINCT 或者先按关联键聚合，而 EXISTS 天然不会放大。所以默认推荐 EXISTS，需要字段时再 JOIN 并去重。
 Q: 联合索引的列顺序怎么定，最左前缀是什么？
 A: 结论是等值条件放前面、范围条件放后面，最左前缀指查询必须从索引第一列开始连续使用才能命中。比如建了 a、b、c 三列索引，where a 等于 1 and b 大于 2 能用上前两列，where b 等于 2 就完全用不上。如果同时有多个等值列，把区分度高的放前面收益更大。范围列之后的列无法再用于定位，只能做索引覆盖。另外要注意，把范围条件放前面会让后面的等值列失效，这是最常见的顺序错误。

===== sq-10 =====
TITLE: limit 一百万 offset 二十很慢，怎么优化
ONE: 慢在要扫描并丢弃前一百万行，用延迟关联先把主键分页出来再回表，或者改成游标分页按上一页最后一个 id 往后取，彻底避免大偏移。
S60: limit 大偏移不是直接跳过，而是先取出一百万零二十行再丢弃前一百万行，越后越慢。两个改法。延迟关联是 SELECT o.* FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id，子查询只走主键，回表二十次。游标分页是 SELECT * FROM orders WHERE id > 上一页最后一个 id ORDER BY id LIMIT 20，用条件定位代替数偏移，业务上可限制最大页数。
S180: 先讲原因：LIMIT offset, size 的执行方式是扫描满足条件的行，跳过 offset 行，再返回 size 行，被跳过的行虽然不返回但每一行都要读，回表型查询还要为每行做一次随机 IO，一百万偏移就是一百万次无效劳动，所以耗时随页码线性增长。方案一延迟关联：SELECT o.* FROM orders o JOIN (SELECT id FROM orders WHERE status = 'PAID' ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id。子查询只读主键索引，页内数据密集，扫描代价远低于读整行，外层再按 id 回表二十次。前提是排序字段和过滤条件都在索引里，否则子查询照样要回表。方案二游标分页：SELECT id, amount, create_time FROM orders WHERE status = 'PAID' AND id > 1000000 ORDER BY id LIMIT 20，把上一页最后一条的 id 传给下一页，用索引范围定位，无论翻到多深都是常数代价。限制是不能跳页、排序键必须唯一且稳定。方案三业务限制最大可翻页数，或改用搜索引擎的 search_after。

S600: 深挖分场景。第一，排序键是主键或索引列时，延迟关联效果最好，因为子查询可以覆盖索引只扫索引页；如果排序键不是索引列，比如按 create_time 倒序但没建索引，优化器要先 filesort 全量排序，此时优化排序索引比改写分页更关键，建 create_time 加 id 的联合索引让排序走索引顺序。第二，count 也是深分页的隐性成本，前端要显示总条数时 SELECT COUNT(*) 会全量扫描，可以改成近似值、缓存总数或者只做无限加载不显示总页数。第三，游标分页的限制要讲清楚：不能随机跳页，只能上一页下一页；排序键必须唯一，否则同值行在边界处可能重复或遗漏，所以要组合排序键，比如 create_time 加 id，条件写成 create_time 小于上一页时间或者时间相等且 id 小于上一页 id；数据实时插入时新数据会挤占位置，表现为翻页过程中出现重复，这是可接受的最终一致体验。第四，索引设计上，覆盖索引是核心：建立过滤条件加排序键加返回列的联合索引，让子查询完全在索引里完成，不产生回表，这是延迟关联真正快的原因。第五，其他方案：把深分页结果物化成临时表或缓存；用主键范围预估偏移，比如只允许跳到某 id 附近；把列表页做成按时间分区的历史归档，用户默认只看最近数据；ES 的 search_after 也是游标思想。第六，验证方法：用 EXPLAIN 看子查询是不是 Using index，外层是不是 eq_ref 或 const，实际对比优化前后扫描行数和响应时间，测试要造足量数据，几百行看不出差异。最后强调，深分页的本质问题是偏移量线性成本，只要还依赖 offset 就没有根治办法，游标分页和业务妥协才是终局。

 - [done] LIMIT 大偏移慢的本质是扫描并丢弃前 offset 行，耗时随页码线性增长，不是直接跳到目标位置。
 - [done] 延迟关联让子查询只走索引取主键，外层再按主键回表少量行，前提是过滤和排序都能走索引。

PITFALLS:
 - 以为 LIMIT 1000000, 20 是直接定位到一百万行，实际是先读书一百万行再丢弃，数据越深越慢。
 - 延迟关联的子查询里加了 SELECT * 或者带了不在索引里的过滤条件，子查询照样回表，优化等于没做。
FOLLOWUPS:
 Q: 延迟关联为什么能快，原理是什么？
 A: 结论是减少了无效回表。原语句要为前一百万行每一行读出完整数据行，主键索引之外的列存在聚簇索引或回表里，每次都是随机 IO。改成子查询只查主键 id 后，如果排序和过滤都在同一个索引上，子查询就是纯索引扫描，索引页紧凑、顺序读、命中率高，代价远小于读整行；外层用 id 做等值匹配只回表二十次，随机 IO 从一百万次降到二十次。前提是子查询能覆盖索引，一旦 SELECT 了索引外的列，它又要回表，优化就失效了。
 Q: 游标分页有什么缺点，什么业务不能用？
 A: 结论是不能随机跳页、排序键必须唯一稳定、实时数据会错位。用户只能上一页下一页，无法直接跳到第五十页，后台管理类需要页码跳转的场景不适用。排序键不唯一时同值行在边界会重复或遗漏，所以要组合排序键做全序比较。数据边翻边插入时，新数据会把旧数据往后挤，下一页可能重复出现已看过的内容，这是游标的固有特性，通常用快照时间过滤缓减。另外参数从页码变成游标，接口要跟着改，前端也要改成无限滚动。
 Q: 如果必须显示总页数，count 很慢怎么办？
 A: 结论是别每次都精确统计。可以缓存总数并设置过期时间，允许短暂不一致；或者只统计近似值，用 EXPLAIN 的 rows 估算；或者在业务上只显示有没有下一页，不显示总页数，很多信息流产品就是这么做的。如果确实要精确，把 count 拆到从库或离线任务里算，主库只负责取当页数据。还可以按时间分区，只统计最近一段时间的数据，历史数据归档后单独查询。核心是接受 count 和列表数据可以不同步。
