# 口述稿（speak）重写规范 —— MySQL / 中间件

每题三层口述稿，全部是**面试现场能直接说出口的第一人称口语稿**。现有 `currentSpeak` 多数不达标（60 秒层只有几十字、3 分钟层和 60 秒层一样长），把它当素材而不是要保护的对象：可以重写、重组、换例子。

## 输出结构

```json
[
  { "id": "<题目 id>", "speak": { "s60": "…", "s180": "…", "s600": "…" } }
]
```

字符串内用 `\n\n` 分段（页面按换行切段渲染）。不要写代码围栏，除非题目本身就是讲 SQL/命令。

## 三层各自的硬指标

| 层 | 定位 | 汉字数 | 折算口播 | 段落 |
|---|---|---|---|---|
| `s60` | 电梯版，面试官说「简单说说」 | **200–260** | 55–70 秒 | 3–5 段 |
| `s180` | 正式面主答，默认展开 | **580–720** | 2 分 45 秒–3 分 10 秒 | 6–8 段 |
| `s600` | 深挖，面试官说「展开讲讲」 | **720–920** | 3 分 30 秒–4 分 30 秒 | 5–8 段 |

（换算口径：汉字 4.3 字/秒，含段落停顿约 250 字/分钟。**不要写超出上限的内容**，宁可少写不要注水。）

## 每层的写法

**s60**：结论 → 2~3 个支撑点（每点一个名词起头）→ 一句取舍或边界 → 收尾抛钩子。第一句必须能单独当答案，不铺垫、不自我介绍。

**s180**：把 s60 的每个支撑点各展开一段，每段第一句仍是结论句。必须有：一个具体机制（页/索引/日志/线程模型/协议）、一到两个具体数字或阈值、一处「什么时候不这么用」。

**s600**：在 s180 基础上加机制细节、版本演进、参数名、故障归因。至少两个具体参数或字段名（如 `innodb_flush_log_at_trx_commit`、`maxmemory-policy`、`cleanup.policy`、`index.refresh_interval`），至少一处故障现象 + 归因。

## 口吻

研三应届生秋招/春招现场，第一人称。短句为主，允许「我这边」「说白了」「其实」少量插入，允许重复关键词。

**禁止**：加分点 / 拉开差距 / 最容易丢分 / 但注意 / 整个推翻 / 我分三层讲（最多一次）/ 任何评价自己讲得好不好的内心独白。

## 准确性红线

- 版本必须标清：MySQL 5.7 / 8.0（8.0 才有 CTE、窗口函数、`innodb_redo_log_capacity`）；Redis 6.0（多线程 IO）/ 7.0（Function、多线程 IO 默认开）；RocketMQ 4.9 / 5.x（Pop 消费、Proxy）；Elasticsearch 7.x / 8.x（默认开启安全）；Kafka 2.8+ KRaft / 3.x。
- 数字要准：InnoDB 页 16KB、`innodb_buffer_pool_size`、binlog 三种格式、Redis 跳表 + 哈希表双索引、RocketMQ CommitLog 1GB 定长、Kafka 分区不可减、ES 倒排 + FST。
- 不确定的量化结论不写；写「量级」也别编具体数值。
- **不许编项目事实**。素材里没有项目锚点，就用通用判断标准（什么时候不用 / 怎么选 / 怎么排查），不要虚构「我们项目用了 X」。

## 输出纪律

- UTF-8 无 BOM，顶层数组，元素数 = 任务给定题数，`id` 与素材一致。
- 写完自验：`JSON.parse` 通过、逐题打印三层汉字数。
- 只写任务指定的那一个分片文件，不改题目源文件，不跑构建。
