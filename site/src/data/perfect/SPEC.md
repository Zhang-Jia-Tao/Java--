# 满分口语版（perfect）撰写规范

产出物是**面试现场能直接说出口的第一人称口播稿**，不是书面答案。每题存两档：`short`（60–90 秒主答案）与 `deep`（面试官说「展开讲讲」时的弹药库）。原文 / 必答点 / 硬伤 / 项目锚点是素材，不是要保护的对象——重写、重组、补机制都可以。

## 输出结构

```json
[
  {
    "id": "<题目 id>",
    "perfect": {
      "short": { "s": ["第一段", "第二段"] },
      "deep": { "s": ["第一段", "第二段"] },
      "hook": "把追问引到哪个方向（≤20 字，名词级）",
      "hookLabel": "钩子",
      "why": "为什么这么组织（80–160 字）",
      "diff": ["相对原文改了什么，一条一句"]
    }
  }
]
```

不要写 `seconds`（合并脚本按语速公式统一算）。`title` / `voice` 也由脚本补。

## short：60–90 秒主答案（汉字 200–280）

- 段落 5–8 段，一段一个意思，段落之间不靠「接下来」「首先其次」衔接。
- 顺序固定：**结论 → 核心机制（最多两代/两层）→ 两三个高频差异 → 一个坑 → 一句项目落点 → 钩子**。
- 项目落点必须是**「什么时候不用」或「怎么选」**的判断句，不是「项目里用了 X」。素材里没有项目锚点时，写通用判断标准，不编造项目名。
- 最后一段是钩子，一句话，点名下一层要讲的具体机制（如 `sizeCtl 并发扩容`、`AQS 的 state`）。
- 数字只在必须时报，报了就写准（如 `16 个 Segment`、`8 和 64`）。

## deep：展开版（汉字 700–1100，允许压到 600）

- 段落 8–15 段。比 `short` 多出来的必须是**机制、边界、代价**，不是同义反复。
- 每一段第一句都是结论句，能单独摘出来当答案。
- 必须补上素材里 `checklist` 标为 `missing` 的点，并把 `hardErrors`/`deductions` 里的错误表述改对。
- 至少一处落到具体字段名 / 参数名 / 版本号（如 `sizeCtl`、`tabAt`、`JDK21 的 ZGC 分代`）。
- 至少一处给「代价」或「边界」：这个方案在什么条件下不成立。
- 段首用主题词或名词起头（`结构上`、`null 上`、`扩容上`），全篇设问最多一处。

## 口吻（研三应届生 · 秋招现场）

- 短句为主，允许重复关键词，允许「我这边」「说白了」「其实」少量口语插入。
- 禁止内心独白：「这是加分点」「最能拉开差距」「最容易丢分」「注意」「但这一句……」全部不要。
- 禁止评价自己的表达：「我分三层讲」可以保留一次作开场，其余不要。
- 用「我不自己套锁，用它给的原子方法」这类**判断句**，不用「我们应该」这种空话。

## 准确性红线

- 版本相关结论必须写明适用版本（JDK7 / JDK8 / JDK17+、Spring Boot 2 / 3）。
- 不确定的量化数字不要写；宁可写「量级」也不编具体数。
- 反向表述（「JDK8 修了环但仍不安全」）必须给出原因，不能只给结论。

## 输出纪律

- 字符串内不要裸换行；需要分层用 `\n`。
- UTF-8 无 BOM，顶层数组，`JSON.parse` 可解析。
- 数组元素个数 = 任务给定题数，`id` 与任务一致。
- 只写任务指定的那一个分片文件，不改题目源文件，不跑构建。
- 若输出文件已存在且元素数等于题数，直接回复 done，不重写。
